# 홈 화면 위젯
----

**홈 화면 위젯**은 앱이 꺼져 있어도 **OS가 직접 그리는** 작은 UI다. 앱이 그리는 게 아니라, 앱이 넘겨준 데이터로 **OS가 정해진 틀 안에서** 그린다.

그래서 위젯은 "작은 앱 화면"이 아니라 **"OS에 맡겨 둔 정지 사진"** 에 가깝다. 이 한 문장에서 위젯의 모든 제약이 나온다.

> 기준: Apple WidgetKit 문서 · Android AppWidget 문서 · expo-widgets · react-native-android-widget (2026-10-15 확인)
> 출처: https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date · https://developer.android.com/develop/ui/views/appwidgets · https://developer.android.com/reference/android/appwidget/AppWidgetProviderInfo · https://docs.expo.dev/versions/latest/sdk/widgets/ · https://saleksovski.github.io/react-native-android-widget/

## 1. 플랫폼별 구현 기술

| | iOS | Android |
| ----------- | ----------- | ----------- |
| 프레임워크 | WidgetKit | AppWidget |
| UI | SwiftUI (제한된 뷰만) | RemoteViews (XML 레이아웃) 또는 Jetpack Glance (Compose 문법) |
| 앱과 공유 저장소 | App Group의 `UserDefaults` | `SharedPreferences` |
| 갱신 주도권 | **OS**가 타임라인·예산으로 | **앱**이 밀어 넣음 (+ 최소 주기 폴링) |

* Android `RemoteViews` 는 *"모든 레이아웃·뷰를 지원하지 않고, 커스텀 뷰는 쓸 수 없다"* (공식 문서). 다른 프로세스(런처)가 대신 그리기 때문이다
* 공식 문서는 새로 만든다면 **Jetpack Glance**를 권한다

## 2. 왜 웹으로 못 만드나

위젯은 런처(홈 화면 앱) 프로세스 안에서 OS가 그린다. 그 자리에는

* [[웹뷰]]를 띄울 수 없고
* JS가 **상시 실행되지 않는다**

PWA든 [[하이브리드 앱]]이든 웹 기술로는 위젯을 못 만든다. [[React Native]]로 해도 **위젯 부분은 결국 네이티브 영역**이다. RN/Expo 라이브러리는 JSX로 쓰게 해 줄 뿐, 결과물은 SwiftUI/RemoteViews다 (5장).

## 3. 데이터 흐름

위젯은 스스로 서버를 부르기보다, **앱이 써 둔 값을 읽어서 다시 그리는** 구조가 기본이다.

```
앱 (또는 푸시로 깨어난 백그라운드)
   │  ① 공유 저장소에 쓰기
   ▼
공유 저장소 ── iOS: App Group UserDefaults / Android: SharedPreferences
   │  ② "다시 그려" 요청 (iOS reloadTimelines / Android updateAppWidget)
   ▼
위젯이 읽어서 다시 그림
   │  ③ 탭
   ▼
딥링크로 앱의 해당 화면 이동
```

* 위젯은 **버튼 하나하나가 앱 화면으로 가는 링크**라고 생각하면 설계가 쉽다. 복잡한 입력은 앱으로 넘긴다
* 앱이 꺼져 있을 때도 갱신하려면 앱을 깨워야 한다 → 6장

## 4. 갱신 제약

### iOS — 타임라인과 리로드 예산
iOS 위젯은 **타임라인**(시각 + 그 시각에 보여줄 데이터 목록)을 OS에 미리 넘긴다. OS는 각 시각이 되면 그 항목으로 그린다. 타임라인을 다시 요청하는 것이 **리로드**이고, 리로드에는 **예산**이 있다.

| 항목 | 공식 문서 내용 (2026-10-15 확인) |
| ----------- | ----------- |
| 하루 예산 | 자주 보는 위젯 기준 **보통 40~70회** (대략 15~60분 간격). 위젯 인스턴스마다 따로 |
| 예산 주기 | 24시간. 자정에 딱 리셋되는 게 아니라 사용자 패턴에 맞춰 조정 |
| 예산 안 쓰는 경우 | 앱이 **포그라운드**일 때, 앱이 Now Playing 앱일 때, StandBy 표시 갱신, 시스템 외형·언어 변경 |
| 항목 간격 | 타임라인 항목은 **약 5분 이상** 간격으로 |

* 미리 예약한 타임라인 항목이 그 시각에 그려지는 건 **리로드가 아니다.** 예측 가능한 변화(예: 산책 후 경과 시간)는 타임라인에 미리 넣어 두는 게 예산을 아끼는 방법이다
* 예측 불가한 변화(서버 이벤트)만 리로드로 처리한다
* 같은 내용으로 리로드하면 예산만 낭비된다 → 공유 저장소에 쓰기 전에 **표시할 값의 signature(해시)를 비교**해서 바뀌었을 때만 리로드 요청 (piew-dev에서 쓴 방식)
* Apple 문서에는 타임라인과 별개로 **WidgetKit 푸시 알림**으로 위젯을 갱신하는 방법도 나온다. 지원 OS 버전과 RN 라이브러리 지원 여부는 **미검증**

### Android — 앱이 민다
* `updatePeriodMillis` 로 OS 주기 갱신을 요청할 수 있지만 *"30분에 한 번보다 자주 전달되지 않는다"* (공식 API 문서)
* 그보다 빠른 갱신은 **앱 쪽에서 직접 `updateAppWidget` 을 호출**해야 한다. 즉 앱 코드가 돌아야 한다

### 공통
* **GIF·영상 재생 불가.** 애니메이션은 정지 이미지로 대체한다 (펫바타 캐릭터 애니메이션도 정지 이미지)
* 위젯 자체에서 긴 네트워크 작업을 기대하지 말 것. 데이터는 앱이 미리 채운다

## 5. RN/Expo에서 JSX로 작성하기

| 플랫폼 | 라이브러리 | 방식 |
| ----------- | ----------- | ----------- |
| iOS | `expo-widgets` | `'widget'` 지시어를 붙인 컴포넌트를 `@expo/ui/swift-ui` 부품으로 작성 → SwiftUI 위젯 |
| Android | `react-native-android-widget` | `FlexWidget`·`TextWidget` 같은 위젯 전용 컴포넌트 → Android 위젯 |

### expo-widgets (iOS)
* **iOS 전용**, [[Expo]] Go 불가 → Development Build 필요
* `'widget'` 컴포넌트는 **격리된 런타임**에서 돈다. 공식 문서: *"`@expo/ui/swift-ui` 컴포넌트만 쓸 수 있고, React 훅·앱 상태·비동기 작업은 쓸 수 없다."* 위젯이 "그림만 그리는 함수"라는 걸 API가 강제하는 셈이다
* App Group이 필수이고 기본 ID는 **`group.<번들 ID>`** 다 (`groupIdentifier` 로 변경 가능)
* [[Live Activity]] 도 같은 라이브러리로 만든다

### react-native-android-widget (Android)
* Expo config plugin 제공
* 위젯 이벤트(`WIDGET_ADDED`·`WIDGET_UPDATE`·`WIDGET_CLICK` 등)를 받는 **task handler**를 등록해야 한다

### 함정: task handler는 엔트리 파일에서 등록한다
위젯 이벤트는 앱 화면 없이 **헤들리스(headless) JS** 로 처리된다. 이때는 화면 모듈이 로드되지 않으므로, 핸들러를 화면 컴포넌트 파일 안에서 등록하면 **등록이 안 된 상태**가 된다. 증상:

```
No task registered for key RNWidgetBackgroundTask
```

공식 문서대로 **엔트리 파일**에서 등록한다. expo-router를 쓰면 `index.ts` 를 만들고 `package.json` 의 `main` 을 그쪽으로 바꾼다.

```ts
// index.ts  (package.json: "main": "index.ts")
import 'expo-router/entry';
import { registerWidgetTaskHandler } from 'react-native-android-widget';
import { widgetTaskHandler } from './src/widgets/widget-task-handler';

registerWidgetTaskHandler(widgetTaskHandler);
```

## 6. 앱이 꺼져 있을 때 갱신하기 — 푸시

앱이 꺼져 있으면 공유 저장소에 쓸 사람이 없다. 그래서 서버가 [[푸시 알림]]으로 앱을 백그라운드에서 잠깐 깨운다.

| | iOS | Android |
| ----------- | ----------- | ----------- |
| 수단 | silent push (`content-available`) | FCM data message |
| 누가 만드나 | **백엔드** (APNs 발송) | **백엔드** (FCM 발송) |

* 이건 **백엔드 작업**이다. 프론트만으로는 끝나지 않으므로 일정에 미리 넣어야 한다
* silent push는 OS가 전달을 보장하지 않는다. "언젠가 갱신됨" 정도로 기대할 것 (전달 빈도 정책은 **미검증**)

### piew-dev 데모 사례 — 하지 말 것
시연에서 실시간 갱신을 보여 주려고 **무음 오디오를 재생해 앱을 백그라운드에서 살려 두고, 롱폴링으로 서버를 기다렸다가** 위젯을 갱신했다. 시연은 됐지만

* 오디오 백그라운드 모드를 오디오 재생 외 목적으로 쓰는 것이라 **App Store 반려 위험**이 크다
* 배터리를 계속 쓴다

실서비스는 **푸시 기반으로 대체**한다. 데모용 꼼수와 운영 설계를 구분할 것.

## 7. Live Activity와의 차이

| | 홈 화면 위젯 | [[Live Activity]] |
| ----------- | ----------- | ----------- |
| 위치 | 홈 화면 (+ 잠금화면 위젯) | 잠금화면 · 다이나믹 아일랜드 |
| 수명 | 사용자가 지울 때까지 상시 | 진행 중인 일 하나 (배달·산책 등) 동안만 |
| 갱신 | 타임라인 + 리로드 예산 | **ActivityKit push 토큰**으로 서버가 APNs로 직접 갱신 |
| 앱을 깨워야 하나 | 대개 그렇다 | 아니다 — 서버가 바로 업데이트 |

Apple 문서: ActivityKit으로 받은 push 토큰을 서버에 보내면, 서버가 APNs로 Live Activity를 **시작·갱신·종료**할 수 있다. 일반 푸시처럼 User Notifications 프레임워크로 등록하는 게 아니라 ActivityKit에서 토큰을 받는다.

**판단 기준**: "지금 진행 중이고 곧 끝나는 일"이면 Live Activity, "언제 봐도 의미 있는 요약"이면 위젯.

## 8. 계정·식별자 주의

* **App Group ID는 번들 ID에서 파생**된다 (`group.<번들 ID>`). 번들 ID가 바뀌면 App Group도 새로 만들어야 하고, 앱과 위젯 익스텐션 양쪽 프로비저닝 프로필을 다시 받아야 한다 → [[코드 서명(Code Signing)]]. **번들 ID 확정 전에는 App Group을 등록하지 말 것**
* 무료 Apple 계정(Apple Developer, 유료 멤버십 없음)도 **App Groups capability는 지원**한다. 반면 **Push Notifications는 무료 계정에서 지원하지 않는다** — 푸시 기반 갱신·Live Activity 원격 갱신을 테스트하려면 유료 멤버십(ADP)이 필요하다 ([Supported capabilities (iOS)](https://developer.apple.com/help/account/reference/supported-capabilities-ios), 2026-10-15 확인)
* 위젯 코드(Swift/Kotlin 결과물)는 네이티브 레이어라 [[EAS Update]]로 못 고친다. 위젯 수정 = 새 빌드 + 심사

## 장단점

### 장점
* 앱을 안 열어도 정보가 보인다 → 매일 보는 앱의 리텐션 장치
* 탭 한 번에 해당 화면으로 ([[딥링크]]) — 진입 경로가 짧아진다

### 단점
* OS가 주도권을 쥔다. iOS는 예산, Android는 30분 주기 하한
* 실시간 갱신은 **백엔드 푸시가 있어야** 가능하다
* 애니메이션·영상·복잡한 입력 불가
* 플랫폼마다 구현이 달라 **두 벌**을 만든다 (JSX 라이브러리도 iOS·Android가 별개)
* OTA 불가 — 수정마다 스토어 심사

## 정리
* 위젯 = OS가 그리는 정지 사진. 웹뷰·상시 JS 불가 → 웹으로 못 만든다
* 흐름: 앱이 공유 저장소에 쓰기 → 리로드 요청 → 위젯이 읽어 그림 → 탭은 딥링크
* iOS는 하루 40~70회 리로드 예산(공식). 예측 가능한 변화는 타임라인으로, 같은 값이면 signature 비교로 리로드 생략
* Android는 `updatePeriodMillis` 30분 하한. 빠른 갱신은 앱이 민다
* 앱이 꺼져 있을 때 갱신 = silent push / FCM data message = 백엔드 일
* Android task handler는 엔트리 파일에서 등록. App Group은 번들 ID 확정 후
