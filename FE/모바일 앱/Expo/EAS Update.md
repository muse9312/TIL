# EAS Update
----

**[[EAS]]의 [[OTA 업데이트]] 서비스.** JS 코드·스타일·이미지 같은 **업데이트 레이어**를 스토어 심사 없이 이미 설치된 앱에 바로 내려보낸다.

> 기준: EAS Update · expo-updates 공식 문서 (2026-10-15 확인)
> 출처: https://docs.expo.dev/eas-update/introduction/ · https://docs.expo.dev/eas-update/how-it-works/ · https://docs.expo.dev/eas-update/runtime-versions/

## 1. 원리 — 앱은 두 층이다

[[React Native]] 앱의 바이너리는 두 층으로 나뉜다.

```
┌──────────────────────────────┐
│ 업데이트 레이어 (교체 가능)      │  JS 번들 · 이미지 · 폰트
│  ← EAS Update가 바꾸는 곳       │
├──────────────────────────────┤
│ 네이티브 레이어 (바이너리에 고정) │  Swift/Kotlin 코드 · 네이티브 모듈
│  ← 바꾸려면 새 빌드 + 스토어 심사  │  · 권한 · SDK
└──────────────────────────────┘
```

화면과 로직 대부분이 JS에 있으므로, 위층만 갈아끼워도 대부분의 수정이 배포된다. 웹 배포가 빠른 것과 같은 이유다.

### 동작 순서
1. 앱 시작 시 `expo-updates` 라이브러리가 서버에 새 업데이트가 있는지 확인 (기본 동작)
2. 있으면 **매니페스트**(필요한 JS 번들·에셋 목록)를 받고 에셋을 다운로드
3. 다운로드가 빨리 끝나면 바로 새 업데이트로 실행, **오래 걸리면 다음 실행 때** 적용

그래서 "업데이트 올렸는데 왜 안 바뀌지?"의 흔한 답은 **앱을 한 번 더 껐다 켜야 한다**는 것이다.

## 2. 새 빌드가 필요한 경우

업데이트는 네이티브 레이어를 못 바꾼다. 다음은 반드시 [[EAS Build]]로 새 빌드 → 스토어 심사다.

| 변경 | OTA 가능? |
| ----------- | ----------- |
| 화면·로직·스타일(JS/TS) | O |
| 이미지·폰트 등 에셋 | O |
| 네이티브 라이브러리 설치·업그레이드 (예: `expo-camera`) | **X** |
| Expo SDK 업그레이드 | **X** |
| 권한 추가(Info.plist / AndroidManifest) | **X** |
| 앱 아이콘·스플래시·번들 ID 등 네이티브 설정 | **X** |
| [[홈 화면 위젯]]·[[Live Activity]] (Swift/Kotlin) | **X** |

## 3. runtimeVersion — 호환성의 열쇠

새 JS가 옛 네이티브 위에서 돌면 앱이 죽는다(없는 네이티브 모듈 호출). 이를 막는 게 `runtimeVersion` 이다. 공식 정의: *"빌드의 네이티브 코드와 업데이트 사이의 호환성을 보장하는 속성."*

**빌드의 runtimeVersion과 업데이트의 runtimeVersion이 정확히 일치해야만** 그 업데이트가 내려간다. 플랫폼도 정확히 일치해야 한다.

```ts
// app.config.ts
runtimeVersion: { policy: 'fingerprint' }
// 또는 직접 문자열: runtimeVersion: '1.0.0'
```

| 정책 | runtimeVersion이 바뀌는 시점 | 특징 |
| ----------- | ----------- | ----------- |
| `appVersion` | 앱 `version` 을 올릴 때 | 단순. 대신 네이티브를 바꾸고 버전을 안 올리면 **사고** |
| `nativeVersion` | `version` + iOS `buildNumber` / Android `versionCode` | `"[version]([buildNumber])"` 형식 |
| `fingerprint` | 네이티브에 영향을 줄 수 있는 **무엇이든** 바뀔 때 자동 계산 (`@expo/fingerprint`) | 사람이 판단할 필요 없음. 실수 방지에 가장 강함 |
| 직접 문자열 | 내가 바꿀 때 | 완전한 통제, 완전한 책임 |

> `sdkVersion` 정책도 enum에 있지만 레거시용이라 여기선 생략 (설명 미검증)

**판단 기준**: 팀이 "이 변경이 네이티브를 건드리나?"를 매번 정확히 판단할 자신이 없으면 `fingerprint`. 앱 버전과 업데이트 호환 단위를 일치시키고 싶으면 `appVersion` — [[시맨틱 버저닝(SemVer)]]처럼 버전 번호에 호환성 의미를 싣는 발상이다.

## 4. 채널과 브랜치

| 개념 | 어디에 있나 | 역할 |
| ----------- | ----------- | ----------- |
| **채널(channel)** | 빌드에 박힘 (`eas.json` 프로필의 `channel`) | "이 빌드는 어느 줄에서 업데이트를 받나" |
| **브랜치(branch)** | EAS 서버 | 업데이트들의 순서 있는 목록 |

채널은 아무 브랜치에나 연결할 수 있고, 기본은 **같은 이름의 브랜치에 자동 연결**된다. `production` 채널을 다른 브랜치로 돌리면 **새 빌드 없이** 운영 앱이 받는 업데이트 줄을 바꿀 수 있다 → 롤백·단계적 배포에 쓴다.

```bash
eas update --branch preview --message "펫 상세 화면 버그 수정"
```

## 5. 장단점

### 장점
* JS 수정은 **심사 없이 분 단위로** 배포 — 웹뷰 앱의 최대 장점을 RN도 갖게 된다
* 크래시 나는 업데이트를 채널 전환·재배포로 빠르게 롤백
* runtimeVersion이 호환 안 되는 업데이트를 자동으로 막아 준다

### 단점·함정
* **네이티브 변경은 못 보낸다.** "OTA로 고치면 되지"가 안 통하는 변경이 생각보다 많다(2절 표)
* 다운로드가 늦으면 **다음 실행에 적용** → 긴급 패치가 즉시 반영된다는 보장이 없다
* 무료 플랜 업데이트 대상 **1K MAU** (Starter 3K, Production 50K — expo.dev/pricing, 2026-10-15 확인)
* runtimeVersion을 수동으로 관리하다 네이티브 변경 후 안 올리면, 새 JS가 옛 바이너리로 가서 크래시
* 스토어 정책상 **앱의 주요 목적을 바꾸는 업데이트는 금지**다 → [[OTA 업데이트]] 3절

### 대안
* `expo-updates` 는 공개된 **Expo Updates 프로토콜**을 따르는 서버면 어디든 붙는다. 공식 문서: *"EAS Update는 그런 서비스 중 하나이고, 커스텀 서버와도 쓸 수 있다."* → MAU 과금이 부담되거나 사내망 배포가 필요하면 자체 업데이트 서버 운영
* (과거) Microsoft CodePush — 2025-03-31 App Center와 함께 종료 → [[OTA 업데이트]]

## 6. 펫바디 — 왜 이게 RN 채택의 핵심 근거인가

[[펫바타 앱 - React Native 채택 근거]]에서 "전부 웹뷰로 하자"는 안의 최대 장점은 **배포 속도**였다. 웹은 서버에 올리면 끝이니까. EAS Update가 있으면 RN도 JS 변경에 대해 같은 속도를 낸다 → 배포 속도는 더 이상 웹뷰를 고를 이유가 아니게 된다.

단 펫바타의 차별점인 위젯·Live Activity는 네이티브라 OTA 대상이 아니다. **위젯 수정은 항상 새 빌드**라는 걸 일정에 반영해야 한다.

## 정리
* 앱 = 네이티브 레이어(고정) + 업데이트 레이어(교체 가능). EAS Update는 위층만 바꾼다
* 네이티브 라이브러리·SDK·권한·위젯 변경은 새 빌드
* runtimeVersion이 정확히 일치해야 업데이트가 내려간다. 헷갈리면 `fingerprint`
* 채널(빌드 쪽) ↔ 브랜치(서버 쪽) 연결을 바꿔 롤백
* 적용은 기본적으로 다음 실행 시점일 수 있다
