# 상태 관리
----

애플리케이션이 들고 있는 **변하는 데이터**를 어디에 두고 어떻게 갱신·공유할 것인가의 문제.

프론트엔드 설계에서 가장 자주 틀리는 지점이다. 대부분의 성능 문제와 버그가 "상태를 잘못된 곳에 뒀다"에서 나온다.

## 1. 상태를 종류별로 나눠라 — 가장 중요한 구분

모든 상태를 하나의 전역 스토어에 몰아넣는 게 흔한 실수다. **성격이 다른 상태는 다른 도구로 다뤄야 한다.** 이 축은 [[서버 상태 vs 클라이언트 상태]]에 따로 정리했다.

| 종류 | 정의 | 특징 | 어디에 둘까 |
| ----------- | ----------- | ----------- | ----------- |
| **서버 상태** | 서버가 원본을 가진 데이터 | 비동기, 캐싱·무효화 필요, **내 것이 아님** | [[TanStack Query]], SWR |
| **클라이언트 상태** | 앱이 원본을 가진 데이터 | 동기, 즉시 변경 | useState, [[zustand]], Redux |
| **URL 상태** | 화면을 재현하는 조건 | 공유·북마크 가능해야 함 | [[쿼리스트링(Query String)]] |
| **폼 상태** | 입력 중인 값 | 고빈도 변경, 지역적 | react-hook-form |

### 서버 상태를 전역 스토어에 넣지 말 것
이게 제일 흔한 실수다. 서버 데이터를 Redux에 넣으면 **캐싱·재검증·로딩/에러 처리·중복 요청 제거를 전부 직접 만들게 된다.** 그건 이미 Query 계열 라이브러리가 푼 문제다. 여기서 제일 잡기 어려운 건 경쟁 상태(race condition)인데, 이유는 [[서버 상태 vs 클라이언트 상태]]에 적었다.

> 판별법: **"이 데이터의 원본이 서버에 있는가?"** 그렇다면 서버 상태다.

## 2. 상태를 얼마나 위로 올릴까

판단 기준은 [[전역 상태와 지역 상태]]에 자세히 있다.

* **지역 상태부터 시작한다.** 필요해지기 전에 전역으로 올리지 말 것
* 두 컴포넌트가 공유해야 하면 **공통 조상까지만** 올린다 (lifting state up)
* [[Context API]]는 **자주 안 바뀌는 값**에 쓴다 — 테마, 로그인 사용자, 현재 테넌트
* Context에 자주 바뀌는 값을 넣으면 **구독하는 모든 컴포넌트가 리렌더**된다. 이때 필요한 게 selector를 지원하는 스토어, 즉 [[zustand]]다

## 3. 구독 범위 — 실시간 UI의 핵심

여기가 [[메모이제이션(Memoization)]] 보다 훨씬 큰 성능 차이를 만든다.

초당 여러 건의 이벤트가 들어오는 대시보드에서, 컴포넌트가 **전체 배열을 구독하면** 이벤트 하나에 화면 전체가 리렌더된다.

```
❌ const events = useStore(s => s.events)          // 전부 구독 → 전부 리렌더
✅ const urgent = useStore(s => s.byLevel.urgent)  // 필요한 슬라이스만
```

```
SSE  ──▶  이벤트 스토어
              │
   ┌──────────┼───────────┐
   ▼          ▼           ▼
알람 피드   재원 현황    추이 차트
(등급별     (개체 상태   (1분 집계
 최근 N건)   변화만)      버킷만)
```

차트는 **원본 이벤트가 아니라 집계된 버킷**을 구독해야 한다. 이벤트 1건마다 차트를 다시 그릴 이유가 없다.

> 리렌더가 많다고 느껴지면 메모를 붙이기 전에 **구독 범위를 먼저 좁혀라.** 대부분 여기서 해결된다.

다만 selector를 걸어도 새 객체·새 배열을 반환하면 소용이 없다. 참조 비교로 변경을 감지하는 구조라 그렇고, 이 전제는 [[불변성(Immutability)]]에 정리했다. [[zustand]]에서는 `useShallow` 가 그 완화책이다.

## 4. 서버 상태 + 실시간의 조합

실시간 데이터를 다룰 때 흔한 실수는 **SSE/WebSocket만으로 상태를 만드는 것**이다. 연결이 끊겼다 붙으면 놓친 이벤트만큼 화면이 **조용히 틀어진다.** 에러도 안 나고 값만 안 맞는다.

두 채널로 나눠야 한다.

```
스냅샷 (REST + Query)  ──▶  현재 상태 전체   ← 최초 진입 · 재연결 직후
델타 (SSE)             ──▶  변경분만        ← 연결 유지 중
```

* 도착한 델타는 `setQueryData` 로 캐시에 반영 — 반드시 **id 기준 병합**이어야 중복이 안 생긴다
* 재연결 시 `invalidateQueries` 로 스냅샷 재조회 → 유실 복구

전송 방식 선택은 [[SSE vs WebSocket]], 캐시 쪽 구현은 [[TanStack Query]]에 있다. 서버 응답을 기다리지 않고 먼저 그리는 [[낙관적 업데이트(Optimistic Update)]]까지 섞이면 한 항목에 출처가 셋이 되므로 병합 규칙이 더 중요해진다.

## 5. 도구 선택

| 도구 | 성격 | 언제 |
| ----------- | ----------- | ----------- |
| `useState` / `useReducer` | 지역 | 기본값. 여기서 시작 |
| [[Context API]] | 전역, selector 없음 | 자주 안 바뀌는 값 |
| **[[zustand]]** | 전역, selector 있음, 가벼움 | 대부분의 클라이언트 전역 상태 |
| Redux Toolkit | 전역, 미들웨어·devtools 강력 | 복잡한 상태 전이, 큰 팀 |
| **[[TanStack Query]]** | 서버 상태 전용 | 서버 데이터는 거의 항상 이것 |
| URL | 공유 가능한 상태 | 필터·정렬·탭 → [[쿼리스트링(Query String)]], [[TanStack Router]] |

[[라이브러리]] 조합의 자유가 곧 결정 비용이라, 팀 규약으로 못 박아두는 게 낫다. 펫바디는 Query·Router를 [[TanStack]]에서, 클라이언트 전역은 [[zustand]]로 가져왔다.

## 정리

* **서버 상태와 클라이언트 상태를 섞지 말 것.** 가장 중요한 구분
* 지역에서 시작해 필요할 때만 올린다
* 공유 가능해야 하는 상태는 **URL에**
* 실시간 UI의 성능은 **구독 범위**가 좌우한다. 메모이제이션보다 먼저 볼 것
* 실시간은 **스냅샷 + 델타** 두 채널로. 재연결 복구 경로가 없으면 조용히 틀어진다
