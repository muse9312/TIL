# 서버 상태 vs 클라이언트 상태
----

상태를 **원본(source of truth)이 어디에 있는가**로 나누는 구분. [[상태 관리]]에서 가장 먼저, 가장 정확하게 해야 하는 분류다.

> 판별법은 한 문장이다. **"이 데이터의 원본이 서버에 있는가?"**
> 그렇다면 서버 상태다. 내 앱이 들고 있는 건 원본이 아니라 **사본(캐시)** 이다.

## 1. 왜 이 구분이 중요한가

둘은 같은 "변수"처럼 보이지만 **성질이 정반대**다.

| | 클라이언트 상태 | 서버 상태 |
| ----------- | ----------- | ----------- |
| 원본 위치 | 내 앱 메모리 | 원격 서버 |
| 소유권 | **내가 소유** | **내 것이 아님** (남도 바꾼다) |
| 갱신 | 동기, 즉시 | 비동기, 실패할 수 있음 |
| 신선도 | 항상 최신 | **언제든 낡을 수 있음** |
| 필요한 것 | setter 하나 | 캐싱 · 재검증 · 로딩/에러 · 중복요청 제거 · 재시도 |
| 대표 예 | 모달 열림, 선택된 행, 사이드바 접힘 | 매장 목록, 알림 이력, 사용자 프로필 |

핵심은 **소유권**이다. 클라이언트 상태는 내가 바꾸지 않으면 안 바뀐다. 서버 상태는 **내가 아무것도 안 해도 낡는다.** 옆자리 운영자가 알림을 처리하면, 내 화면의 값은 그 순간부터 틀린 값이다.

그래서 서버 상태는 "값"이 아니라 **"값 + 그 값이 얼마나 믿을 만한가"** 라는 두 개의 정보를 늘 같이 들고 다녀야 한다. 이게 클라이언트 상태 도구로는 표현이 안 되는 부분이다.

## 2. 서버 상태를 전역 스토어에 넣으면 생기는 일

가장 흔한 실수. Redux나 [[zustand]]에 `stores: []` 를 넣고 `useEffect` 로 fetch 하는 코드다.

```ts
// ❌ 서버 데이터를 클라이언트 스토어에 넣은 모습
const useStore = create((set) => ({
  alerts: [],
  loading: false,
  error: null,
  fetchAlerts: async (storeId) => {
    set({ loading: true });
    try   { set({ alerts: await api.getAlerts(storeId), loading: false }); }
    catch (e) { set({ error: e, loading: false }); }
  },
}));
```

동작은 한다. 문제는 여기서 **직접 만들게 되는 것들**이다.

* **캐싱** — 같은 매장을 다시 열면 또 요청할 것인가, 있던 걸 쓸 것인가
* **재검증** — 탭에 돌아왔을 때 · 네트워크가 복구됐을 때 다시 받아올 것인가
* **중복 요청 제거** — 세 위젯이 같은 데이터를 동시에 요구하면 요청이 3번 나간다
* **로딩/에러 상태** — 쿼리마다 `loading` · `error` 플래그를 손으로 하나씩
* **경쟁 상태(race condition)** — 매장을 빠르게 전환하면 **늦게 도착한 이전 응답이 최신 데이터를 덮어쓴다**
* **재시도 · 백오프**, 페이지네이션 커서, 언마운트 시 정리, 가비지 컬렉션

전부 **이미 풀린 문제**다. [[TanStack Query]] 같은 서버 상태 라이브러리가 하는 일이 정확히 이 목록이다. 직접 만들면 잘 만들어야 절반쯤 되고, 나머지 절반은 버그로 남는다.

특히 경쟁 상태는 악질이다. 에러가 안 나고 **화면에 틀린 값이 조용히 남는다.**

## 3. 반대 방향의 함정 — 전부 Query에 넣기

구분을 배운 다음에 오는 두 번째 실수는 **모든 걸 서버 상태 도구로 다루는 것**이다.

* 모달 열림 여부를 `useQuery` 로 관리 → 캐시 키를 만들 이유가 없다
* 선택된 행 목록을 `queryClient.setQueryData` 로 → 서버에 원본이 없는데 캐시를 쓴다
* 폼 입력값을 Query에 → 고빈도 변경이라 `react-hook-form` 이 맞다

원본이 서버에 없으면 서버 상태가 아니다. `useState` 로 충분한 걸 캐시에 넣으면 **불필요한 간접층**만 생긴다.

## 4. 경계가 애매한 것들

실무에서 헷갈리는 건 대개 이 셋이다.

| 상태 | 어디에 | 이유 |
| ----------- | ----------- | ----------- |
| 필터 · 정렬 · 페이지 | **URL** | 서버 상태도 클라이언트 상태도 아니다. 화면을 재현하는 조건이라 공유·북마크가 돼야 한다 → [[쿼리스트링(Query String)]] |
| 폼 입력값 | 지역(폼 라이브러리) | 제출 전까지는 서버와 무관. 제출하는 순간 서버 상태로 넘어간다 |
| 실시간 이벤트 버퍼 | 클라이언트 스토어 | 원본은 서버지만 **연결이 살아있는 동안만 유효한 델타**라 성격이 다르다 |

### 실시간 델타는 어느 쪽인가
펫바디 관제 대시보드에서 SSE로 들어오는 이벤트는 원본이 서버에 있으니 서버 상태처럼 보인다. 하지만 **재조회로 다시 얻을 수 없는 "그 순간의 변경분"** 이라 캐시 모델과 잘 안 맞는다.

그래서 두 채널로 나눈다.

```
스냅샷 (REST + Query)  ──▶  서버 상태     ← 최초 진입 · 재연결 직후
델타   (SSE → zustand) ──▶  이벤트 버퍼   ← 연결 유지 중
```

델타만 믿으면 **연결이 끊겼다 붙는 동안 놓친 이벤트만큼 화면이 조용히 틀어진다.** 에러도 안 나고 값만 안 맞는다. 이 설계는 [[SSE vs WebSocket]]과 [[TanStack Query]]에 자세히 적었다.

## 5. 도구 매핑

| 종류 | 도구 |
| ----------- | ----------- |
| 서버 상태 | [[TanStack Query]], SWR |
| 클라이언트 전역 상태 | [[zustand]], Redux Toolkit, [[Context API]] |
| 클라이언트 지역 상태 | `useState` / `useReducer` → [[전역 상태와 지역 상태]] |
| URL 상태 | [[TanStack Router]]의 search params → [[쿼리스트링(Query String)]] |
| 폼 상태 | react-hook-form + zod |

도구가 다섯 개라 복잡해 보이지만, 반대로 **하나로 다 하려다 직접 만든 코드**보다 훨씬 적다.

## 정리

* 판별 기준은 하나 — **원본이 서버에 있는가**
* 서버 상태는 **내 것이 아니라서 언제든 낡는다.** 그래서 값이 아니라 "값 + 신선도"를 다뤄야 한다
* 서버 상태를 전역 스토어에 넣으면 **캐싱·재검증·중복요청 제거·경쟁 상태 처리를 직접 만들게 된다**
* 반대로 원본이 서버에 없는 걸 Query에 넣지 말 것
* 애매한 건 대개 **URL 상태**다. 공유돼야 하면 URL로
