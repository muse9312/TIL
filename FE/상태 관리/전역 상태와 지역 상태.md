# 전역 상태와 지역 상태
----

같은 상태를 **컴포넌트 트리의 어느 높이에 둘 것인가**의 문제. [[서버 상태 vs 클라이언트 상태]]가 "무엇으로 다룰까"라면, 이건 **"어디에 둘까"** 다.

기본 원칙은 하나다. **필요한 만큼만 올린다.**

## 1. 지역 상태부터 시작한다

```jsx
function AlertRow({ alert }) {
  const [expanded, setExpanded] = useState(false);   // 이 행만 아는 상태
  ...
}
```

`expanded` 는 이 행 말고 아무도 알 필요가 없다. 지역 상태의 장점은 **범위가 곧 문서**라는 점이다.

* 이 상태를 누가 바꾸는지 파일 하나만 보면 안다
* 컴포넌트가 언마운트되면 **같이 사라진다.** 정리할 게 없다
* 상태 변경의 리렌더 범위가 그 서브트리로 **자동으로 갇힌다**

## 2. 올리는 순간 — lifting state up

두 컴포넌트가 같은 값을 봐야 하는 순간이 오면, 상태를 **공통 조상까지** 올린다.

```
      ❌ 각자 들고 있음              ✅ 공통 조상으로 올림

        Dashboard                      Dashboard
        ├ FilterBar  [range]           ├ FilterBar   ─┐ [range]
        └ Chart      [range]           └ Chart       ─┘
          (두 값이 어긋난다)              (한 값을 공유)
```

여기서 중요한 건 **"공통 조상까지만"** 이다. 두 형제가 공유하는 값을 앱 루트나 전역 스토어에 올릴 이유는 없다.

### 올리는 비용
* **prop drilling** — 중간 컴포넌트들이 자기가 안 쓰는 props를 통과시킨다
* **리렌더 범위 확대** — 상태를 위로 올린 만큼 리렌더되는 서브트리가 커진다
* 중간 컴포넌트가 그 값에 **결합**된다. 재사용성이 떨어진다

## 3. 언제 전역으로 갈까

전역화의 진짜 명분은 "여러 곳에서 쓴다"가 아니라 **"트리 구조상 공통 조상이 너무 멀다"** 이다.

전역이 정당한 경우
* 로그인 사용자 · 현재 테넌트 · 테마 — **앱 어디서나** 필요하고 조상이 루트다
* 토스트 큐 · 전역 모달 — 호출하는 쪽과 그리는 쪽의 위치가 무관하다
* 실시간 이벤트 버퍼 — **트리 밖(SSE 연결)에서 쓰기가 들어온다**

마지막 항목이 펫바디에서 [[zustand]]를 쓴 이유다. SSE 구독은 컴포넌트가 아니라 연결 계층에 있고, 거기서 스토어에 직접 쓴다. 이건 lifting up으로 표현할 수 없다.

### prop drilling 2단계는 문제가 아니다
prop drilling이 나오자마자 전역으로 도망가는 게 가장 흔한 성급한 전역화다. 2~3단계 통과는 **명시적이라 오히려 읽기 쉽다.** 5단계 이상, 혹은 중간 컴포넌트가 그 값과 논리적으로 아무 상관이 없을 때 비로소 냄새가 된다.

컴포넌트 합성(children으로 넘기기)으로 먼저 풀 수 있는지도 봐야 한다.

```jsx
// drilling 대신 합성으로 — Layout이 user를 몰라도 된다
<Layout sidebar={<UserBadge user={user} />} />
```

## 4. 성급한 전역화가 왜 문제인가

"나중에 필요할 것 같아서" 전역에 올려두는 건 되돌리기 어려운 결정이다.

### 단점
* **생명주기가 사라진다.** 지역 상태는 언마운트되면 리셋된다. 전역 상태는 **화면을 떠나도 남아** 다음 진입 때 이전 매장의 필터가 그대로 보인다. 직접 `reset()` 을 호출해야 하고, 이걸 빠뜨리는 게 전역 상태 버그의 대부분
* **누가 바꾸는지 추적이 어렵다.** 앱 어디서나 쓸 수 있다는 건 앱 어디서나 망칠 수 있다는 뜻
* **동시 인스턴스가 불가능해진다.** 모달을 두 개 띄우거나 탭을 분할하는 순간 전역 단일 값이 무너진다
* **테스트가 무거워진다.** 컴포넌트 하나를 렌더하려고 스토어를 세팅해야 한다
* 리렌더 범위가 넓어진다 — selector 없는 [[Context API]]라면 특히

> 지역 → 전역은 언제든 쉽다. **전역 → 지역은 어렵다.** 그래서 기본값은 지역이다.

## 5. 판단 순서

```
1. useState 로 둔다
2. 형제가 공유해야 하면 → 공통 조상으로 올린다 (lifting state up)
3. 통과 단계가 깊어지면 → 합성(children)으로 풀 수 있는지 본다
4. 그래도 안 되면
   ├ 원본이 서버에 있다        → TanStack Query (전역화 아님, 캐시다)
   ├ 공유·북마크돼야 한다      → URL 쿼리스트링
   ├ 거의 안 바뀐다            → Context API
   └ 자주 바뀌거나 트리 밖에서 쓴다 → zustand
```

3단계 전에 4단계로 건너뛰지 않는 게 핵심이다. 특히 **서버 데이터를 "여러 곳에서 쓴다"는 이유로 전역화하는 것**은 전역 상태 문제가 아니라 캐시 문제다 → [[서버 상태 vs 클라이언트 상태]].

## 정리

* 기본값은 **지역**. 필요해진 뒤에 올린다
* 올릴 때는 **공통 조상까지만**
* prop drilling 2~3단계는 냄새가 아니다. 합성으로 먼저 풀어볼 것
* 전역화의 명분은 "여러 곳에서 쓴다"가 아니라 **"공통 조상이 없다" 또는 "트리 밖에서 쓴다"**
* 전역 상태의 가장 큰 비용은 **생명주기가 사라지는 것.** 언마운트 시 리셋을 잊지 말 것
