# Git 훅(Git Hooks)
----

git 이 특정 동작을 하기 전후에 **자동으로 실행하는 스크립트**. 실패하면(0이 아닌 종료 코드) 그 동작을 중단시킨다.

문서로 적힌 규칙과 실제로 지켜지는 규칙 사이의 간격을 메우는 장치다. **읽어야 지켜지는 규칙은 안 지켜지고, 어기면 막히는 규칙은 지켜진다.**

> 기준: git-scm 공식 문서 `githooks(5)` (2026-09-01 확인)
> 출처: https://git-scm.com/docs/githooks

## 1. 동작 방식

```
$GIT_DIR/hooks/           ← 기본 위치 (보통 .git/hooks/)
├── pre-commit            ← 파일 이름이 곧 훅 이름
├── commit-msg
└── pre-push
```

규칙이 세 줄이다.

* **파일 이름이 훅 이름이다.** 확장자 없이 정해진 이름을 그대로 쓴다
* **실행 권한 비트가 없으면 무시된다.** 조용히 넘어가므로 "왜 안 돌지"의 1순위 원인
* **위치는 `core.hooksPath` 설정으로 바꿀 수 있다.** husky 같은 도구가 `.husky/` 를 쓰는 근거가 이것이다

훅이 실행되기 전에 git 은 **작업 트리 루트로 디렉터리를 옮긴다**(bare 저장소면 `$GIT_DIR`). 그래서 훅 스크립트 안의 상대 경로는 항상 저장소 루트 기준이다. 단 push 관련 훅(`pre-receive`, `update`, `post-receive`, `post-update`, `push-to-checkout`)은 예외로 항상 `$GIT_DIR` 에서 돈다.

## 2. 주로 쓰는 훅

`githooks(5)` 에 19개가 문서화돼 있다. 커밋 검증에 실제로 쓰이는 건 셋이다.

| 훅 | 시점 | 받는 인자 | 쓰임 |
| ----------- | ----------- | ----------- | ----------- |
| `pre-commit` | 커밋 메시지를 입력받기 **전** | 없음 | 린트·포맷·타입 검사 |
| `commit-msg` | 메시지 입력 **후**, 커밋 생성 전 | **메시지 파일 경로** (`$1`) | 메시지 형식 검사 |
| `pre-push` | 푸시 직전 | remote 이름·URL | 테스트·빌드 |

`commit-msg` 의 인자가 "메시지 문자열"이 아니라 **"메시지가 든 파일의 경로"** 라는 게 중요하다. 그래서 이 훅은 검사만 하는 게 아니라 **메시지를 제자리에서 고칠 수도 있다.** 공식 문서도 "프로젝트 표준 형식으로 정규화하는 데 쓸 수 있다"고 명시한다. commitlint 가 `commitlint --edit $1` 로 호출되는 이유이기도 하다.

시점 배치에도 이유가 있다. `pre-commit` 이 메시지 입력 **전**이라 여기서 막으면 사용자가 메시지를 쓰는 헛수고를 안 한다. 반대로 형식 검사는 메시지가 있어야 가능하니 `commit-msg` 로 간다.

### 훅은 커밋에서만 도는 게 아니다

`git merge` 도 기본적으로 `pre-merge-commit` 과 `commit-msg` 훅을 실행한다. 머지 커밋 메시지가 커밋 규약에 걸려 머지가 막히는 상황이 여기서 나온다.

## 3. 가장 큰 한계 두 개

### ① `--no-verify` 로 그냥 넘길 수 있다

```bash
git commit -m "..." --no-verify    # pre-commit 과 commit-msg 를 우회
git commit -m "..." -n             # 같은 것
git push --no-verify               # pre-push 우회
```

공식 문서의 `-n / --no-verify` 설명 그대로다 — **"pre-commit 과 commit-msg 훅을 우회한다."** 훅은 게이트가 아니라 **안전벨트**다. 매고 다니면 사고를 줄이지만 풀 수 있고, 급할 때 사람은 푼다.

여기서 나오는 결론이 중요하다. **훅은 실수를 막는 장치지 악의나 급함을 막는 장치가 아니다.** 정말 막아야 하는 것(보호된 브랜치에 규약 위반 커밋이 들어오는 것)은 **서버 측**에서 막아야 한다 — [[지속적 통합(CI)|CI]] 검사, 브랜치 보호, MR 게이트. 훅은 그 검사에 걸리기 **전에** 알려주는 조기 경보로 쓸 때 값어치가 가장 크다.

### ② `.git/hooks` 는 clone 으로 전파되지 않는다

`.git/` 디렉터리는 버전 관리 대상이 아니다. 훅을 아무리 잘 짜도 **저장소를 클론한 다른 사람에게는 아무것도 전달되지 않는다.**

이게 훅 도구가 존재하는 이유의 전부다. 해결 방향은 둘이다.

| 방식 | 방법 | 문제 |
| ----------- | ----------- | ----------- |
| 훅을 버전 관리 폴더에 두고 `core.hooksPath` 를 그쪽으로 | `.husky/` | 설정을 **각자 한 번은 실행**해야 한다 |
| 설치 스크립트로 자동화 | npm `prepare` 스크립트 | `npm install` 을 해야 걸린다 |

husky 는 둘을 합친다 → [[커밋 컨벤션 강제 도구(husky · lint-staged · commitlint)]]

### 장점
* **문서가 못 하는 일을 한다.** 규칙 위반이 발견되는 시점이 리뷰가 아니라 커밋 순간으로 당겨진다
* **피드백 루프가 가장 짧다.** CI 에서 10분 뒤에 아는 것과 커밋할 때 즉시 아는 것의 차이는 크다
* **사람의 주의력을 아낀다.** 리뷰어가 포맷·커밋 메시지 형식을 지적할 필요가 없어지고, 리뷰가 설계 이야기로 간다
* 규칙이 **기계적으로 검사 가능하다는 걸 강제로 확인**하게 만든다. 훅으로 못 짜는 규칙은 사실 애매한 규칙이다

### 단점
* **우회 가능하다.** 위의 ①
* **커밋이 느려진다.** 훅이 2~3초를 넘어가면 사람은 커밋을 뭉치기 시작한다. **"작게 자주 커밋"과 정면으로 충돌**하는 게 훅의 가장 과소평가된 비용이다
* **팀원 환경 문제가 생긴다.** GUI 클라이언트(SourceTree, VS Code, JetBrains)는 터미널과 다른 `PATH` 로 뜨기 때문에 nvm·fnm·volta 로 설치한 node 를 못 찾아 `command not found` 가 난다. 훅이 도입 며칠 만에 미움받는 가장 흔한 경로가 이것이다
* **CI·Docker 에서도 설치되려 한다.** 훅이 필요 없는 환경에서 설치 스크립트가 실패하는 문제
* **훅이 파일을 고치면 상태가 꼬인다.** 포매터가 파일을 수정했는데 스테이징에 반영이 안 되면 커밋된 내용과 디스크 내용이 달라진다. lint-staged 가 푸는 문제가 정확히 이거다

## 정리

* 훅은 **`$GIT_DIR/hooks` 의 실행 가능한 스크립트.** 0이 아닌 종료 코드로 동작을 중단시킨다
* 위치는 **`core.hooksPath`** 로 바꿀 수 있고, 이게 훅 관리 도구의 작동 원리다
* 커밋 검증에는 셋 — **`pre-commit`(메시지 전, 코드 검사) · `commit-msg`(메시지 파일 경로를 받음) · `pre-push`**
* `commit-msg` 는 검사뿐 아니라 **메시지를 제자리에서 고칠 수도** 있다
* **`--no-verify` 로 우회된다.** 훅은 게이트가 아니라 안전벨트고, 진짜 게이트는 **서버 측**(CI · 브랜치 보호)에 있어야 한다
* **`.git/hooks` 는 clone 으로 전파되지 않는다.** 훅 도구가 존재하는 이유
* 실무에서 훅을 죽이는 건 우회가 아니라 **속도와 환경 문제**다
