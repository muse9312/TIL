# Conventional Commits
----

커밋 메시지 첫 줄에 **변경의 성격을 기계가 읽을 수 있는 형태로** 못 박는 규약.

핵심 주장은 [[Feature-Sliced Design(FSD)]]과 같다. **관습을 검사 가능한 규칙으로 만든다.** 사람이 읽으라고 쓰던 커밋 메시지를 도구도 읽을 수 있게 바꾸면, 체인지로그 생성·버전 결정·릴리스 트리거가 전부 커밋 로그에서 자동으로 나온다.

> 기준: **Conventional Commits v1.0.0** (2026-09-01 확인)
> 출처: https://www.conventionalcommits.org/en/v1.0.0/

## 1. 메시지 구조

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

스펙은 RFC 2119 키워드(MUST/SHOULD/MAY)로 쓰인 **16개 조항**이다. 실제로 외워야 하는 건 몇 개 안 된다.

| 조항 | 내용 |
| ----------- | ----------- |
| 1 | 커밋은 **type** 으로 시작한다. 뒤에 선택적 scope, 선택적 `!`, 그리고 **필수인 콜론과 공백**(`: `)이 온다 |
| 2 · 3 | `feat` 은 기능 추가, `fix` 는 버그 수정에 **MUST** 쓴다 |
| 4 | scope 는 **명사**여야 하고 **괄호**로 감싼다 — `fix(parser):` |
| 5 · 6 | description 은 콜론+공백 **바로 뒤**에 온다. 변경의 짧은 요약 |
| 7 · 8 | body 는 description **한 줄 띄고** 시작한다. 자유 형식, 문단 여러 개 가능 |
| 9 | footer 는 body 한 줄 띄고 온다. `토큰 + (`: ` 또는 ` #`) + 값` |
| 10 | **footer 토큰은 공백 대신 `-` 를 쓴다** — `Acked-by`. `BREAKING CHANGE` 만 예외 |
| 11 | footer 값은 공백·줄바꿈을 포함할 수 있고, **다음 유효한 토큰/구분자 쌍이 나오면** 파싱이 끝난다 |
| 12~14 | 파괴적 변경 표기 → 3절 |
| 15 | 구성 요소는 **대소문자를 구분하지 않는다.** 단 `BREAKING CHANGE` 는 **반드시 대문자** |
| 16 | `BREAKING-CHANGE` 는 footer 토큰으로서 `BREAKING CHANGE` 와 **동의어다** |

10번이 왜 있는지가 재밌다. `Refs: #42` 같은 줄과 그냥 본문 문단을 구별할 방법이 필요한데, **"공백 없는 한 단어 + 구분자"** 라는 모양이 그 역할을 한다. 그래서 토큰에 공백을 못 쓰고, git 의 trailer 관습을 그대로 빌려왔다.

```
feat(api)!: 응답 페이로드에서 legacy 필드 제거

기존 v1 클라이언트가 참조하던 필드를 정리했다.
서버 응답 크기가 약 30% 줄었다.

BREAKING CHANGE: legacy 필드를 읽던 클라이언트는 전부 수정해야 한다.
Refs: #42
Reviewed-by: wjy
```

## 2. type — 스펙이 정하는 건 둘뿐이다

**가장 많이 오해하는 지점.** 스펙이 강제하는 type 은 `feat` 과 `fix` **두 개뿐**이고, 조항 14는 "그 외의 type 도 **MAY** 쓸 수 있다"고만 한다. 흔히 보는 아홉 개짜리 목록은 스펙이 아니라 Angular 관습과 그걸 코드로 옮긴 `@commitlint/config-conventional` 의 기본값이다 → [[커밋 컨벤션 강제 도구(husky · lint-staged · commitlint)]]

| type | 용도 | 출처 |
| ----------- | ----------- | ----------- |
| `feat` | 기능 추가 | **스펙** (MINOR) |
| `fix` | 버그 수정 | **스펙** (PATCH) |
| `docs` | 문서만 | 관습 |
| `style` | 포맷·공백. 로직 무관 | 관습 |
| `refactor` | 동작 변화 없는 구조 개선 | 관습 |
| `perf` | 성능 개선 | 관습 |
| `test` | 테스트 | 관습 |
| `build` | 빌드 시스템·의존성 | 관습 |
| `ci` | CI 설정 | 관습 |
| `chore` | 그 외 잡무 | 관습 |
| `revert` | 되돌리기 | 관습 (스펙 FAQ 권장) |

되돌리기는 스펙이 명시적으로 정의하지 않는다. FAQ 는 `revert` type 과 되돌린 커밋 SHA 를 담은 footer 를 **권장할 뿐**이다.

```
revert: let us never again speak of the noodle incident

Refs: 676104e, a215868
```

대소문자도 마찬가지다. 조항 15에 따라 `Feat:` 과 `feat:` 은 스펙상 같고, FAQ 는 **"아무 케이싱이나 써도 되지만 일관성이 최선"** 이라고만 한다. 소문자 강제는 도구의 선택이지 스펙의 요구가 아니다.

## 3. 파괴적 변경 — 두 가지 표기법

조항 12~14가 정하는 건 두 방식이고, **둘 다 유효하다.**

| 방식 | 형태 | 스펙 |
| ----------- | ----------- | ----------- |
| ① prefix | `!` 를 콜론 **바로 앞**에 | `feat(api)!: ...` |
| ② footer | 대문자 `BREAKING CHANGE:` + 공백 + 설명 | `BREAKING CHANGE: ...` |

`!` 를 쓰면 footer 의 `BREAKING CHANGE:` 는 **생략해도 되고**, 그때는 **description 이 파괴적 변경의 설명 역할을 한다**(조항 13). 둘 다 쓰는 것도 물론 가능하고, 실무에서는 그게 낫다 — `!` 는 `git log --oneline` 에서 눈에 띄고, footer 는 무엇이 왜 깨졌는지 설명할 자리를 준다.

주의할 점 하나. `BREAKING CHANGE` 는 **유일하게 대소문자를 가리는 요소**다(조항 15). `Breaking change:` 는 그냥 body 의 한 줄로 취급된다. 대신 조항 16이 하이픈 형태 `BREAKING-CHANGE:` 를 동의어로 인정하는데, 이건 10번(토큰에 공백 금지)과의 모순을 메우는 조항이다.

## 4. SemVer 와의 연결

스펙 FAQ 가 직접 정의하는 대응이다.

| 커밋 | 버전 증가 |
| ----------- | ----------- |
| `fix` | **PATCH** |
| `feat` | **MINOR** |
| 파괴적 변경 (type 무관) | **MAJOR** |

"type 무관"이 중요하다. `docs!:` 든 `chore!:` 든 `!` 가 붙으면 MAJOR 다. 이 세 줄이 [[시맨틱 버저닝(SemVer)]]의 버전 결정을 **사람의 판단에서 커밋 로그의 함수로** 바꾼다. semantic-release 같은 도구가 하는 일이 정확히 이 표를 실행하는 것이다.

거꾸로 말하면 **이 연결이 Conventional Commits 의 이득 대부분을 떠받친다.** 버전을 자동으로 올릴 필요가 없는 프로젝트에서는 이득의 절반이 사라진다 → 6절

### 장점

* **체인지로그가 공짜로 나온다.** `feat` 만 모으면 "새 기능", `fix` 만 모으면 "버그 수정"이다
* **버전 결정이 자동화된다.** 릴리스 담당자의 판단이 필요 없어진다
* **`git log --grep` 이 검색 도구가 된다.** type·scope·footer 로 이력을 잘라볼 수 있다
* **커밋을 쪼개게 만든다.** type 이 두 개 걸치면 커밋이 두 개여야 한다는 신호다. 스펙 FAQ 도 "가능하면 되돌아가서 커밋을 나누라"고 답한다. 부수 효과가 아니라 **가장 큰 실질 이득**에 가깝다
* **리뷰어가 diff 를 열기 전에 기대치를 세운다.** `refactor` 라면 동작이 같아야 하고, 그 전제로 diff 를 읽는다

### 단점 · 한계

* **학습 비용이 있고, 그 비용을 새 사람이 낸다.** 규칙 자체는 5분이면 읽지만 몸에 붙기까지는 몇 주다. 그동안 커밋할 때마다 마찰이 생긴다
* **type 선택이 애매한 경우가 계속 나온다.** 리팩터링하다 버그를 고쳤으면 `refactor` 인가 `fix` 인가. 테스트를 고치려고 소스를 건드렸으면 `test` 인가. 스펙에는 답이 없고, "커밋을 나눠라"는 답은 나눌 수 없는 변경 앞에서 무력하다. 실무에서는 **팀이 자체 판별 기준을 문서로 정해두는 것 외에 방법이 없다**
* **`chore` 가 쓰레기통이 된다.** 애매하면 전부 `chore` 로 가고, 그러면 분류가 정보를 잃는다
* **강제 도구가 없으면 무너진다.** 이건 FSD 와 완전히 같은 구조의 문제다. 규칙을 지킨 커밋과 안 지킨 커밋이 섞이면 `git log --grep` 도, 체인지로그 생성도 신뢰할 수 없게 되고, **신뢰할 수 없는 순간 규칙을 지킬 이유도 사라진다.** 커밋 메시지는 파일과 달리 나중에 일괄로 못 고친다(이미 푸시했다면 사실상 불가능)는 점이 코드 린트보다 더 나쁘다 → [[Git 훅(Git Hooks)]]
* **스쿼시 워크플로에서는 개별 커밋 규칙이 의미가 옅어진다.** 스펙 FAQ 도 "스쿼시 기반 워크플로라면 모든 기여자가 규약을 따를 필요는 없다"고 인정한다. 최종 커밋 메시지만 규약을 따르면 된다는 뜻인데, 그러면 작업 중 커밋을 검사하는 훅의 값어치가 떨어진다 → [[Git 머지 전략(merge · squash · rebase)]]

## 5. SemVer 가 의미 없는 곳에서는 어떻게 쓰나

사내 앱·B2B 대시보드·백오피스처럼 **배포되는 패키지가 아닌** 프로젝트에서는 4절의 표가 통째로 무의미하다. 버전을 올릴 일이 없으니 `feat` 과 `fix` 를 구분해도 아무 도구가 반응하지 않는다.

그렇다고 규약 전체가 쓸모없어지는 건 아니다. 남는 이득이 셋 있다.

1. **커밋을 쪼개게 만드는 압력** — 버전과 무관하게 유효하다
2. **`git log` 검색성** — type·scope 로 이력을 잘라보는 건 여전히 된다
3. **`!` 라는 남는 슬롯** — 원래 용도가 비었으니 **팀에 실제로 중요한 다른 신호로 전용할 수 있다**

3번이 핵심이다. `!` 는 "이 커밋은 다른 곳을 함께 고쳐야 한다"는 뜻의 강조 표시고, "다른 곳"이 반드시 SemVer 소비자여야 할 이유는 없다. 다만 **스펙의 원래 의미와 다르게 쓰는 것이므로 팀 합의와 문서가 전제**다. 그러지 않으면 나중에 들어온 사람이 스펙대로 해석한다.

## 6. 펫바디 클라이언트에서의 검토 (초안 · 미확정)

`petbody-client` 의 `CONTRIBUTING.md` 는 **아직 초안이고 팀 논의 전이다.** 확정된 규칙이 아니라 검토 중인 판단 두 개를 기록해둔다.

### ① scope 를 FSD 레이어로 쓴다

scope 어휘를 `app` · `pages` · `widgets` · `features` · `entities` · `shared` 여섯 개(+ `deps` · `config`)로 고정하는 안이다.

```
feat(widgets): 알람 피드에 등급 필터 추가
fix(entities): 오탐 신고 시 handledAt 누락 수정
refactor(shared): fetch 래퍼를 shared/api 로 이동
```

`feat(widgets/alert-feed)` 처럼 **슬라이스까지 넣지 않는 이유는 유지비용**이다. 슬라이스가 늘 때마다 commitlint 의 `scope-enum` 목록을 고쳐야 하고, 그 마찰이 쌓이면 규칙 자체를 끄게 된다. 레이어는 [[Feature-Sliced Design(FSD)]] 스펙이 고정한 여섯 개라 **더 늘어나지 않는다**는 게 결정적이다. 슬라이스는 description 에 쓴다.

부수 효과가 하나 더 있는데, 이게 오히려 더 값어치 있어 보인다. **레이어 위반이 커밋 로그에서도 드러난다.** `feat(shared)` 커밋이 `entities/` 를 건드렸다면 [[단방향 의존성]]의 방향이 뒤집힌 것이다. 린터가 잡는 것과 별개로, 리뷰어가 diff 를 열기 전에 냄새를 맡을 수 있다.

### ② `!` 를 API 계약 파괴 신호로 전용한다

5절의 3번을 그대로 적용한 안이다. 사내 B2B 관제 대시보드라 SemVer 가 의미 없는 대신, **`entities/` 의 zod 스키마가 백엔드와의 API 계약**이라는 점에 주목했다.

```
feat(entities)!: Alert 스키마에 zoneId 를 필수로 변경

BREAKING CHANGE: 백엔드 SSE payload 에 zoneId 가 없으면 파싱이 실패한다.
서버 측 이벤트 발행부 수정이 함께 필요하다.
```

client / server / ai 세 레포가 나뉘어 있어서 "이 커밋 때문에 저쪽도 고쳐야 한다"가 코드로는 드러나지 않는데, `!` 가 그 자리를 메운다. 나중에 이렇게 뽑을 수 있다.

```bash
git log --grep='BREAKING CHANGE'   # 백엔드 협의가 필요했던 지점만
```

**미결로 남은 쟁점**은 그대로다 — 커밋 description 을 한국어로 쓸지, scope 를 슬라이스까지 내릴지, `!` 를 스펙과 다르게 쓰는 것에 팀이 동의할지, 그리고 강제 도구를 붙일지. 특히 마지막 항목이 나머지 전부를 좌우한다.

## 정리

* 구조는 `<type>[(scope)][!]: <description>` + body + footer. **콜론 뒤 공백 하나는 필수**
* 스펙이 강제하는 type 은 **`feat` 과 `fix` 둘뿐.** 나머지 아홉 개는 Angular 관습이지 스펙이 아니다
* footer 토큰은 **공백 대신 하이픈.** `BREAKING CHANGE` 만 예외이고, **유일하게 대문자를 강제**받는다
* 파괴적 변경은 `!` 또는 `BREAKING CHANGE:` footer. `!` 를 쓰면 footer 생략 가능하고 description 이 설명을 맡는다
* [[시맨틱 버저닝(SemVer)]] 연결은 **fix→PATCH, feat→MINOR, 파괴적 변경→MAJOR (type 무관)**
* 진짜 이득은 자동화보다 **커밋을 쪼개게 만드는 압력**이다. 이건 버전이 없는 프로젝트에서도 남는다
* 한계는 **type 판별이 애매하다는 것**과 **강제 도구 없으면 무너진다는 것.** 커밋 메시지는 나중에 일괄 수정이 안 돼서 코드 린트보다 회복이 어렵다
* SemVer 가 무의미한 사내 앱에서는 **`!` 를 다른 신호로 전용**할 수 있다. 단 스펙 이탈이므로 문서화가 전제다
