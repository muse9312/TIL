# Git 머지 전략(merge · squash · rebase)
----

브랜치의 작업을 `main` 에 합칠 때 **히스토리를 어떤 모양으로 남길 것인지**의 선택.

같은 코드가 들어오는데 결과 히스토리가 셋 다 다르다. 그래서 이건 기능의 문제가 아니라 **"나중에 이 로그를 누가 무엇을 위해 읽는가"** 의 문제고, 팀의 답이 갈리는 지점이다.

> 출처: git-scm 공식 문서 (2026-09-01 확인)
> https://git-scm.com/docs/git-merge · https://git-scm.com/docs/git-rebase · https://git-scm.com/docs/git-revert

## 1. 세 가지가 남기는 모양

브랜치에 커밋 셋(`a` `b` `c`)이 있고 그 사이 `main` 이 앞으로 나갔다고 하자.

```
merge (--no-ff)              squash                    rebase
                                                       
main ──●──●──────●           main ──●──●──●'           main ──●──●──a'─b'─c'
        ╲       ╱                          ↑                            
         a──b──c                    a+b+c 를 합친 새 커밋 하나        원래 커밋이 재작성됨
                                                                     (SHA 가 전부 바뀜)
    커밋 4개(a,b,c,머지)         커밋 1개               커밋 3개, 선형
```

| | 남는 커밋 | 머지 커밋 | 원래 SHA | 히스토리 |
| ----------- | ----------- | ----------- | ----------- | ----------- |
| **merge** | 브랜치 커밋 전부 + 머지 커밋 | **있음** (부모 2개) | 보존 | 그래프 |
| **squash** | 새 커밋 **1개** | 없음 | **사라짐** | 선형 |
| **rebase** | 브랜치 커밋 전부 | 없음 | **바뀜** (내용은 같음) | 선형 |

세 줄만 알면 나머지는 파생이다. **merge 는 사실을 남기고, squash 는 요약하고, rebase 는 사실을 다시 쓴다.**

## 2. merge — 있었던 일을 그대로 남긴다

```bash
git merge --no-ff feat/alert-feed
```

`--no-ff` 가 핵심이다. 기본값 `--ff` 는 **가능하면 fast-forward 로 처리해서 머지 커밋을 만들지 않는다** — 브랜치 포인터만 앞으로 옮긴다. 그러면 브랜치가 있었다는 사실 자체가 로그에서 사라진다. `--no-ff` 는 **fast-forward 가 가능한 경우에도 머지 커밋을 만든다.**

머지 커밋이 있으면 `git log --first-parent` 로 **"머지 단위"만 훑을 수 있다.** 공식 문서가 설명하는 그대로, 머지 커밋을 만나면 첫 번째 부모만 따라가서 개별 커밋을 건너뛴다. 즉 **한 히스토리 안에 두 개의 해상도가 공존한다** — 평소엔 머지 단위로 보고, 필요하면 안을 열어본다. 이게 merge 의 가장 큰 실질 이득이다.

### 장점
* **일어난 일이 그대로 남는다.** 언제 갈라져 언제 합쳐졌는지가 사실로 기록된다
* **`--first-parent` 로 해상도를 골라 볼 수 있다**
* **되돌리기 전에 이력이 손상되지 않는다.** 푸시된 커밋을 다시 쓰지 않으므로 안전하다
* 브랜치 안의 세부 커밋이 남아서 **`git bisect` · `git blame` 이 정확한 지점을 짚는다**

### 단점
* **로그가 지저분해진다.** "wip", "오타", "리뷰 반영" 같은 커밋이 영구히 남는다
* **그래프가 복잡해진다.** 브랜치가 여럿 동시에 돌면 `git log --graph` 가 읽기 힘들어진다
* **머지 커밋 되돌리기가 까다롭다.** `git revert` 는 머지 커밋에 대해 `-m` 으로 **어느 부모가 본류인지** 지정해야 하고, 공식 문서는 여기에 경고를 붙여둔다 — *"머지 커밋을 되돌리는 것은 그 머지가 가져온 트리 변경을 다시는 원하지 않는다고 선언하는 것"* 이라, 나중에 같은 브랜치를 다시 머지해도 이미 되돌린 부분은 안 들어온다

## 3. squash — 브랜치 하나를 커밋 하나로

```bash
git merge --squash feat/alert-feed
git commit
```

공식 문서의 정의가 정확하다. **"진짜 머지가 일어난 것처럼 작업 트리와 인덱스 상태를 만들되, 커밋을 만들지 않고 HEAD 도 옮기지 않으며 `MERGE_HEAD` 도 기록하지 않는다."** 그래서 뒤이은 `git commit` 이 **머지 커밋이 아니라 일반 커밋 하나**를 만든다.

GitHub · GitLab 의 "Squash and merge" 버튼이 이걸 자동화한 것이고, 최종 메시지를 UI 에서 입력받는다.

### 장점
* **`main` 의 로그가 "한 줄 = 한 기능"이 된다.** 읽는 사람에게 가장 친절한 형태
* **작업 중 커밋을 마음대로 해도 된다.** "wip" 를 남발해도 최종 로그에 영향이 없다. 이 심리적 여유가 생각보다 크다
* **되돌리기가 쉽다.** 커밋 하나를 `git revert` 하면 기능 전체가 사라진다
* [[Conventional Commits]] 와 궁합이 좋다 — 최종 커밋 메시지 **하나만** 규약을 지키면 되고, 실제로 스펙 FAQ 도 "스쿼시 워크플로라면 모든 기여자가 규약을 따를 필요는 없다"고 인정한다

### 단점
* **작업 과정이 사라진다.** 왜 이렇게 짰는지, 어떤 시도를 했다가 되돌렸는지가 남지 않는다
* **커밋이 커진다.** 100줄짜리 기능이 커밋 하나면 `git bisect` 가 "이 커밋이 범인"까지만 알려주고 그 안에서는 도움이 안 된다. 브랜치가 클수록 이 손실이 커진다
* **`git blame` 이 뭉개진다.** 모든 줄이 같은 커밋·같은 날짜를 가리킨다
* **훅으로 커밋 메시지를 검사하는 의미가 옅어진다.** 작업 중 커밋은 어차피 사라지고, 최종 메시지는 서버(GitLab MR UI)에서 만들어져 로컬 훅을 거치지 않는다 → [[Git 훅(Git Hooks)]]
* **브랜치를 짧게 유지해야 한다는 조건이 붙는다.** 이건 단점이라기보다 [[Git 브랜치 전략]]과 맞물리는 전제다

## 4. rebase — 없었던 일로 다시 쓴다

```bash
git rebase main       # 브랜치 커밋을 main 끝에 다시 얹는다
```

커밋을 하나씩 `main` 끝에 다시 적용한다. 내용은 같지만 **부모가 달라지므로 SHA 가 전부 바뀐다** — 원래 커밋과 "같은 커밋"이 아니라 복제본이다.

이 성질에서 유일하지만 절대적인 규칙이 나온다. 공식 문서의 표현 그대로다.

> **"다른 사람이 그 위에 작업을 쌓은 브랜치를 리베이스(또는 다른 방식으로 재작성)하는 것은 나쁜 생각이다. 하류의 모든 사람이 자기 히스토리를 손으로 고쳐야 한다."**

그래서 rebase 는 **아직 공유되지 않은 브랜치**에서만 안전하다. 공유된 브랜치를 리베이스하면 강제 푸시가 따라오고, 그 시점에 다른 사람의 로컬은 조용히 갈라진다.

### 장점
* **히스토리가 선형이 된다.** `git log` 가 시간순 한 줄로 읽힌다
* **커밋 단위가 보존된다.** squash 와 달리 `git bisect` 의 해상도가 유지된다
* **"내 브랜치를 최신 main 위에서 검증했다"는 상태를 만든다.** 머지 전에 충돌을 미리 해소한다
* 대화형 리베이스(`git rebase -i`)로 **푸시 전에 커밋을 정리**할 수 있다. 지저분한 커밋을 squash 로 뭉개는 대신 손으로 다듬는 선택지

### 단점
* **공유된 브랜치에서는 쓰면 안 된다.** 이 한 줄이 rebase 의 진입 장벽 전부다
* **충돌을 여러 번 해결해야 할 수 있다.** 커밋을 하나씩 다시 적용하므로 같은 파일 충돌이 커밋 수만큼 반복될 수 있다
* **히스토리가 거짓말을 한다.** 실제로는 갈라져서 작업했는데 로그는 순서대로 한 일처럼 보인다. 이걸 장점으로 보는 사람과 단점으로 보는 사람이 갈린다
* **팀원 숙련도를 요구한다.** 리베이스 중 충돌 상태에서 `--continue` / `--abort` / `--skip` 을 헷갈리면 작업을 날린다. **3인 팀이라도 한 명이 이걸 모르면 사고가 난다**

## 5. 어떻게 고를 것인가

| 상황 | 선택 |
| ----------- | ----------- |
| 브랜치가 짧고(며칠), 기능 단위 로그를 원한다 | **squash** |
| 브랜치 안 커밋 하나하나가 의미 있다 (리팩터링 단계 등) | **merge (`--no-ff`)** 또는 rebase |
| 여러 사람이 한 브랜치에서 작업했다 | **merge.** rebase 는 금지 |
| 릴리스 이력을 브랜치 단위로 추적한다 | **merge (`--no-ff`)** + `--first-parent` |
| 커밋 메시지 규약을 개별 커밋까지 강제하고 싶다 | **merge 또는 rebase.** squash 는 개별 커밋을 지운다 |

실무에서 가장 흔한 조합은 **"내 브랜치는 rebase 로 최신화하고, `main` 에는 squash 로 넣는다"** 다. 로컬에서만 rebase 를 쓰니 공유 브랜치 문제가 안 생기고, `main` 로그는 기능 단위로 깔끔해진다.

주의할 점 하나. **셋 중 하나로 통일하지 않으면 로그가 세 가지 모양이 섞여서 어느 것도 신뢰할 수 없게 된다.** `--first-parent` 는 머지 커밋이 일관되게 있어야 의미가 있고, 선형 히스토리는 예외가 하나만 생겨도 선형이 아니다. **전략을 고르는 것보다 하나로 고정하는 게 중요하다** — [[Feature-Sliced Design(FSD)]]의 레이어 규칙이나 [[단방향 의존성]]과 같은 성질이다. 규칙은 전부 지켜지거나 없거나로 수렴한다.

## 정리

* **merge 는 사실을 남기고, squash 는 요약하고, rebase 는 사실을 다시 쓴다**
* `git merge` 기본값은 `--ff` — **브랜치가 있었다는 사실이 로그에서 사라진다.** 남기려면 `--no-ff`
* 머지 커밋의 값어치는 **`git log --first-parent`** 로 해상도를 골라 볼 수 있다는 것
* squash 는 **"한 줄 = 한 기능"** 을 준다. 대가는 `bisect` · `blame` 해상도와 작업 과정
* rebase 의 유일한 규칙: **공유된 브랜치를 리베이스하지 마라.** SHA 가 바뀌어서 하류가 전부 깨진다
* 흔한 조합은 **로컬 rebase + main 에 squash**
* **무엇을 고르든 하나로 통일하는 게 고르는 것보다 중요하다.** 섞이면 어느 것도 신뢰할 수 없다
