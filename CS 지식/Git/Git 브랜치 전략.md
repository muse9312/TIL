# Git 브랜치 전략
----

브랜치를 **몇 개, 얼마나 오래, 어떤 방향으로 흐르게** 둘 것인지에 대한 팀의 합의.

브랜치 전략이 실제로 푸는 문제는 하나다. **여러 사람이 동시에 고친 코드를 언제 합칠 것인가.** 합치기를 미룰수록 개별 작업은 편해지고 합칠 때의 고통은 커진다. 모든 전략은 이 저울의 어디에 설 것인지에 대한 답이고, **그 답은 팀 규모가 아니라 배포 주기가 결정한다.**

> 출처 (2026-09-01 확인)
> Git Flow: https://nvie.com/posts/a-successful-git-branching-model/
> GitHub Flow: https://docs.github.com/en/get-started/using-github/github-flow
> GitLab Flow: https://about.gitlab.com/topics/version-control/what-is-gitlab-flow/
> Trunk Based Development: https://trunkbaseddevelopment.com/

## 1. 네 가지 전략

### ① Git Flow — 릴리스가 이벤트인 세계

2010년 nvie 가 제안한 모델. 장수 브랜치 둘(`main` · `develop`)에 임시 브랜치 셋(`feature/*` · `release/*` · `hotfix/*`)이 붙는다.

```
main      ──●──────────────●────────●──   태그가 붙는 곳. 배포된 것만
             ╲            ╱        ╱
hotfix        ╲          ╱        ●        긴급 수정. main 과 develop 양쪽으로
               ╲        ╱        ╱
release         ╲      ●────────╱          안정화 기간. 버그만 고침
                 ╲    ╱
develop   ────●───●──●──────────────────   통합 지점. 다음 릴리스의 상태
             ╱ ╲
feature   ──●   ●──                        기능별 브랜치
```

핵심은 **`develop` 과 `release` 라는 완충 구간**이다. `develop` 에 합쳐진 코드가 곧바로 배포되지 않고, `release` 브랜치에서 안정화 기간을 거친다. 그동안 다음 기능 개발은 `develop` 에서 계속된다. **릴리스가 하나의 이벤트이고 그 이벤트에 준비 기간이 필요한** 세계를 위한 설계다.

**저자 본인이 2020년 3월에 반성문을 달았다는 게 이 모델에 대한 가장 정확한 평가다.**

> "이 모델은 2010년에 고안됐고 (…) 웹 애플리케이션을 지속적으로 배포하는 팀이라면 git-flow 를 억지로 끼워 맞추기보다 **훨씬 단순한 워크플로(GitHub flow 같은)를 채택하기를 권한다.** 다만 명시적으로 버전이 매겨지는 소프트웨어를 만들거나, 여러 버전을 동시에 지원해야 한다면 git-flow 는 여전히 잘 맞을 수 있다."

즉 Git Flow 가 틀린 게 아니라 **전제가 달라졌다.** [[시맨틱 버저닝(SemVer)]]으로 버전을 매겨 배포하는 소프트웨어(설치형 앱, 라이브러리, 온프레미스 제품)에는 여전히 맞고, 하루에도 몇 번 배포하는 웹 서비스에는 완충 구간이 순수 비용이다.

### ② GitHub Flow — 브랜치 하나 + PR

공식 문서가 정의하는 절차는 여섯 단계뿐이다.

```
1. 브랜치를 만든다 (설명적인 이름으로)
2. 변경한다 (변경 단위마다 커밋)
3. Pull Request 를 연다
4. 리뷰 코멘트에 대응한다
5. 머지한다
6. 브랜치를 지운다
```

장수 브랜치는 `main` 하나다. **`main` 은 항상 배포 가능한 상태**라는 것이 유일하면서 가장 중요한 불변식이고, 나머지는 전부 이 불변식을 지키기 위한 장치다. `develop` 도 `release` 도 없다.

단순함이 곧 강점이다. 배울 게 사실상 없고, 브랜치가 지금 어떤 상태인지 헷갈릴 일이 없다. 대신 **`main` 을 지키는 책임이 전적으로 리뷰와 CI 에 실린다** → [[지속적 통합(CI)]]

### ③ GitLab Flow — GitHub Flow + 환경/릴리스 브랜치

GitHub Flow 를 그대로 두고, 그것만으로 안 되는 두 상황에 브랜치를 추가한다.

| 변형 | 추가하는 것 | 언제 |
| ----------- | ----------- | ----------- |
| **production 브랜치** | `main` → `production` | 배포 시점을 코드 병합과 분리해야 할 때 |
| **환경 브랜치** | `main` → `staging` → `production` | 스테이징·QA 단계를 거쳐야 할 때 |
| **릴리스 브랜치** | `v1` · `v2` 를 따로 유지 | 여러 버전을 동시에 지원해야 할 때 |

핵심 규칙은 **"커밋은 아래로만 흐른다"** — `main` 에 먼저 합치고 거기서 아래 환경으로 내려보낸다. 반대 방향(운영에서 급히 고치고 `main` 에 반영을 잊는 것)이 사고의 근원이라 이 방향을 못 박는다. [[단방향 의존성]]과 같은 발상이 브랜치에 적용된 셈이다.

GitLab 은 여기에 **이슈 트래킹과의 결합**을 강조한다. 브랜치와 MR 이 이슈에서 시작되고 머지되면 이슈가 닫힌다. 전략이라기보다 **GitHub Flow 를 실제 배포 파이프라인에 맞춰 늘리는 방법의 카탈로그**에 가깝다.

### ④ Trunk Based Development (TBD) — 브랜치를 만들지 않는다

> "개발자들이 **trunk 라 불리는 단일 브랜치에서 협업하고, 다른 장수 개발 브랜치를 만들라는 압력에 저항하는** 소스 관리 브랜칭 모델."

두 가지 형태가 있다.

* **trunk 에 직접 커밋** — 아주 작은 팀
* **수명이 아주 짧은 브랜치** — 리뷰와 CI 를 위해서만 만들고 바로 지운다

두 번째의 조건이 구체적이다. 공식 문서는 **브랜치 수명 "이틀을 넘기면 장수 브랜치가 될 위험"**, **브랜치당 개발자 1명(페어면 2명)** 을 못 박고, 개발자끼리 브랜치를 공유하는 것을 금지한다.

미완성 기능을 어떻게 `main` 에 넣느냐는 질문에 대한 답이 **피처 플래그와 branch by abstraction** 이다. 코드는 합치되 기능은 꺼둔다. 이게 TBD 의 전제이자 진입 장벽이다 → [[피처 플래그(Feature Flag)]]

릴리스는 두 방식 중 하나다. trunk 에서 필요할 때 릴리스 브랜치를 잘라 쓰고 얼마 뒤 지우거나, **trunk 에서 바로 배포하고 문제가 생기면 "앞으로 고친다(fix forward)"**. 되돌리는 대신 앞으로 고친다는 게 TBD 의 성격을 잘 보여준다.

## 2. 비교

| | Git Flow | GitHub Flow | GitLab Flow | TBD |
| ----------- | ----------- | ----------- | ----------- | ----------- |
| 장수 브랜치 | `main` · `develop` | `main` | `main` + 환경/릴리스 | `trunk` |
| 브랜치 수명 | 수일~수주 | 수일 | 수일 | **≤ 2일** |
| 배포 주기 | 주·월 단위 | 수시 | 수시 (환경 통과 후) | 하루 여러 번 |
| 필요한 인프라 | 없음 (사람이 관리) | CI + 리뷰 | CI + 환경별 파이프라인 | CI + **피처 플래그** |
| 여러 버전 동시 지원 | **가능** (`release/*`) | 어려움 | **가능** (릴리스 브랜치) | 릴리스 브랜치로 가능 |
| 통합 빈도 | 낮음 | 중간 | 중간 | **매우 높음** |
| 학습 비용 | 높음 | 매우 낮음 | 낮음 | 개념은 낮고 **인프라가 비쌈** |

## 3. 무엇을 고를 것인가

**팀 규모보다 배포 주기가 먼저다.** 인원이 많아도 한 달에 한 번 배포하면 Git Flow 가 맞고, 셋이어도 매일 배포하면 GitHub Flow 가 맞다.

| 상황 | 맞는 전략 | 이유 |
| ----------- | ----------- | ----------- |
| 라이브러리 · 설치형 · 온프레미스 (버전이 명시적) | **Git Flow** | 저자 본인이 인정한 유효 구간. 여러 버전 동시 지원이 필요하다 |
| 웹 서비스, 배포가 수시, 팀 1~10명 | **GitHub Flow** | 완충 구간이 순수 비용이 되는 구간 |
| 웹 서비스인데 스테이징·QA 관문이 있음 | **GitLab Flow** | GitHub Flow + 환경 브랜치 |
| 여러 팀, 하루 수십 회 배포, 플래그 인프라 있음 | **TBD** | 머지 충돌을 시간으로 죽인다 |
| **뭘 골라야 할지 모르겠음** | **GitHub Flow** | 가장 싼 기본값. 필요해지면 GitLab Flow 로 늘리면 된다 |

각각이 실제로 무너지는 지점은 이렇다.

### Git Flow 의 단점
* **대부분의 팀에 과하다.** 브랜치 다섯 종류의 규칙을 전원이 외워야 하고, 그 대가로 얻는 건 "릴리스 준비 기간"인데 수시 배포하는 팀에는 그 기간이 없다
* **`develop` 과 `main` 이 갈라진다.** hotfix 를 양쪽에 반영하는 걸 한 번만 놓쳐도 두 브랜치의 진실이 달라지고, 그다음부터는 어느 쪽이 맞는지 아무도 모른다
* **머지 충돌이 릴리스 직전에 몰린다.** 통합을 미루는 구조라서 필연적이다
* **CI 를 어디에 걸어야 하는지 애매하다.** `develop` · `release` · `main` 을 다 검사하면 파이프라인이 세 배가 된다

### GitHub Flow 의 단점
* **`main` 을 지키는 장치가 없으면 그냥 "다같이 main 에 푸시"와 같아진다.** 브랜치 보호·필수 리뷰·CI 게이트가 전제고, 이게 없으면 전략이 아니라 희망이다
* **배포 시점을 머지 시점과 분리할 수 없다.** 머지했는데 오늘 나가면 안 되는 기능이라면 답이 없다. 여기서 GitLab Flow 의 production 브랜치나 피처 플래그가 필요해진다
* **여러 버전을 동시에 지원하지 못한다**

### GitLab Flow 의 단점
* **브랜치가 늘어나면 Git Flow 의 문제가 그대로 돌아온다.** 환경 브랜치가 셋이 되는 순간 "어디까지 내려갔는지"를 추적하는 비용이 생긴다
* **정의가 느슨하다.** 표준 문서 하나로 못 박힌 Git Flow 나 TBD 와 달리, "상황에 맞게 늘려 쓰라"는 카탈로그에 가까워서 **팀마다 GitLab Flow 라 부르는 것이 다르다**

### TBD 의 단점
* **피처 플래그 인프라를 전제한다.** 이게 가장 큰 진입 장벽이다. 플래그를 켜고 끄는 수단, 플래그별 테스트, **그리고 다 쓴 플래그를 제거하는 규율**까지 필요하다. 마지막 것을 놓치면 코드가 죽은 분기로 뒤덮인다
* **CI 가 느리거나 불안정하면 즉시 무너진다.** 통합 빈도가 높다는 건 CI 실패가 전원을 막는다는 뜻이다
* **"이틀 안에 끝나는 단위"로 일을 쪼갤 수 있어야 한다.** 이건 브랜치 규칙이 아니라 작업 분할 능력의 문제고, 도구로 해결되지 않는다
* **리뷰 시간이 병목이 된다.** 이틀 안에 머지하려면 리뷰가 몇 시간 안에 끝나야 한다

## 4. 브랜치 이름

전략과 별개로 정해야 하는 것. 커밋 [[Conventional Commits]]의 type 어휘를 그대로 쓰면 어휘가 하나로 줄어든다.

```
feat/alert-feed          기능
fix/sse-reconnect        수정
chore/commitlint-setup   잡무
```

`<type>/<요약>` 형태는 슬래시 덕에 일부 Git GUI 에서 폴더처럼 접히고, `git branch --list 'feat/*'` 로 걸러진다. 이름 규칙 자체보다 **커밋 type 과 어휘를 공유한다**는 점이 실질적인 이득이다 — 외울 목록이 두 개가 아니라 하나가 된다.

## 5. 펫바디에서의 검토 (초안 · 미확정)

`petbody-client` 의 `CONTRIBUTING.md` 는 **초안이고 팀 논의 전이다.** 현재 초안은 **GitHub Flow** 를 제안하고 있다.

근거는 이렇다.

* 3인 팀(사용자 + wjy + dgchoi)에 사내 GitLab, 레포 세 개(client / server / ai)
* 배포되는 라이브러리가 아니라 **사내 B2B 관제 대시보드** — 여러 버전을 동시에 지원할 일이 없다. Git Flow 의 유효 구간(명시적 버전 · 다중 버전 지원)에 해당하지 않는다
* 피처 플래그 인프라가 없다 — TBD 의 전제가 성립하지 않는다
* 현재 상태가 **전원 `main` 직접 푸시**이고 커밋 이력이 `222`, `test`, `md 수정` 이다. 이 지점에서 도입 비용이 가장 낮은 게 GitHub Flow 다

```
main                    항상 배포 가능. 직접 푸시 금지
 ├─ feat/alert-feed
 ├─ fix/sse-reconnect
 └─ chore/commitlint-setup
```

작업 → MR → 리뷰 1명 → **Squash merge** 로 제안돼 있다. 스쿼시를 고른 이유와 그 대가는 [[Git 머지 전략(merge · squash · rebase)]]에 정리했다.

**미결 쟁점**이 둘 남아 있다. 하나는 사내 GitLab 에서 `main` 브랜치 보호를 **실제로 걸 것인지, 신뢰 기반으로 둘 것인지**. GitHub Flow 의 단점 첫 줄이 바로 이것이라 여기서 갈린다. 다른 하나는 **3인 팀에서 리뷰 1명이 현실적인지** — 리뷰가 병목이 되면 규칙을 우회하게 되고, 그러면 브랜치 보호를 걸어둔 의미가 없어진다.

스테이징 환경이 생기면 GitLab Flow 의 환경 브랜치로 늘리는 게 자연스러운 다음 수순이다. **지금 미리 만들어둘 이유는 없다.**

## 정리

* 브랜치 전략이 푸는 문제는 **"통합을 언제 할 것인가"** 하나다. 미룰수록 개별 작업은 편하고 합치기는 아프다
* 선택 기준은 팀 규모가 아니라 **배포 주기와 다중 버전 지원 필요 여부**
* **Git Flow** 는 버전이 명시적이고 여러 버전을 지원하는 소프트웨어용. 저자 본인이 2020년에 "웹 앱이면 GitHub flow 를 쓰라"고 썼다
* **GitHub Flow** 는 `main` 하나 + PR. 가장 싼 기본값이지만 **브랜치 보호와 CI 가 없으면 전략이 아니라 희망**이다
* **GitLab Flow** 는 GitHub Flow 에 환경·릴리스 브랜치를 더한 카탈로그. 정의가 느슨해서 팀마다 다르게 부른다
* **TBD** 는 브랜치 수명 ≤2일, 1인 1브랜치. **피처 플래그 인프라가 전제**고 이게 진입 장벽이다
* 뭘 고를지 모르겠으면 GitHub Flow. **늘리는 건 싸고 줄이는 건 비싸다**
