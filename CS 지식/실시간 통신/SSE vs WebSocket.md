# SSE vs WebSocket
----

서버가 클라이언트에게 데이터를 **먼저 밀어주는** 방법들. [[싱글 페이지 애플리케이션(SPA)]] 대시보드·알림·채팅 같은 실시간 UI를 만들 때 매번 나오는 선택.

## 1. 선택지 3개

### Polling / Long Polling
클라이언트가 주기적으로 물어본다.
- 장점 — 구현이 제일 단순. 인프라 제약 없음
- 단점 — 지연이 폴링 주기만큼 생기고, 변화가 없어도 요청이 나감. 서버 부하 낭비

### SSE (Server-Sent Events)
`text/event-stream` 콘텐츠 타입으로 HTTP 연결을 열어두고 서버가 계속 흘려보낸다. **단방향(서버 → 클라이언트).**

```js
const es = new EventSource('/api/stream');
es.addEventListener('alert', (e) => {
  const data = JSON.parse(e.data);
});
```

서버가 보내는 형식은 그냥 텍스트다.
```
event: alert
id: 1042
data: {"level":"urgent","zone":"playroom-1"}

```

### WebSocket
HTTP로 핸드셰이크한 뒤 **TCP 위의 양방향 전이중 채널**로 업그레이드한다. `ws://` / `wss://`.

## 2. 비교표

| 항목 | Polling | SSE | WebSocket |
| ----------- | ----------- | ----------- | ----------- |
| 방향 | 요청/응답 | 서버 → 클라이언트 (단방향) | 양방향 |
| 프로토콜 | HTTP | HTTP | 별도 프로토콜(업그레이드) |
| 자동 재연결 | 해당 없음 | **브라우저가 기본 제공** | 직접 구현 |
| 유실 복구 | 해당 없음 | **`Last-Event-ID` 기본 지원** | 직접 구현 |
| 데이터 형식 | 제한 없음 | **텍스트만** (UTF-8) | 텍스트 + 바이너리 |
| 프록시/방화벽 통과 | 최상 | 좋음 (그냥 HTTP) | 중간 (업그레이드 차단되는 곳 있음) |
| 인증 | 평범 | 쿠키 자동 전송 / **커스텀 헤더 불가** | 핸드셰이크 시 쿠키, 이후 직접 |
| 압축·HTTP/2 이점 | 있음 | 있음 | 제한적 |
| 구현 난이도 | 낮음 | **낮음** | 중간~높음 |

## 3. SSE의 함정 두 가지

> 아래 두 항목은 2026-09-01에 [WHATWG HTML 표준 §Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html) 와 [MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource) 로 확인했다.

### HTTP/1.1 동시 연결 6개 제한
브라우저는 **도메인당 동시 연결을 6개**로 제한한다. SSE 연결 하나가 그 자리를 계속 점유하므로, 탭을 여러 개 열면 나머지 요청이 막힌다.

**중요한 건 이 6개가 "탭당"이 아니라 "브라우저 + 도메인" 단위라는 점이다.** 즉 `example.com` 탭을 7개 열면 7번째 탭의 SSE는 앞의 연결이 끊길 때까지 그냥 안 붙는다. 사용자가 대시보드를 여러 탭에 띄우는 건 흔한 일이라 실제로 밟는다. Chrome·Firefox 모두 이 이슈를 **"Won't fix"** 로 닫아놨으니 브라우저가 고쳐주길 기다릴 게 아니다.

→ **HTTP/2 이상에서는 해결된다.** 멀티플렉싱으로 한 커넥션에 스트림을 여러 개 태우기 때문. 상한은 고정값이 아니라 서버·클라이언트가 협상하며 **기본값이 100 스트림**이다. 즉 **SSE를 쓸 거면 HTTP/2를 켜라.**

- 함정 — 앱 서버가 HTTP/2여도 앞단 프록시가 백엔드로는 HTTP/1.1로 붙는 구성이 흔하다. **브라우저↔엣지 구간만 HTTP/2면 이 제한은 풀린다**(제한은 브라우저 쪽 규칙이므로). 확인은 브라우저 개발자도구 네트워크 탭의 Protocol 열로 한다

### 커스텀 헤더를 못 붙인다
브라우저 기본 `EventSource`는 `Authorization` 헤더를 넣을 수 없다. 생성자가 받는 옵션이 `withCredentials` 하나뿐이다.

```js
const es = new EventSource('/api/stream', { withCredentials: true });
```

- **쿠키 세션이면 문제 없음** — 동일 오리진이면 쿠키는 그냥 자동 전송된다. `withCredentials` 가 필요한 건 **크로스 오리진일 때**뿐이고, 이때 자격증명 모드를 `include` 로 올리는 역할을 한다. 서버도 그에 맞는 CORS 헤더를 줘야 한다 → [[세션 vs JWT vs OAuth]]
	- 인스턴스의 `EventSource.withCredentials` 는 **읽기 전용**이다. 만든 뒤에 바꿀 수 없으니 생성 시점에 정해야 한다
- Bearer 토큰이면 → [[쿼리스트링(Query String)]]에 담거나(로그에 남아 비추천), `fetch` 기반 SSE 폴리필을 쓰거나, 아예 WebSocket으로 간다

## 4. 어떻게 고를까

**양방향이 정말 필요한가?** 이 한 줄로 대부분 갈린다.

WebSocket이 맞는 경우
- 채팅, 협업 편집 — 클라이언트도 고빈도로 보낸다
- 게임, 실시간 커서 — 지연이 밀리초 단위로 중요
- 바이너리 전송 (오디오, 영상 프레임)

SSE가 맞는 경우
- **알림, 대시보드, 로그 스트림, 진행률** — 서버가 밀기만 하면 됨
- 클라이언트 → 서버는 어차피 일반 REST로 충분한 경우
- 인프라를 단순하게 유지하고 싶을 때 (그냥 HTTP라 프록시/로드밸런서가 안 막음)

> 클라이언트가 서버에 보내는 게 "가끔 있는 액션" 정도라면, **SSE + 일반 REST 조합**이 WebSocket보다 거의 항상 낫다. 재연결과 유실 복구를 공짜로 얻기 때문.

## 5. 재연결과 유실 복구 — 실무에서 제일 중요한 부분

실시간 UI의 진짜 난이도는 "연결하기"가 아니라 **"끊겼다 붙었을 때 상태를 어떻게 맞추냐"** 다. 모바일에서 화면을 잠갔다 켜는 상황이 상시로 벌어진다.

### SSE의 기본 지원
서버가 `id:` 를 같이 보내면, 브라우저가 재연결할 때 **`Last-Event-ID` 헤더에 마지막으로 받은 id를 자동으로 실어 보낸다.** 서버는 그 이후 이벤트만 다시 보내면 된다. 명세에 정의된 동작이라 브라우저 구현에 기대도 되는 부분이다.

명세를 읽고 알게 된 두 가지 (2026-09-01 확인)
- **last event ID는 이벤트마다 초기화되지 않는다.** `id:` 없는 이벤트가 와도 직전 값이 그대로 유지된다. 그래서 일부 이벤트에만 id를 붙여도 동작은 한다 — 대신 복구 지점이 그만큼 성겨진다
- **재연결 간격은 서버가 정할 수 있다.** 초기값은 구현이 정하는 "몇 초 언저리"의 값이지만, 스트림에 `retry: 10000` 처럼 밀리초 정수를 보내면 브라우저가 그 값을 쓴다. 서버 재시작 시 **모든 클라이언트가 동시에 재접속하는 thundering herd** 를 이걸로 완화할 수 있다
- **본문은 항상 UTF-8이다.** 다른 인코딩을 지정할 방법이 명세상 없다. 바이너리를 실어야 하면 base64를 씌우거나 WebSocket으로 가야 한다

### 그것만으로 부족한 이유
서버가 그 사이 재시작했거나 버퍼가 날아갔으면 못 메운다. 그래서 실무에서는 **두 채널을 나눈다.**

```
스냅샷 조회 (REST)  ──▶  현재 상태 전체        ← 최초 진입 · 재연결 직후
델타 푸시 (SSE)     ──▶  변경분만              ← 연결 유지 중
```

React라면 ([[상태 관리]] 참고)
- **[[TanStack Query]]** — 스냅샷 조회. 재연결 시 `invalidateQueries` 로 상태 복구
- **SSE** — 도착하면 `setQueryData` 로 캐시 갱신. 이때 append가 아니라 **id 기준 병합**이어야 델타와 재조회 결과가 중복되지 않는다

이 복구 경로가 없으면 화면이 **조용히 틀어진다.** 에러도 안 나고 그냥 값이 안 맞는다. 제일 잡기 어려운 종류의 버그.

## 6. 클라이언트 상태 설계 — 구독 범위를 쪼갤 것

이벤트가 초당 여러 건 들어오는 대시보드에서, 컴포넌트가 **전체 이벤트 배열을 구독하면 안 된다.** 이벤트 하나에 화면 전체가 리렌더된다. 이건 [[메모이제이션(Memoization)]]으로 덮을 문제가 아니라 [[상태 관리]] 구조의 문제다.

```
SSE  ──▶  이벤트 스토어([[zustand]])
                 │
     ┌───────────┼──────────────┐
     ▼           ▼              ▼
 알람 피드    재원 현황       추이 차트
 (등급·최근    (개체 상태      (1분 집계
  N건만)        변화만)         버킷만)
```

- selector로 **각 위젯이 자기 슬라이스만** 구독
- 차트는 원본 이벤트가 아니라 **집계된 버킷**을 구독 (이벤트 1건마다 차트를 다시 그릴 이유가 없다)

## 7. 정리

- **SSE = 단방향 + HTTP + 자동 재연결.** 서버가 밀기만 하면 되는 대부분의 경우에 정답
- WebSocket은 **양방향이 진짜 필요할 때** 꺼내는 카드
- SSE 쓸 거면 **HTTP/2를 켤 것** (연결 6개 제한)
- 브라우저 `EventSource`는 **커스텀 헤더 불가** — 쿠키 세션이면 무관
- 진짜 어려운 건 연결이 아니라 **재연결 후 상태 복구.** 스냅샷(REST) + 델타(SSE) 로 나눌 것

이 대시보드의 프론트 스택 선택 과정은 [[Vite React 템플릿 변형 비교]]에 정리했다.
