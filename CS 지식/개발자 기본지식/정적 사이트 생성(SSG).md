# 정적 사이트 생성(SSG)
----

**빌드 시점에** 모든 페이지의 HTML을 미리 만들어두고, 요청이 오면 그냥 파일을 내려주는 방식.

Static Site Generation. 서버가 요청마다 렌더링하는 [[서버 사이드 렌더링(SSR)]] 과 달리, 렌더링이 **배포 전에 한 번** 끝난다.

```
빌드 타임:  데이터 조회 → 모든 페이지 HTML 생성 → 파일로 저장
런타임:     요청 ──▶ 저장된 HTML 파일 그대로 응답 (CDN)
```

## 세 방식 비교

| | [[클라이언트 사이드 렌더링(CSR)]] | [[서버 사이드 렌더링(SSR)]] | **SSG** |
| ----------- | ----------- | ----------- | ----------- |
| HTML 생성 시점 | 브라우저 실행 시 | 요청 시마다 | **빌드 시 한 번** |
| 서버 필요 | 정적 서빙만 | **상시 필요** | 정적 서빙만 |
| TTFB | 빠름 | 느림 | **가장 빠름** |
| SEO | 불리 | 유리 | **유리** |
| 데이터 신선도 | 항상 최신 | 항상 최신 | **빌드 시점에 고정** |

### 장점
* **가장 빠르다** — CDN에서 파일 하나 내려주는 게 전부
* 서버 런타임 불필요 → 운영 비용이 거의 0
* 트래픽이 몰려도 안정적 (그냥 정적 파일)
* SEO에 유리

### 단점
* **데이터가 빌드 시점에 고정된다** — 내용이 바뀌면 다시 빌드·배포해야 함
* 페이지 수가 많으면 **빌드 시간이 폭발** — 수만 개 상품 페이지를 매번 다 생성?
* 사용자마다 다른 화면(로그인 상태, 개인화)에는 부적합

## 한계를 메우는 방법

* **ISR (Incremental Static Regeneration)** — 정적 페이지에 유효기간을 두고, 만료되면 백그라운드에서 다시 생성. SSG의 속도와 SSR의 신선도를 절충
* **온디맨드 재생성** — 데이터가 바뀔 때 웹훅으로 해당 페이지만 다시 빌드
* **정적 껍데기 + 클라이언트 페칭** — 뼈대는 SSG, 개인화 데이터는 브라우저에서 요청

## 언제 쓰나

* 문서, 블로그, 랜딩 페이지 — 내용이 자주 안 바뀜
* 제품 카탈로그처럼 **읽기 전용이고 모두에게 같은** 화면
* 반대로 대시보드·관리자 도구처럼 **사용자마다 다르고 실시간인** 화면에는 맞지 않는다
