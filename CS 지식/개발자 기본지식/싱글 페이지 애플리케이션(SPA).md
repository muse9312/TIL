# 싱글 페이지 애플리케이션(SPA)
----

**HTML 문서 하나**를 로드해두고, 이후 화면 전환을 서버 요청 없이 **JS가 DOM을 갈아끼워** 처리하는 구조.

전통적인 MPA(Multi Page Application)는 링크를 누를 때마다 서버에서 새 HTML을 받아 페이지가 통째로 새로고침된다. SPA는 그 왕복을 없앤다.

```
MPA:  클릭 ──▶ 서버 ──▶ 새 HTML ──▶ 전체 새로고침 (깜빡임)
SPA:  클릭 ──▶ JS가 URL 변경 + 필요한 데이터만 fetch ──▶ 일부 DOM 교체
```

## 성립 조건 두 가지

### 1. 클라이언트 사이드 라우팅
서버에 요청하지 않고 URL만 바꿔야 한다. History API(`pushState`)로 주소창을 바꾸고, 라우터가 그에 맞는 컴포넌트를 그린다.

**서버 설정이 하나 필요하다.** 사용자가 `/dashboard` 를 직접 입력하거나 새로고침하면 서버는 그런 파일을 모른다. **모든 경로를 `index.html` 로 폴백**시켜야 한다 (nginx `try_files ... /index.html`).

### 2. 데이터는 API로
화면은 클라이언트가 그리므로, 서버는 HTML이 아니라 **JSON을 준다.** 자연히 프론트/백이 분리된다.

## 렌더링 방식과의 관계

SPA는 **구조**이고 [[클라이언트 사이드 렌더링(CSR)]] · [[서버 사이드 렌더링(SSR)]] 은 **렌더링 시점**의 이야기라 층위가 다르다.

* SPA + CSR — 가장 흔한 조합. 빈 HTML을 받아 JS가 다 그림
* SPA + SSR — 첫 화면만 서버가 그려주고 ([[하이드레이션(Hydration)]] 이후) 이후 전환은 SPA처럼. Next.js 등

### 장점
* **화면 전환이 빠르고 매끄럽다** — 깜빡임 없음, 서버 왕복 없음
* 앱 같은 사용감 — 전환 애니메이션, 상태 유지가 자연스러움
* 서버는 API만 제공하면 됨 → **정적 호스팅 + CDN**으로 배포 가능
* 프론트/백 독립 배포

### 단점
* **초기 로딩이 무겁다** — JS 번들을 다 받아야 시작. 코드 스플리팅 필요
* **SEO에 불리** — 크롤러가 빈 HTML을 볼 수 있음
* 브라우저가 해주던 걸 직접 해야 함 — 뒤로가기, 스크롤 복원, 포커스 관리
* **메모리 누수가 쌓인다** — 페이지가 새로고침되지 않으므로 구독 해제·타이머 정리를 안 하면 누적됨
* 에러 하나가 앱 전체를 죽일 수 있음 → 에러 바운더리 필요

## 어디에 맞나

**맞는 경우**
* 로그인 뒤의 도구형 서비스 — 대시보드, 관리자 페이지, 에디터
* 화면 전환이 잦고 상태를 유지해야 하는 UI
* SEO가 필요 없는 화면

**안 맞는 경우**
* 검색 노출이 핵심인 콘텐츠 사이트 → [[정적 사이트 생성(SSG)]] 이나 SSR
* 페이지 간 이동이 드물고 각각 독립적인 사이트

## SPA에서 상태를 어디에 둘까

페이지가 새로고침되지 않으니 상태가 메모리에 계속 산다. 편하지만 함정이기도 하다 — 새로고침하면 다 날아간다.

필터·정렬·선택 같은 **화면을 재현하는 데 필요한 상태는 URL(쿼리스트링)에** 두는 게 좋다. 자세한 건 [[쿼리스트링(Query String)]] 과 [[상태 관리]].
