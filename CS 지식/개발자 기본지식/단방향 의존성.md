# 단방향 의존성
----

모듈 사이의 의존이 **한 방향으로만 흐르게** 만드는 규칙. 반대편은 상대를 아예 모른다.

[[응집도와 결합도]]에서 "결합은 없앨 수 없고 방향을 정하는 것이 목표"라고 했는데, 그 **방향을 정하는 규칙**이 이것이다.

## 1. 순환 참조가 왜 문제인가

A ↔ B처럼 서로를 참조하면 무슨 일이 생기는가. "찜찜하다" 말고 구체적인 비용이 넷 있다.

### ① 이해 비용 — 읽는 순서가 없어진다
단방향이면 아래에서 위로 읽으면 된다. 순환이 있으면 **A를 이해하려면 B를 알아야 하고 B를 이해하려면 A를 알아야 한다.** 진입점이 없다. 새로 온 사람이 코드를 못 읽는 이유의 상당 부분이 이거다.

### ② 테스트 비용 — 단독으로 세울 수 없다
A를 테스트하려면 B가 필요하고 B는 A가 필요하다. 결국 **둘을 통째로 세우거나 절반을 mock**해야 한다. "단위" 테스트가 사라진다.

### ③ 빌드·런타임 비용 — 초기화 순서가 깨진다
ES 모듈에서 순환은 문법 오류가 아니라 **런타임에 `undefined`로 나타난다.**

```ts
// a.ts
import { b } from './b';
export const a = 'A';
export const combined = a + b;   // b가 아직 초기화 안 됐으면 undefined

// b.ts
import { a } from './a';
export const b = a + 'B';        // a도 아직 초기화 전
```

무서운 점은 **터지는 게 아니라 조용히 값이 틀린다**는 것, 그리고 **import 순서·번들러·코드 스플리팅 설정에 따라 결과가 달라진다**는 것이다. 개발에서는 되는데 프로덕션 빌드에서만 깨지는 부류의 버그가 여기서 나온다.

번들러 입장에서도 순환은 **한 덩어리로 취급**할 수밖에 없어서 [[코드 스플리팅]]과 [[트리 셰이킹]]이 잘 안 먹는다.

### ④ 변경 비용 — 뗄 수가 없다
A를 다른 프로젝트로 옮기거나 지우려면 B가 딸려온다. 그리고 B에는 C가 딸려 있다. **모듈 하나를 꺼내려다 절반이 딸려 나오는 것**이 순환이 쌓인 코드베이스의 최종 형태다.

## 2. 방향은 어떻게 정하는가

기준은 **안정성**이다.

> **자주 바뀌는 것이 잘 안 바뀌는 것을 알아야 한다. 반대는 안 된다.**

잘 안 바뀌는 쪽(유틸, 도메인 타입)을 아래에 두고, 자주 바뀌는 쪽(화면, 기능)이 그걸 참조한다. 반대로 하면 안정적이어야 할 것이 불안정한 것에 끌려다닌다.

```
자주 바뀜   화면 / 페이지
    │             ↓
    │       기능 / 업무 로직
    │             ↓
    │       도메인 모델
    ↓             ↓
잘 안 바뀜   공용 유틸 · 타입
```

같은 발상이 코드 밖에도 적용된다. GitLab Flow 가 "커밋은 `main` 에서 아래 환경으로만 흐른다"를 못 박는 이유도 똑같다 — 운영에서 급히 고치고 위로 반영하는 걸 잊는 순간 두 곳의 진실이 갈라진다 → [[Git 브랜치 전략]]

이 그림이 곧 **레이어드 아키텍처**의 원리고, 프론트엔드에서 이걸 구체적인 폴더 규칙으로 못 박은 게 [[Feature-Sliced Design(FSD)]]다. 백엔드의 계층 분리, 클린 아키텍처의 의존성 규칙도 전부 같은 이야기의 변주다 → [[레이어드 아키텍처]]

## 3. 순환이 생기면 어떻게 푸는가

세 가지 방법이 있고, 순서대로 시도한다.

### ① 공통분모를 아래로 내린다 (대부분 이걸로 해결)
A와 B가 서로 필요한 이유는 보통 **둘 다 필요한 무언가가 한쪽에 잘못 들어 있어서**다. 그걸 C로 빼서 아래에 두면 A와 B가 서로를 모른다.

```
A ↔ B          →        A     B
                         ↘   ↙
                           C
```

### ② 의존성 역전 — 인터페이스를 아래에 둔다
아래 계층이 위 계층의 기능을 호출해야 하는 경우다. **인터페이스를 아래에 정의하고 위에서 구현을 주입**하면 컴파일 시점 의존은 여전히 아래로만 향한다. 프론트엔드에서는 콜백이나 이벤트를 넘기는 형태로 자주 나타난다.

```ts
// 아래 계층이 정의: "누군가 이걸 구현해서 넘겨줘"
type Notifier = (msg: string) => void;
export function processAlert(alert: Alert, notify: Notifier) { ... }
```

### ③ 이벤트로 끊는다
발행자가 구독자를 모르게 만든다. 결합은 확실히 끊기지만 **호출 관계가 코드에서 안 보이게 되는** 대가가 따른다. 이건 결합을 없앤 게 아니라 정적 분석 밖으로 밀어낸 것이라, 남발하면 추적이 더 어려워진다.

## 4. 함정

* **타입만 import하면 순환이 아니다?** — 반은 맞다. `import type`은 컴파일 후 사라져 런타임 순환은 안 생기지만, **개념적 순환은 그대로 남는다.** 타입이 서로 얽혀 있으면 결국 구현도 얽힌다. 그리고 `import type`을 안 붙이고 그냥 `import`하면 번들러가 못 지울 수도 있다
* **배럴 파일이 순환을 만든다** — `index.ts`를 거쳐 import하면 실제로는 필요 없는 모듈까지 딸려 들어와, 직접 참조로는 없던 순환이 생긴다. FSD처럼 배럴을 강제하는 구조에서 특히 자주 본다 → [[공개 API와 배럴 파일]]
* **"잠깐만 위로 부를게"** — 규칙을 한 번 깨면 그 예외가 근거가 돼서 다음 예외를 부른다. 방향 규칙은 **전부 지키거나 없거나** 둘 중 하나로 수렴한다
* **도구 없이는 못 지킨다** — 순환은 두 파일만 봐서는 안 보인다. 그래프 전체를 봐야 한다. `eslint-plugin-import`의 `import/no-cycle`, `madge`, `dependency-cruiser` 같은 걸 CI에 넣어야 한다. 특히 `import/no-cycle`은 느려서 미루기 쉬운데, 미루면 나중에 수백 개가 쌓인 걸 보게 된다

## 정리

* 의존은 **한 방향으로만.** 반대편은 상대를 아예 모르게
* 순환의 비용 — **읽는 순서 없음 · 단독 테스트 불가 · 런타임 `undefined` · 뗄 수 없음**
* ES 모듈 순환은 터지지 않고 **조용히 값이 틀린다.** 환경에 따라 결과가 달라지는 게 최악
* 방향의 기준은 **안정성.** 자주 바뀌는 것이 안 바뀌는 것을 안다
* 푸는 법 — **공통분모를 아래로**(대부분) → 의존성 역전 → 이벤트(최후)
* **린터로 검사하지 않으면 지켜지지 않는다.** 순환은 파일 두 개만 봐서는 안 보인다
