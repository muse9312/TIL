# 서버 사이드 렌더링(SSR)
----

요청이 올 때마다 **서버가 완성된 HTML을 만들어서** 브라우저에 보내는 방식.

브라우저는 받자마자 화면을 그릴 수 있다. 그 뒤 JS가 로드되면 [[하이드레이션(Hydration)]] 을 거쳐 상호작용이 가능한 상태가 된다.

```
브라우저 ──요청──▶ 서버
                    │ 데이터 조회 + HTML 생성
브라우저 ◀─HTML──┘
   │ 즉시 화면 표시 (아직 클릭은 안 됨)
   │ JS 다운로드 → 하이드레이션
   └ 상호작용 가능
```

## 다른 방식과의 비교

| 방식 | HTML을 언제 만드나 | 만드는 주체 |
| ----------- | ----------- | ----------- |
| [[클라이언트 사이드 렌더링(CSR)]] | 브라우저에서 실행 시점 | 브라우저 JS |
| **SSR** | **요청이 올 때마다** | **서버** |
| [[정적 사이트 생성(SSG)]] | 빌드 시점에 미리 | 빌드 도구 |

### 장점
* **첫 화면이 빠르다** — JS 다운로드를 기다리지 않고 바로 보임 (FCP 개선)
* **SEO에 유리** — 크롤러가 완성된 HTML을 그대로 읽음
* 링크 공유 시 미리보기(OG 태그)가 제대로 나옴
* 저사양 기기에서도 초기 표시가 안정적 — 렌더링 부담을 서버가 짐

### 단점
* **서버가 상시 떠 있어야 한다** — 정적 호스팅으로 못 끝냄. 배포 대상과 운영 비용이 늘어남
* 요청마다 서버가 렌더링 → **트래픽이 곧 서버 부하**
* TTFB(첫 바이트까지 시간)가 [[정적 사이트 생성(SSG)]] 보다 느림
* 서버/브라우저 양쪽에서 도는 코드라 `window`·`localStorage` 접근에 주의해야 함
* [[하이드레이션(Hydration)]] 불일치 에러가 디버깅하기 까다로움

## 언제 쓰나

**쓸 만한 경우**
* 검색 노출이 필요한 공개 페이지 — 커머스 상세, 블로그, 랜딩
* 초기 로딩이 매출에 직결되는 서비스
* 데이터가 대체로 정적이고 서버에서 확정 가능한 화면

**굳이 안 써도 되는 경우**
* **로그인 뒤의 내부 도구** — SEO가 의미 없음
* **데이터가 실시간으로 바뀌는 화면** — 서버가 그려준 HTML이 1초 뒤 다 갈아엎히므로 SSR이 오히려 손해
* 백엔드가 이미 별도 서버로 분리돼 있는 경우 — 프론트에 서버를 또 두면 배포 대상이 2개

> 판단 기준: **"첫 화면 HTML을 서버가 확정할 수 있는가"** 와 **"그 HTML이 얼마나 오래 유효한가"**

## 관련 개념

* [[싱글 페이지 애플리케이션(SPA)]] — SSR과 대비되는 구조. SPA도 SSR을 곁들일 수 있다
* Next.js 같은 [[프레임워크]] 는 SSR·SSG·CSR을 페이지 단위로 섞어 쓸 수 있게 해준다
