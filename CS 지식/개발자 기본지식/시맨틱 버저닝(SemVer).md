# 시맨틱 버저닝(SemVer)
----

버전 번호 `MAJOR.MINOR.PATCH` 의 각 자리에 **"무엇이 바뀌었는가"라는 의미를 부여하는** 규약.

버전을 마케팅 숫자가 아니라 **호환성에 대한 약속**으로 쓰자는 게 전부다. 그래서 스펙의 첫 조항이 "**공개 API 를 반드시 선언해야 한다**"이다. 무엇이 공개 API 인지 정해지지 않으면 "호환이 깨졌다"는 말 자체가 성립하지 않기 때문이다 → [[공개 API와 배럴 파일]]

> 기준: **Semantic Versioning 2.0.0** (2026-09-01 확인)
> 출처: https://semver.org/lang/ko/ · 범위 지정자는 https://github.com/npm/node-semver

## 1. 세 자리의 의미

| 자리 | 언제 올리나 | 스펙 |
| ----------- | ----------- | ----------- |
| **PATCH** `x.y.Z` | **하위 호환되는 버그 수정** | 조항 6 (MUST) |
| **MINOR** `x.Y.z` | **하위 호환되는 기능 추가.** 공개 API 를 deprecated 로 표시할 때도 | 조항 7 (MUST) |
| **MAJOR** `X.y.z` | **하위 호환이 깨지는 변경** | 조항 8 (MUST) |

규칙 두 개가 따라붙는다.

* **아래 자리는 리셋된다.** MINOR 를 올리면 PATCH 는 0, MAJOR 를 올리면 MINOR·PATCH 모두 0
* **배포된 버전의 내용은 절대 수정할 수 없다**(조항 3). 고칠 게 있으면 새 버전으로 낸다. npm 의 `package-lock.json` 이나 무결성 해시가 성립하는 전제가 이것이다

조항 7에 숨은 조항이 하나 있다. **deprecated 표시만 해도 MINOR 를 올려야 한다.** 실제로 없앤 건 아무것도 없는데 버전이 올라가는 이유는, "곧 사라진다"는 정보 자체가 소비자에게 전달돼야 할 변경이기 때문이다.

## 2. 0.x — 규칙이 적용되지 않는 구간

조항 4가 명시적으로 예외를 만든다.

> **메이저 버전 0(`0.y.z`)은 초기 개발용이다. 무엇이든 언제든 바뀔 수 있다. 공개 API 는 안정적이라고 여기면 안 된다.**

여기서 자주 하는 오해가 있다. `0.2.3 → 0.3.0` 이 파괴적 변경이라는 건 **스펙의 규칙이 아니라 관행**이다. 스펙은 0.x 에서 "무엇이든 언제든" 이라고만 하고, FAQ 는 `0.1.0` 에서 시작해 릴리스마다 MINOR 를 올리라고 **권고**할 뿐이다. 그런데 npm 의 범위 해석기가 이 관행을 코드로 굳혔다(3절).

그래서 0.x 라이브러리를 쓸 때는 **`0.6.0 → 0.7.0` 업그레이드를 MAJOR 취급**해야 한다. 예를 들어 FSD 공식 린터 `steiger` 가 아직 0.x 라 API 가 바뀔 수 있다는 경고는 이 조항 그대로다 → [[Feature-Sliced Design(FSD)]]

## 3. 범위 지정자 `^` 와 `~`

**중요한 구분: 이건 SemVer 스펙이 아니다.** semver.org 에는 `^` 도 `~` 도 나오지 않는다. npm 이 쓰는 `node-semver` 라이브러리가 정의한 **범위 문법**이고, 이걸 SemVer 스펙으로 오해하는 경우가 많다.

| 지정자 | 의미 | 허용 범위 |
| ----------- | ----------- | ----------- |
| `^1.2.3` | **왼쪽에서 첫 0이 아닌 자리를 고정** | `>=1.2.3 <2.0.0` |
| `^0.2.3` | 같은 규칙. 첫 0 아닌 자리가 MINOR | `>=0.2.3 <0.3.0` |
| `^0.0.3` | 첫 0 아닌 자리가 PATCH → **업데이트 없음** | `>=0.0.3 <0.0.4` |
| `~1.2.3` | MINOR 가 지정됐으면 **PATCH 만** | `>=1.2.3 <1.3.0` |
| `~1.2` | 같음 (`1.2.x`) | `>=1.2.0 <1.3.0` |
| `~1` | MINOR 가 없으면 **MINOR 까지** | `>=1.0.0 <2.0.0` |

`^` 의 정의가 "MAJOR 를 고정"이 아니라 **"왼쪽에서 첫 0이 아닌 자리를 고정"** 이라는 게 핵심이다. 이 한 문장이 2절의 0.x 관행을 그대로 반영한다 — node-semver 문서도 *"많은 저자가 0.x 의 x 를 파괴적 변경 표시자처럼 다룬다"* 고 근거를 밝힌다.

`~` 는 `^` 보다 보수적이라 기능 추가조차 받지 않는다. 반대로 `1.2.3` 처럼 그냥 고정하면 보안 패치도 안 들어온다. 실무에서는 **`^` 를 기본으로 두고 lockfile 로 실제 설치 버전을 고정**하는 조합이 정착했다 — 범위는 "받아들일 수 있는 폭", lockfile 은 "지금 실제로 쓰는 것"으로 역할이 갈린다.

## 4. 사전 배포와 빌드 메타데이터

```
1.0.0-alpha        1.0.0-alpha.1      1.0.0-rc.1        ← 사전 배포 (조항 9)
1.0.0+20130313144700          1.0.0-alpha+001         ← 빌드 메타데이터 (조항 10)
```

| 표기 | 구분자 | 우선순위에 영향? |
| ----------- | ----------- | ----------- |
| 사전 배포 | `-` 하이픈 | **있다.** 같은 `1.0.0` 이면 사전 배포가 **낮다** |
| 빌드 메타데이터 | `+` 플러스 | **없다.** 비교 시 **무시된다**(조항 10) |

둘 다 ASCII 영숫자와 하이픈만 쓸 수 있고, 숫자 식별자에 앞자리 0을 넣을 수 없다.

빌드 메타데이터가 우선순위에서 무시된다는 조항 10이 실무에서 함정을 만든다. **`1.0.0+build.1` 과 `1.0.0+build.2` 는 SemVer 상 같은 버전**이다. CI 빌드 번호를 여기에 넣으면 버전으로 구별되지 않고, 조항 3(배포된 버전은 수정 불가)과 부딪힌다. npm 레지스트리가 `+` 를 포함한 버전 발행을 사실상 안 쓰는 이유다.

사전 배포 우선순위는 `1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta < 1.0.0-rc.1 < 1.0.0` 순으로 흐른다. 즉 **사전 배포 버전은 항상 정식 버전보다 낮다.** `^1.0.0` 이 `1.1.0-beta.1` 을 잡아오지 않는 이유가 이것이다.

## 5. Conventional Commits 와 맞물리는 지점

[[Conventional Commits]] 는 "이 버전 증가를 누가 판단하는가"에 답을 준다.

```
fix:            →  PATCH
feat:           →  MINOR
! / BREAKING    →  MAJOR   (type 무관)
```

방향이 중요하다. **SemVer 는 "무엇을 올릴지"의 규칙이고, Conventional Commits 는 "그 판단을 어디서 읽을지"의 규칙이다.** 둘을 합치면 릴리스 시점에 사람이 개입할 자리가 없어진다 — 커밋 로그를 훑어서 셋 중 가장 높은 걸 고르면 끝이다.

다만 이 자동화는 **각 커밋의 type 이 정확했다는 가정 위에서만** 성립한다. 파괴적 변경인 줄 모르고 `fix` 로 올린 커밋 하나가 MAJOR 를 MINOR 로 만든다. 이 가정을 지키는 건 도구가 아니라 사람이라, 여기서 다음 절의 문제로 넘어간다.

### 장점

* **업그레이드 판단이 싸진다.** PATCH 는 그냥 올리고, MAJOR 는 릴리스 노트를 읽는다. 이 구분이 없으면 매번 diff 를 봐야 한다
* **의존성 범위를 기계가 해석할 수 있다.** `^` · `~` 와 lockfile 이 성립하는 전제
* **릴리스 자동화의 입력이 된다.** Conventional Commits + semantic-release 조합
* **공개 API 를 정의하도록 강제한다.** 조항 1의 부수 효과인데, 실제로는 이게 제일 값어치 있을 때가 많다

### 단점 · 한계

* **무엇이 파괴적인지는 주관적이다.** 이게 가장 큰 구멍이다. 버그를 고쳤는데 누군가 그 버그에 의존하고 있었다면 파괴적 변경인가? 오타를 고친 에러 메시지를 파싱하던 코드는? 타입 정의를 더 엄격하게 바꾼 건? **스펙은 "하위 호환"의 판정 기준을 정의하지 않는다.** semver.org FAQ 도 이 질문에 "신중히 생각하라"는 답 이상을 주지 않는다
* **공개 API 의 경계가 흐리면 규칙 전체가 무너진다.** 조항 1을 대충 넘긴 프로젝트에서 SemVer 는 그냥 숫자 세 개다
* **MAJOR 를 올리기 싫은 사회적 압력이 있다.** MAJOR 는 "생태계에 부담을 준다"는 인상을 줘서, 실제로는 파괴적인 변경이 MINOR 로 나가는 일이 흔하다. 규칙을 어기는 게 아니라 **판정을 유리하게 하는** 방식이라 잡기도 어렵다
* **0.x 에 오래 머무는 프로젝트가 많다.** `1.0.0` 을 내는 순간 조항 5에 따라 공개 API 를 확정해야 해서, 그 부담을 피하려고 0.x 를 유지한다. 그러면 규칙이 적용되지 않는 상태가 무한정 이어진다
* **애플리케이션에는 잘 안 맞는다.** 라이브러리와 달리 앱에는 "소비자가 참조하는 공개 API" 가 없다. 조항 1이 성립하지 않으니 나머지 조항도 해석할 근거가 없다 → 다음 절

## 6. 애플리케이션에서는 어떻게 하나

SemVer 는 **소비자가 있는 소프트웨어**를 위한 규약이다. 사내 앱·대시보드·백오피스처럼 배포 대상이 사람뿐이면 조항 1부터 성립하지 않는다.

이런 프로젝트가 흔히 쓰는 대안이 셋 있다.

| 방식 | 예 | 성격 |
| ----------- | ----------- | ----------- |
| **CalVer** (날짜 기반) | `2026.09.1` | 언제 나갔는지가 정보. 호환성 정보는 없음 |
| **빌드 번호 · 커밋 SHA** | `a3f19c2` | 추적만 필요할 때. 배포와 커밋을 1:1로 연결 |
| **버전 자체를 안 씀** | `0.0.0` | 항상 최신 하나만 돌 때 |

펫바디 클라이언트가 세 번째다. `package.json` 이 `"version": "0.0.0"` 에 `"private": true` 로, npm 에 발행하지 않는 앱이라 버전 필드가 아무 역할도 하지 않는다.

여기서 [[Conventional Commits]] 와의 관계가 흥미로워진다. SemVer 연동이 사라지면 `!` 와 `BREAKING CHANGE` 의 **원래 용도가 비게 된다.** 그 빈 슬롯을 팀에 실제로 중요한 다른 신호로 전용할 수 있는데, 펫바디에서는 **백엔드와의 API 계약이 깨지는 지점**을 표시하는 데 쓰는 안을 검토 중이다. **아직 팀 합의 전 초안**이다.

## 정리

* `MAJOR.MINOR.PATCH` = **호환 깨짐 / 호환되는 기능 추가 / 호환되는 버그 수정.** 아래 자리는 리셋
* 조항 1이 전제다 — **공개 API 를 선언하지 않으면 나머지 조항은 해석 불가**
* **`0.y.z` 는 규칙 적용 밖.** "0.x 는 MINOR 가 MAJOR 역할"은 스펙이 아니라 관행이고, npm 의 `^` 가 그 관행을 코드로 굳혔다
* **`^` · `~` 는 SemVer 스펙이 아니다.** npm 의 `node-semver` 범위 문법. `^` 는 "왼쪽 첫 0 아닌 자리를 고정"
* 사전 배포(`-`)는 우선순위에 **영향 있고**, 빌드 메타데이터(`+`)는 **무시된다**
* [[Conventional Commits]] 와 합치면 버전 결정이 커밋 로그의 함수가 된다. 단 **type 이 정확했다는 가정** 위에서만
* 가장 큰 구멍은 **"파괴적"의 판정이 주관적**이라는 것. 스펙에 기준이 없다
* **애플리케이션에는 안 맞는다.** 공개 API 가 없으면 CalVer 나 커밋 SHA 가 정직하다
