# 낙관적 업데이트(Optimistic Update)
----

서버 응답을 **기다리지 않고 성공했다고 가정해서** 화면을 먼저 바꾸는 기법. 실패하면 되돌린다.

"낙관적(optimistic)"인 이유는 **대부분의 요청은 성공한다**는 데 베팅하기 때문이다.

```
비관적:  클릭 ─▶ 스피너 ─▶ (200ms~2s) ─▶ 응답 ─▶ 화면 갱신
낙관적:  클릭 ─▶ 화면 즉시 갱신 ─▶ (백그라운드로 요청) ─▶ 실패하면 롤백
```

## 1. 왜 쓰는가

체감 지연이 사라진다. 하지만 진짜 이유는 심리적인 쪽에 가깝다.

* 사용자는 **자기 행동의 결과가 즉시 보일 때** 조작감을 느낀다. 200ms의 스피너도 "끊긴다"고 인지된다
* 스피너가 사라지면 **연속 조작**이 가능해진다. 알림 20건을 훑으며 처리하는 흐름에서 매번 기다리게 하면 작업 자체가 성립하지 않는다
* 낙관적 갱신이 없으면 개발자는 대신 **비활성화된 버튼**을 만들게 되고, 그게 더 나쁜 UX인 경우가 많다

## 2. 최소 구현 — 세 조각이 필요하다

```
1. 스냅샷(이전 상태 저장)  ← 롤백하려면 반드시 있어야 한다
2. 낙관적 반영
3. 실패 시 스냅샷으로 복구 / 성공 시 서버 값으로 정합
```

3번의 "성공 시에도 정합을 맞춘다"가 자주 빠진다. 낙관적으로 넣은 값은 **내가 추측한 값**이지 서버가 확정한 값이 아니다. 서버가 채운 `id`, `createdAt`, 서버 시간 기준 순서 같은 게 다르다. 그래서 성공한 뒤에도 서버 응답으로 덮거나 재조회해야 한다.

[[TanStack Query]]는 이 세 조각을 `onMutate` / `onError` / `onSettled` 로 나눠 제공한다.

## 3. 어디에 쓰고 어디에 안 쓰는가

판단 기준은 **"실패했을 때 되돌리는 게 사용자에게 납득되는가"** 다.

| 적합 | 이유 |
| ----------- | ----------- |
| 좋아요 · 북마크 · 읽음 처리 | 실패해도 손해가 없고 되돌려도 자연스럽다 |
| 알림 확인/무시 | 실패율이 낮고 되돌림이 이해 가능 |
| 목록 순서 바꾸기, 체크박스 | 결과가 뻔하다 |

| 부적합 | 이유 |
| ----------- | ----------- |
| 결제 · 송금 | 실패 롤백이 **신뢰를 깨뜨린다.** "됐다"고 보였다가 취소되면 안 된다 |
| 삭제 (복구 불가) | 되돌릴 대상이 사라진 뒤라 롤백이 위험 |
| 서버가 값을 **계산해서** 돌려주는 작업 | 무엇을 낙관적으로 넣을지 알 수 없다 (예: 서버가 배정하는 번호) |
| 실패율이 높은 요청 | 롤백이 자주 보이면 화면이 튀어 오히려 불안하다 |

> 애매하면 **"실패했을 때 화면이 되돌아가는 걸 사용자가 봐도 괜찮은가"** 를 물어라. 아니면 비관적으로 가고 대신 응답을 빠르게 만드는 게 맞다.

## 4. 함정

### 롤백 대상이 그 사이 바뀌어 있다
스냅샷을 찍은 뒤 응답이 오기 전에 **다른 갱신(다른 뮤테이션, 실시간 델타)** 이 들어오면, 실패 시 그 스냅샷으로 되돌리는 순간 **그 사이의 변경까지 지워진다.** 낙관적 업데이트의 가장 흔한 데이터 손실 경로다.

→ 통째로 스냅샷을 되돌리는 대신 **내가 바꾼 항목만 되돌리는** 편이 안전하다.

### 진행 중 재조회가 낙관적 값을 덮는다
낙관적으로 바꿔둔 캐시를, 마침 돌아온 이전 요청의 응답이 덮어써서 **화면이 잠깐 되돌아갔다가 다시 바뀐다.** 그래서 낙관적 반영 전에 **해당 쿼리의 진행 중 요청을 취소**해야 한다(`cancelQueries`).

### 동시 뮤테이션의 순서
같은 대상에 두 번 연속 요청하면 응답 순서가 뒤바뀔 수 있다. 마지막 요청 결과가 최종이 되도록 직렬화하거나, 뮤테이션 키로 큐를 만들어야 한다.

### 오프라인·재연결
요청이 큐에 쌓였다가 나중에 나가면 **낙관적 상태로 오래 머문다.** "저장 중"임을 알려주지 않으면 사용자는 이미 저장된 줄 안다.

### 되돌림을 사용자가 눈치채야 한다
조용히 롤백하면 사용자는 **자기가 한 조작이 반영된 줄 안다.** 실패는 반드시 토스트 등으로 알린다. 낙관적 업데이트에서 에러 처리를 생략하면 [[불변성(Immutability)]] 위반과 같은 종류의 사고가 난다 — 에러 없이 값만 틀린 상태.

## 5. 실시간 데이터와 겹칠 때

SSE 같은 푸시 채널이 같이 있으면 한 항목에 대해 **낙관적 값 · 서버 응답 · 델타 푸시** 세 출처가 경쟁한다.

```
클릭 ─▶ 낙관적 반영 (내 추측)
     ─▶ 200 응답     (서버 확정값)
     ─▶ SSE 델타      (같은 변경이 푸시로 또 온다)
```

같은 변경이 두 번 반영돼 **카운트가 2 늘어나는** 식의 버그가 여기서 나온다. 해법은 **모든 갱신이 같은 캐시를 거치게 하고, 항목 id 기준으로 병합(upsert)** 하는 것. 배열에 append하는 방식이면 반드시 중복이 생긴다. 이 구조는 [[SSE vs WebSocket]]과 [[TanStack Query]]에 정리했다.

## 정리

* 서버를 기다리지 않고 **성공을 가정해 먼저 반영**하고, 실패하면 되돌린다
* **스냅샷 → 반영 → 롤백/정합** 세 조각이 다 있어야 한다. 성공 시 정합을 빠뜨리기 쉽다
* 판단 기준은 **"실패 롤백이 사용자에게 납득되는가"** — 결제·삭제엔 쓰지 않는다
* 반영 전에 **진행 중 요청을 취소**하지 않으면 화면이 튄다
* 롤백은 통째로가 아니라 **내가 바꾼 것만**
* 실시간 푸시와 겹치면 **id 기준 병합**으로 중복을 막을 것
