# 클라이언트 사이드 렌더링(CSR)
----

서버는 **거의 빈 HTML과 JS 번들만** 보내고, 브라우저가 JS를 실행해 화면을 그리는 방식.

```html
<!-- 서버가 보내는 HTML -->
<body>
  <div id="root"></div>          <!-- 비어 있음 -->
  <script src="/bundle.js"></script>
</body>
```

브라우저가 `bundle.js` 를 받아 실행하면 그때 `#root` 안이 채워진다. [[싱글 페이지 애플리케이션(SPA)]] 의 기본 렌더링 방식이다.

```
브라우저 ──요청──▶ 서버
브라우저 ◀─빈 HTML + JS──┘
   │ JS 다운로드 (여기까지 흰 화면)
   │ JS 실행 → 데이터 요청 → DOM 생성
   └ 화면 표시
```

### 장점
* **서버가 단순하다** — 정적 파일만 서빙하면 됨. CDN에 얹으면 끝
* 초기 로드 이후 **화면 전환이 빠름** — 서버 왕복 없이 JS가 바꿔치기
* 프론트/백 완전 분리 — 백엔드는 API만 제공
* 배포가 간단하고 저렴 (서버 런타임 불필요)

### 단점
* **첫 화면까지 흰 화면** — JS 다운로드 + 실행 + 데이터 요청을 다 기다려야 함
* **SEO에 불리** — 크롤러가 빈 HTML을 볼 수 있음
* 번들이 커질수록 초기 로딩이 선형으로 나빠짐 → 코드 스플리팅 필요
* 저사양 기기에서 렌더링 부담이 클라이언트에 몰림

## SSR과의 관계

CSR과 [[서버 사이드 렌더링(SSR)]] 은 배타적이지 않다. 실무에서는 섞는다.

* 공개 페이지는 SSR, 로그인 뒤 대시보드는 CSR
* 첫 요청만 SSR로 그리고 이후 화면 전환은 CSR ([[하이드레이션(Hydration)]] 이후)

## 언제 CSR로 충분한가

* 로그인 게이트 뒤의 내부 도구 → SEO 무관
* 실시간 데이터가 계속 갱신되는 화면 → 서버가 그려줘도 금방 무의미
* 백엔드 API 서버가 이미 따로 있는 경우

이 조건이면 굳이 SSR을 얹어 배포 대상을 늘릴 이유가 없다.
