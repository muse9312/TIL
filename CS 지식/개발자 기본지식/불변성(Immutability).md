# 불변성(Immutability)
----

**한 번 만든 값을 고치지 않고, 바꿀 때는 새 값을 만드는** 원칙. 원본은 그대로 두고 사본을 만든다.

```js
const a = { level: 'warn' };

a.level = 'urgent';              // ❌ 변경(mutation) — a는 그대로 a
const b = { ...a, level: 'urgent' };  // ✅ 새 객체 — a !== b
```

프론트엔드에서 이게 규율이 아니라 **동작 조건**인 이유가 있다.

## 1. 왜 필요한가 — 변경 감지를 참조로 하기 때문

React·[[zustand]]·[[TanStack Query]]는 "이 값이 바뀌었나"를 판단할 때 **내용을 비교하지 않는다.** `Object.is` 로 **참조만** 비교한다.

```js
prev === next  →  "안 바뀜"  →  리렌더 안 함
```

이유는 성능이다. 이벤트 5000개짜리 배열의 내용을 매 렌더마다 전부 비교하면, 비교 비용이 렌더 비용을 넘는다. 참조 비교는 **O(1)** 이고, 그 대가로 "값을 바꿀 땐 참조도 바꾼다"는 규칙을 개발자가 지켜야 한다.

이 규칙을 어기면 이렇게 된다.

```js
// ❌ 원본을 직접 밀어넣음 — 배열 참조가 그대로다
push: (e) => set((s) => { s.events.push(e); return { events: s.events }; })
//                                                     ↑ prev === next → 화면이 안 바뀐다
```

**에러가 안 난다.** 데이터는 분명히 늘었는데 화면만 갱신되지 않는다. 불변성 위반 버그가 잡기 어려운 이유다.

## 2. 얕은 비교(shallow equality)

참조 비교의 한 단계 완화판. **객체의 1단계 속성들만** `Object.is` 로 비교한다.

```js
shallowEqual({ a: 1, b: 2 }, { a: 1, b: 2 })          // true  — 값은 다르지만 1단계가 같다
shallowEqual({ a: { x: 1 } }, { a: { x: 1 } })        // false — a의 참조가 다르다
```

`React.memo` 의 props 비교, [[zustand]]의 `useShallow`, `useEffect` 의 의존성 배열이 전부 이 규칙이다.

여기서 나오는 결론 하나. **selector가 매번 새 객체를 만들면 얕은 비교도 소용없다** — 정확히는 얕은 비교를 명시적으로 걸어야 산다.

```ts
// ❌ 매 렌더 새 객체 → 참조가 늘 달라 항상 리렌더
useStore((s) => ({ urgent: s.byLevel.urgent }))
// ✅
useStore(useShallow((s) => ({ urgent: s.byLevel.urgent })))
```

### 얕은 비교의 함정 — 중첩된 곳만 갈아끼워야 한다
불변 갱신은 **바뀐 경로 위의 모든 조상을 새로 만들어야** 한다. 하나라도 빠뜨리면 그 지점에서 감지가 끊긴다.

```js
// ✅ 경로 전체를 새로
set((s) => ({
  filters: { ...s.filters, zone: { ...s.filters.zone, id: next } },
}));
```

중첩이 3단계만 넘어가도 이 코드는 읽기 힘들어진다. 이게 immer가 푸는 문제다.

## 3. immer — mutable하게 쓰고 불변으로 받기

immer는 **Proxy로 감싼 초안(draft)** 을 준다. 초안에는 마음대로 써도 되고, 끝나면 immer가 **바뀐 경로만 새로 만든 새 객체**를 내놓는다.

```ts
import { produce } from 'immer';

const next = produce(state, (draft) => {
  draft.filters.zone.id = 'playroom-1';   // 그냥 대입한다
  draft.events.push(e);                    // push도 된다
});
// state는 그대로, next는 새 객체. 안 건드린 가지는 참조를 공유한다
```

immer가 실제로 해결하는 건 두 가지다.

* **스프레드 지옥 제거** — 중첩 갱신의 가독성
* **구조적 공유(structural sharing)** — 바뀐 경로만 새로 만들고 **나머지는 참조를 그대로 재사용**한다. 손으로 짜면 무심코 전체를 복사하기 쉬운데, 그러면 안 바뀐 가지의 참조까지 달라져 불필요한 리렌더가 퍼진다

[[zustand]]의 `immer` 미들웨어, Redux Toolkit의 `createSlice` 가 내부에서 쓰는 게 이것이다.

### 장점
* 깊은 갱신이 **읽히는 코드**가 된다
* 실수로 원본을 변경할 수 없다 (Proxy가 막는다)
* 구조적 공유가 자동

### 단점 · 함정
* **Proxy 오버헤드**가 있다. 얕은 갱신 한 줄에 쓰면 손해
* **draft를 밖으로 들고 나가면 안 된다.** `produce` 가 끝난 draft는 revoke돼 접근 시 터진다 (비동기 콜백에 넘기는 실수가 잦다)
* producer 안에서 **draft를 수정하면서 동시에 새 값을 return하면 안 된다.** 둘 중 하나만
* 클래스 인스턴스·`Map`/`Set` 은 기본적으로 draft 대상이 아니다 (`enableMapSet()` 필요)
* 디버깅 시 콘솔에 Proxy가 찍혀 낯설다

## 4. 언제 쓰고 언제 안 쓰나

| 상황 | 방법 |
| ----------- | ----------- |
| 1단계 속성 갱신 | 스프레드로 충분 — `{ ...s, level }` |
| 배열에 추가/제거 | `[...arr, x]` / `arr.filter(...)` |
| 3단계 이상 중첩 | **immer** |
| 대량 갱신을 반복 | immer (매번 전체 복사보다 낫다) |
| 상태 구조가 애초에 깊다 | **구조를 평탄화하는 걸 먼저 고민할 것** |

마지막 줄이 핵심이다. immer는 깊은 중첩의 **증상**을 완화하지, 원인을 없애지 않는다. 상태를 정규화해 평탄하게 만들면 immer 없이도 깨끗해지는 경우가 많다.

### 최신 JS의 불변 메서드
ES2023부터 배열에 복사본을 반환하는 메서드가 생겼다. 짧은 경우엔 이쪽이 더 낫다.

```js
arr.toSorted(fn)     // sort는 원본을 바꾼다 ← 대표적인 사고 지점
arr.toReversed()
arr.toSpliced(0, 1)
arr.with(2, next)
```

`sort` · `reverse` · `splice` · `push` 는 **원본을 바꾸는 메서드**다. 상태 배열에 그대로 쓰면 안 된다.

## 정리

* 불변성은 취향이 아니라 **참조 비교로 변경을 감지하는 구조의 전제 조건**이다
* 위반하면 에러가 아니라 **"화면이 안 바뀐다"** 로 나타난다. 그래서 잡기 어렵다
* 바뀐 경로 **위의 모든 조상**을 새로 만들어야 한다
* 얕은 비교는 1단계만 본다 — selector가 새 객체를 만들면 `useShallow` 를 걸 것
* immer는 **깊은 갱신의 가독성 + 구조적 공유**를 준다. 얕은 갱신에 쓰면 오버헤드만
* `sort` · `push` 등 **원본을 바꾸는 메서드**를 상태에 직접 쓰지 말 것
