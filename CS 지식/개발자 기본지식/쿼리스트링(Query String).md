# 쿼리스트링(Query String)
----

URL에서 `?` 뒤에 붙는 **키=값** 목록. 서버나 화면에 부가 조건을 전달한다.

```
https://example.com/stores/12/alerts?level=urgent&zone=playroom-1&range=6h
                                     └────────── 쿼리스트링 ──────────┘
```

* `?` 로 시작, `&` 로 구분, `=` 로 키와 값을 연결
* 같은 키를 여러 번 쓸 수 있다 — `?tag=a&tag=b` (배열 표현)
* 값에 특수문자가 있으면 **퍼센트 인코딩** — `encodeURIComponent()`

## 경로 파라미터와의 차이

| | 경로 파라미터 | 쿼리스트링 |
| ----------- | ----------- | ----------- |
| 형태 | `/stores/12/alerts` | `?level=urgent` |
| 의미 | **무엇을** 보는가 (리소스 식별) | **어떻게** 보는가 (필터·정렬·페이징) |
| 필수성 | 없으면 리소스가 특정 안 됨 | 없어도 기본값으로 동작해야 함 |
| 순서 | 의미 있음 | 의미 없음 |

> 구분 기준: **빼도 페이지가 성립하면 쿼리스트링**, 빼면 무엇을 볼지 알 수 없으면 경로 파라미터.

## URL을 상태 저장소로 쓴다는 발상

[[싱글 페이지 애플리케이션(SPA)]] 에서 필터·정렬·탭 같은 UI 상태를 어디 둘 것인가. 메모리(useState)에 두면 편하지만:

* 새로고침하면 **날아간다**
* 링크를 공유해도 **상대는 다른 화면**을 본다
* 뒤로가기를 눌러도 이전 필터로 안 돌아간다

이걸 URL에 담으면 전부 해결된다. **URL이 곧 화면의 스냅샷**이 된다.

```
/stores/12/alerts?level=urgent&range=6h
```

이 링크를 슬랙에 붙여넣으면, 받은 사람이 정확히 같은 화면을 본다. 관제 대시보드처럼 "이 상황 좀 봐줘"가 잦은 도구에서 특히 값어치가 크다.

### 장점
* 공유·북마크·새로고침에 강함
* 뒤로가기/앞으로가기가 **공짜로** 동작 (브라우저 히스토리가 상태 히스토리가 됨)
* 서버에도 그대로 전달 가능 — SSR이든 API든

### 단점
* **길이 제한**이 있다 (브라우저·서버마다 다르지만 대략 2000자 안팎)
* **민감 정보를 담으면 안 된다** — 서버 접근 로그, 리퍼러 헤더, 브라우저 히스토리에 그대로 남는다
* 타입이 없다. 전부 문자열이라 파싱·검증이 필요
* 상태가 많아지면 URL이 흉해짐

## 타입 안전하게 다루기

쿼리스트링은 문자열이라 `?range=6h` 를 읽으면 `"6h"` 라는 string이 온다. 잘못된 값(`?range=banana`)이 와도 런타임에야 터진다.

그래서 **스키마로 검증하고 타입을 추론**해주는 라우터를 쓰면 편하다. [[TanStack Router]]가 이걸 강점으로 내세운다 — search params를 zod 같은 스키마로 정의하면 파싱·검증·기본값·타입 추론이 한 번에 해결된다.

```ts
validateSearch: (s) => ({
  level: s.level ?? 'all',      // 기본값
  range: Number(s.range) || 6,  // 타입 변환
})
```

## 무엇을 URL에 둘까

**두는 게 좋은 것** — 필터, 정렬, 검색어, 페이지 번호, 선택된 탭, 시간 범위
**두면 안 되는 것** — 토큰·비밀번호, 대용량 데이터, 매 프레임 바뀌는 값(스크롤 위치 등)
**애매한 것** — 모달 열림 여부. 뒤로가기로 닫히길 원하면 URL에, 아니면 로컬 상태로

URL은 상태를 둘 수 있는 여러 자리 중 하나일 뿐이다. 어디에 둘 것인가의 더 넓은 이야기는 [[상태 관리]]에, 무엇으로 다룰 것인가는 [[서버 상태 vs 클라이언트 상태]]에 있다.
