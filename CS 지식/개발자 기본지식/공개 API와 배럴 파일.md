# 공개 API와 배럴 파일
----

모듈이 **밖에 보여줄 것만 골라 한 곳으로 내보내는** 패턴. JS/TS에서는 폴더마다 `index.ts`를 두는 형태로 나타나고, 이 `index.ts`를 **배럴 파일(barrel file)** 이라 부른다.

```ts
// entities/alert/index.ts  ← 배럴 = 이 슬라이스의 공개 API
export { AlertBadge } from './ui/AlertBadge';
export { useAlerts } from './model/useAlerts';
export type { Alert } from './model/types';
// ui/AlertRow, lib/formatLevel 은 내보내지 않는다 = 내부 구현
```

```ts
// 사용하는 쪽
import { AlertBadge, type Alert } from '@/entities/alert';   // ✅
import { AlertRow } from '@/entities/alert/ui/AlertRow';     // ❌ 내부를 찔렀다
```

## 1. 왜 쓰는가 — 캡슐화

폴더를 나누는 것만으로는 경계가 안 생긴다. **아무나 폴더 안쪽 파일을 직접 import할 수 있으면 그 폴더는 그냥 파일 서랍**이다. 공개 API를 정하고 그 밖을 못 쓰게 해야 비로소 경계가 된다.

### 장점
* **내부를 자유롭게 고칠 수 있다.** `index.ts`가 유지되면 안쪽 파일을 쪼개든 이름을 바꾸든 밖이 안 깨진다. 리팩터링의 반경이 폴더 안으로 제한된다
* **의존 그래프가 폴더 단위로 단순해진다.** `A → B/index` 하나만 보면 되고, 파일 수십 개 사이의 실선이 사라진다
* **의도가 문서가 된다.** `index.ts`만 읽으면 이 모듈이 무엇을 제공하는지 안다
* **경로가 짧고 안정적**이다. `@/entities/alert/model/hooks/useAlerts` 대신 `@/entities/alert`

공개 API 를 정하는 일은 폴더 경계에서만 필요한 게 아니다. [[시맨틱 버저닝(SemVer)]]의 첫 조항도 "공개 API 를 반드시 선언해야 한다"인데, 무엇이 공개인지 정해지지 않으면 "호환이 깨졌다"는 판정 자체가 불가능하기 때문이다. 같은 문제를 폴더 안에서 푸느냐 패키지 밖에서 푸느냐의 차이일 뿐이다.

[[Feature-Sliced Design(FSD)]]가 슬라이스마다 `index.ts`를 요구하는 이유가 이것이다. 같은 층 슬라이스 간 import 금지 같은 규칙도, 접점이 `index.ts` 하나로 모여야 린터가 검사할 수 있다.

## 2. 성능 함정 — 여기가 진짜 중요하다

배럴 파일은 **공짜가 아니다.** 오히려 대규모 프로젝트에서 개발 경험을 망치는 대표적 원인으로 지목된다.

### 왜 느려지는가

```ts
// shared/ui/index.ts
export * from './Button';
export * from './Table';
export * from './Chart';      // recharts를 끌고 옴
export * from './DatePicker'; // date-fns를 끌고 옴
// ... 60개
```

```ts
import { Button } from '@/shared/ui';   // 버튼 하나만 쓰고 싶다
```

이 한 줄에 번들러/개발 서버는 **`index.ts`가 참조하는 60개 모듈을 전부 로드하고 파싱**한다. 그 60개가 각자 또 배럴을 참조하면 눈덩이가 된다.

* **개발 서버가 느려진다.** Vite 같은 네이티브 ESM 개발 서버는 브라우저가 요청하는 모듈을 그때그때 변환하는데, 배럴 하나가 요청 수백 개로 번진다. HMR도 같이 느려진다
* **`optimizeDeps` 사전 번들링이 커진다.** 첫 실행과 의존성 변경 시 대기 시간이 는다
* **테스트가 느려진다.** 한 파일을 테스트하는데 배럴을 타고 앱 절반이 로드된다. 여기서 가장 체감이 크다
* **[[트리 셰이킹]]에 기대기 어렵다.** 프로덕션 빌드에서는 대개 잘 제거되지만, 사이드 이펙트가 있는 모듈이 섞이면 못 지운다. `package.json`의 `sideEffects: false` 같은 신호가 없으면 번들러는 보수적으로 남긴다
* **[[코드 스플리팅]] 경계가 뭉개진다.** 청크가 의도와 다르게 합쳐진다

### 무엇이 특히 나쁜가

| | 영향 |
| ----------- | ----------- |
| `export * from './X'` | **가장 나쁨.** 무엇이 나가는지 정적으로 좁힐 수 없어 전부 로드 |
| 명시적 `export { A } from './X'` | 낫다. 그래도 파일 자체는 평가됨 |
| `export type { T }` / `import type` | **비용 없음.** 컴파일 후 사라진다 |
| 배럴 안에서 또 배럴 참조 | 눈덩이. 깊이만큼 곱해진다 |

`export *` 를 쓰지 않는 것만으로도 상당 부분이 해결된다.

### 순환 참조도 여기서 생긴다
같은 폴더 안의 파일이 배럴을 거쳐 형제를 import하면(`import { x } from '..'`) 자기 자신을 포함한 순환이 만들어진다. **모듈 내부에서는 배럴을 쓰지 말고 상대 경로로 직접 참조**해야 한다 → [[단방향 의존성]]

```ts
// entities/alert/ui/AlertBadge.tsx
import { formatLevel } from '..';            // ❌ 배럴 경유 → 순환
import { formatLevel } from '../lib/format'; // ✅ 직접
```

## 3. 그래서 언제 쓸 가치가 있는가

핵심은 **배럴의 크기와 층위**다. 배럴 자체가 나쁜 게 아니라 **큰 배럴**이 나쁘다.

| 상황 | 판단 |
| ----------- | ----------- |
| 도메인 모듈 하나의 입구 (`entities/alert/index.ts`, 5~15개 export) | **쓸 가치 있음.** 캡슐화 이득이 크고 크기가 작다 |
| 라이브러리·패키지의 진입점 | **필수.** 공개 API를 정의하는 게 목적 |
| 앱 최상위 통합 배럴 (`src/index.ts`) | **쓰지 말 것.** 얻는 게 없다 |
| `shared/ui/index.ts`에 컴포넌트 60개 | **위험.** 층을 나누거나 배럴을 없애라 |
| `utils/index.ts`에 잡다한 함수 전부 | **없애라.** 직접 경로가 낫다 |

실용적인 규칙 몇 개.

* **`export *` 대신 명시적 재export.** 이것 하나가 제일 값이 싸고 효과가 크다
* **배럴은 슬라이스/모듈 단위 한 층만.** 배럴이 배럴을 참조하기 시작하면 멈춰야 한다
* **`shared`처럼 큰 층은 배럴을 쪼갠다.** `shared/ui/index.ts` 하나 대신 `shared/ui/button/index.ts` 식으로
* **타입 전용은 `export type`으로 명시.** 런타임 비용이 0이 된다
* **모듈 내부에서는 배럴을 경유하지 않는다**

### 균형점
공개 API의 이득(경계·리팩터링 자유)은 **모듈이 커질수록** 커지고, 배럴의 비용은 **export가 많아질수록** 커진다. 둘이 만나는 지점은 대체로 **"하나의 도메인 개념, export 10개 안팎"** 이다. 그보다 커졌다면 배럴이 문제가 아니라 **그 모듈이 너무 많은 일을 하고 있다**는 신호다 → [[응집도와 결합도]]

## 정리

* 배럴 파일 = **폴더의 공개 API.** 밖에 보일 것만 내보내고 나머지는 내부 구현으로 감춘다
* 이득은 **경계 · 리팩터링 자유 · 단순한 의존 그래프.** FSD가 슬라이스마다 요구하는 이유
* 대가는 **개발 서버 · 테스트 속도**. import 한 줄이 모듈 수십 개 로드로 번진다
* **`export *` 를 쓰지 마라.** 가장 값싼 개선
* **모듈 안에서는 배럴을 경유하지 마라.** 순환 참조의 흔한 원인
* 작고 도메인 단위인 배럴은 이득, **크고 잡다한 통합 배럴은 순손해**
