# 라이브러리
----

특정 기능을 모아둔 재사용 가능한 코드 묶음. **내가 필요할 때 호출해서 쓰는 도구.**

## 프레임워크와의 차이 — 제어의 역전

둘 다 "남이 만든 재사용 코드"인데, 갈리는 지점은 딱 하나다.

> **누가 누구를 호출하는가.**

| | [[라이브러리]] | [[프레임워크]] |
| ----------- | ----------- | ----------- |
| 제어권 | **내가** 가짐 | **프레임워크가** 가짐 |
| 호출 방향 | 내 코드 → 라이브러리 | 프레임워크 → 내 코드 |
| 비유 | 공구함에서 꺼내 쓴다 | 정해진 공정 라인에 내 부품을 끼운다 |
| 예 | React, lodash, axios | Next.js, Spring, Django |

이걸 **제어의 역전(IoC, Inversion of Control)** 이라 부른다. 프레임워크는 "이 시점에 이 함수를 부를 테니 너는 그 자리를 채워라"고 요구한다. 라이브러리는 그런 요구가 없다.

## 판별법

- 내가 흐름을 짜고 **필요할 때 부른다** → 라이브러리
- **틀이 먼저 있고** 그 안 빈칸을 내가 채운다 → 프레임워크

React가 대표적인 헷갈림 지점이다. React는 [[라이브러리]]로 분류된다 — 렌더링만 담당하고 라우팅·데이터 페칭·빌드는 내가 고른다. 반면 Next.js는 [[프레임워크]]다. 폴더 구조가 라우팅을 결정하고, [[서버 사이드 렌더링(SSR)]] 여부를 프레임워크가 정한 규칙에 따라 선언한다.

### 장점
* 필요한 것만 골라 쓸 수 있음 — 조합의 자유
* 학습 범위가 좁음
* 갈아끼우기 쉬움 (axios → fetch)

### 단점
* 선택지가 많아 **결정 비용**이 큼 (라우터 뭐 쓸지, 상태관리 뭐 쓸지)
* 팀마다 구성이 달라져 표준화가 어려움
* 조합의 정합성을 내가 책임져야 함

## 경계가 흐려질 때

라이브러리를 여러 개 조합하면 사실상 프레임워크처럼 굳어진다. React + 라우터 + [[상태 관리]] + 빌드 도구를 정해놓고 팀 규약으로 쓰면, 그 조합 자체가 프레임워크 역할을 한다.

그래서 실무에서는 "이건 라이브러리다/프레임워크다"보다 **"제어권을 얼마나 내주고 얼마나 쥘 것인가"** 로 생각하는 게 유용하다.
