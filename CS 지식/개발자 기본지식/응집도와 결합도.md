# 응집도와 결합도
----

**응집도(cohesion)** 는 한 모듈 안의 요소들이 얼마나 한 가지 일에 모여 있는가, **결합도(coupling)** 는 모듈들이 서로 얼마나 얽혀 있는가.

목표는 항상 같다. **높은 응집도, 낮은 결합도.** 폴더 구조·모듈 분리·아키텍처 논쟁은 전부 이 두 단어의 각주다.

## 1. 왜 이게 목표인가

교과서적인 답("유지보수성") 말고 실제 이유는 하나다.

> **변경이 얼마나 멀리 번지는가.**

* **응집도가 낮으면** — 한 가지를 고치려고 여러 곳을 연다. 관련 코드가 흩어져 있어서 그렇다. 고칠 곳을 하나 빠뜨리기도 쉽다
* **결합도가 높으면** — 한 곳을 고쳤는데 관계없어 보이는 데가 깨진다. 무엇이 깨질지 미리 알 수 없다

둘 다 결국 **"이 변경의 영향 범위를 예측할 수 있는가"** 로 수렴한다. 예측 가능하면 고칠 수 있고, 예측 불가능하면 아무도 안 건드린다. 코드가 굳는 건 복잡해서가 아니라 **무서워서**다.

### 응집도의 실용적 정의
> **같이 바뀌는 것은 같이 둔다. 따로 바뀌는 것은 따로 둔다.**

"관련 있는 것"이 아니라 **"같이 바뀌는 것"** 이 기준이다. 개념적으로 관련 있어 보여도 변경 이유가 다르면 나눠야 한다. 알람 표시 로직과 알람 저장 로직은 같은 "알람"이지만, 디자인 변경과 스키마 변경은 서로 다른 이유로 일어난다.

이 기준을 폴더에 적용하면 기술별 분류(`components/`·`hooks/`·`api/`)가 왜 무너지는지 바로 보인다 → [[폴더 구조 전략]]

## 2. 결합도의 종류 — 다 같은 결합이 아니다

느슨한 것부터.

| 종류 | 형태 | 얼마나 나쁜가 |
| ----------- | ----------- | ----------- |
| **데이터 결합** | 필요한 값만 인자로 넘김 | 가장 좋음. 목표 지점 |
| **스탬프 결합** | 객체 통째로 넘기고 일부만 씀 | 보통. 안 쓰는 필드까지 알게 됨 |
| **제어 결합** | 불리언 플래그로 상대 동작을 조종 | 나쁨. `render(true)`가 뭔지 알 수 없다 |
| **공통 결합** | 전역 변수·전역 스토어를 공유 | 나쁨. 누가 언제 바꿨는지 추적 불가 |
| **내용 결합** | 상대의 내부 구현에 직접 손댐 | 최악. 상대를 못 고치게 됨 |

```ts
// ❌ 제어 결합 — 호출부가 내부 분기를 알고 조종한다
formatAlert(alert, true, false);

// ✅ 데이터 결합 — 필요한 것만, 의미가 이름에 있다
formatAlert({ level: alert.level, at: alert.detectedAt });
```

**전역 상태가 결합도 관점에서 위험한 이유**도 여기 있다. 공통 결합은 모듈 목록에 안 나타나서, 의존 그래프를 그려도 안 보인다 → [[전역 상태와 지역 상태]]

### 결합을 0으로 만들 수는 없다
모듈이 서로 아무것도 모르면 프로그램이 동작하지 않는다. **줄이는 게 아니라 방향을 정하는 것**이 실제 목표다. A와 B가 서로 알면 둘 다 못 고치지만, A만 B를 알면 B는 자유롭다 → [[단방향 의존성]]

## 3. 흔한 착각

### ① 파일을 잘게 쪼개면 결합도가 낮아진다?
아니다. **쪼개기만 하면 결합도는 그대로고 응집도만 떨어진다.** 100줄 함수를 10줄짜리 열 개로 나눠도 서로를 다 부르면 얽힘은 똑같고, 대신 읽을 때 파일 열 개를 오가야 한다.

쪼개는 게 의미가 있으려면 **자르는 선이 변경 이유와 일치**해야 한다.

### ② 중복을 없애면 항상 좋다?
공통 함수로 묶는 순간 **거기 의존하는 모든 곳이 결합된다.** 한 곳의 요구사항이 바뀌면 플래그가 하나 붙고, 그게 반복되면 아무도 못 고치는 공통 함수가 된다.

> **우연히 같은 코드**와 **본질적으로 같은 코드**는 다르다. 전자를 묶으면 나중에 반드시 찢어야 한다.

성급한 추상화가 중복보다 비싸다는 게 실무의 일반적 결론이다. 두 번째 등장에서는 참고, **세 번째에 묶어라.**

### ③ 응집도와 결합도는 항상 같이 좋아진다?
대체로 그렇지만 **직접 충돌하는 지점**이 있다. 응집도를 위해 관련 코드를 한 모듈에 모으면 그 모듈이 커지고, 커진 모듈은 더 많은 곳에서 참조돼 결합의 허브가 된다. 이때 필요한 게 **모듈 안쪽을 감추는 것** — 밖에서 보이는 면을 줄이면 커진 모듈도 결합을 늘리지 않는다 → [[공개 API와 배럴 파일]]

## 4. 어떻게 알아채는가

숫자로 재기 어려운 개념이라 **징후로 판단**한다.

| 징후 | 무엇을 의미하나 |
| ----------- | ----------- |
| 한 기능을 고치는데 파일 5개를 연다 | 응집도 낮음 |
| 관계없어 보이는 테스트가 깨진다 | 결합도 높음 |
| 이 파일 하나를 테스트하려는데 절반을 mock해야 한다 | 결합도 높음 |
| 기능을 지우고 싶은데 뭐가 딸려 있는지 모른다 | 경계 없음 |
| "여기 건드리면 뭐가 터질지 모른다"는 말이 나온다 | 둘 다 나쁨 |
| import 목록이 화면을 넘어간다 | 응집도 낮음 (그 파일이 너무 많은 일을 함) |

**테스트가 가장 정직한 지표다.** 단위 테스트를 쓰기 어렵다면 거의 항상 결합도 문제고, 테스트 코드가 실제 설계 결함을 먼저 알려주는 셈이다.

## 정리

* **높은 응집도 = 같이 바뀌는 것이 같이 있다**, **낮은 결합도 = 변경이 멀리 번지지 않는다**
* 진짜 목표는 **영향 범위의 예측 가능성**. 예측 못 하면 아무도 안 고친다
* 응집의 기준은 "관련 있음"이 아니라 **"같이 바뀜"**
* 결합은 없앨 수 없다. **방향을 정하는 것**이 현실적인 목표 → [[단방향 의존성]]
* **쪼개기 ≠ 결합도 감소**, **중복 제거 ≠ 항상 이득.** 성급한 추상화가 중복보다 비싸다
* 판별은 **테스트가 쓰기 쉬운가**로. 여기가 가장 정직하다
