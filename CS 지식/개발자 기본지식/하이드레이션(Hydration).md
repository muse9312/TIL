# 하이드레이션(Hydration)
----

서버가 그려 보낸 **정적 HTML에 JS를 붙여 상호작용이 가능한 상태로 만드는** 과정.

"수분을 공급한다(hydrate)"는 비유다. 서버가 보낸 HTML은 **말라 있는 껍데기** — 보이긴 하지만 클릭해도 아무 일이 안 일어난다. 여기에 JS가 이벤트 핸들러와 상태를 주입하면 살아난다.

```
① 서버가 HTML 생성 ──▶ 화면은 보이지만 클릭 안 됨
② JS 번들 다운로드
③ 하이드레이션 — 기존 DOM에 이벤트·상태 연결
④ 상호작용 가능
```

[[서버 사이드 렌더링(SSR)]] 과 [[정적 사이트 생성(SSG)]] 에서 반드시 따라오는 단계다.

## 왜 문제가 되나

### 1. Uncanny Valley 구간
①과 ④ 사이에 **"보이는데 안 눌리는"** 시간이 생긴다. 사용자는 화면이 다 떴다고 생각하고 버튼을 누르는데 반응이 없다. 체감 품질이 나빠지는 대표적 구간.

### 2. 하이드레이션 불일치 (Hydration Mismatch)
서버가 그린 HTML과 클라이언트가 처음 렌더한 결과가 **다르면** 에러가 난다.

```
Warning: Text content did not match.
Server: "2026-08-31"  Client: "2026-09-01"
```

전형적인 원인
* `new Date()` · `Math.random()` — 서버와 클라이언트의 실행 시점이 다름
* `window` · `localStorage` — 서버엔 없음
* 브라우저 확장 프로그램이 DOM을 건드림
* 서버/클라이언트의 타임존·로케일 차이

해결은 대개 **"클라이언트에서만 렌더"** 로 미루는 것이다. 마운트 이후에 그리도록 분기하거나, 해당 부분만 동적 로딩한다.

### 3. 번들을 다 받아야 시작된다
전통적 하이드레이션은 **페이지 전체 JS**를 받아야 시작한다. 그래서 화면 일부만 상호작용이 필요해도 전부를 기다린다.

## 개선 기법

| 기법 | 아이디어 |
| ----------- | ----------- |
| **Selective Hydration** | 중요한 영역부터 순서대로 하이드레이션. React 18의 Suspense 기반 |
| **Progressive Hydration** | 화면에 보이는 부분만 먼저, 나머지는 스크롤 시 |
| **Islands Architecture** | 페이지 대부분은 정적으로 두고, 상호작용이 필요한 "섬"만 하이드레이션 |
| **RSC (Server Components)** | 서버 전용 컴포넌트는 **아예 하이드레이션하지 않는다.** JS 번들에 포함되지도 않음 |

RSC가 근본적인 해법에 가깝다. "하이드레이션을 빠르게 하자"가 아니라 **"하이드레이션할 필요가 없는 컴포넌트를 늘리자"** 는 접근이기 때문.

## 정리

* 하이드레이션 = **HTML 껍데기 + JS = 살아있는 UI**
* [[클라이언트 사이드 렌더링(CSR)]] 은 애초에 HTML이 비어 있으므로 이 단계가 없다
* 서버 렌더링의 이득(빠른 첫 화면)에는 **하이드레이션 비용**이 딸려온다. 공짜가 아니다
