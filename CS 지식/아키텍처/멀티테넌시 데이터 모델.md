# 멀티테넌시 데이터 모델
----

하나의 애플리케이션 인스턴스로 **여러 고객사(테넌트)** 를 동시에 서비스하는 구조. SaaS의 기본 전제.

테넌트 = 데이터가 서로 보이면 안 되는 경계. B2B SaaS라면 보통 **고객사 하나 = 테넌트 하나**다.

## 1. 격리 전략 3가지

### ① 테넌트별 DB 분리 (Database per tenant)
테넌트마다 데이터베이스를 통째로 따로 둔다.

- 장점 — 격리 수준 최상. 백업/복원이 테넌트 단위. 대형 고객의 부하가 다른 테넌트에 안 튐. 규제 대응(데이터 소재지) 쉬움
- 단점 — 테넌트가 늘수록 커넥션·마이그레이션 관리가 폭발. 100개 DB에 스키마 변경을 어떻게 다 돌릴 것인가. 소규모 테넌트에는 비용 과다
- 언제 — 테넌트 수가 적고 각각 크다. 금융·의료처럼 격리가 계약 조건

### ② 스키마 분리 (Schema per tenant)
DB는 하나, 스키마(PostgreSQL) 또는 데이터베이스명(MySQL)을 테넌트별로 나눈다.

- 장점 — ①보다 가볍고 격리도 어느 정도 유지
- 단점 — 여전히 마이그레이션이 N번. MySQL은 스키마 개념이 약해 결국 DB 분리와 비슷해짐
- 언제 — PostgreSQL이고 테넌트가 중간 규모

### ③ 공유 테이블 + TenantId 컬럼 (Shared schema)
모든 테넌트가 같은 테이블을 쓰고, 행마다 `TenantId` 로 구분한다.

- 장점 — **운영이 제일 단순.** 마이그레이션 한 번. 테넌트 수가 늘어도 인프라가 그대로. 크로스 테넌트 집계(본사 통합 대시보드 등)가 쿼리 하나
- 단점 — **`WHERE TenantId = ?` 를 한 번이라도 빠뜨리면 데이터가 샌다.** 이게 유일하지만 치명적인 단점
- 언제 — 테넌트가 많고 각각 작다. 대부분의 B2B SaaS

## 2. ③을 쓸 때 반드시 해야 하는 것

TenantId 조건 누락은 **코드 리뷰로 막을 수 없다.** 구조로 막아야 한다.

- **인덱스 선두 컬럼을 TenantId로** — `INDEX (TenantId, IsActive)` 처럼. 조회가 항상 테넌트로 먼저 좁혀지게 → [[TypeORM 엔티티 설계]]
- **리포지토리 계층에서 강제** — 요청 컨텍스트의 테넌트를 자동으로 주입하는 래퍼를 두고, 원시 쿼리를 직접 못 쓰게 한다
- **RLS(Row-Level Security)** — PostgreSQL이면 DB가 강제해준다. MySQL엔 없어서 애플리케이션 계층 규율에 의존
	- 2026-09-01 확인 — PostgreSQL은 `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + `CREATE POLICY` 로 제공한다([공식 문서](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). MySQL 8에는 이에 대응하는 문법이 **없다.** 굳이 흉내 내려면 실제 테이블 접근을 막고 `WITH CHECK OPTION` 뷰나 저장 프로시저로만 열어주는 방식인데, 이건 DB가 강제하는 게 아니라 **권한 설계로 우회로를 막는 것**이라 성격이 다르다
	- ⚠️ **PostgreSQL RLS를 켜도 안심하면 안 된다.** 슈퍼유저와 `BYPASSRLS` 속성을 가진 롤은 **항상 정책을 통과**하고, **테이블 소유자도 기본적으로 통과**한다. 앱이 테이블 소유자 계정으로 붙는 흔한 구성이면 정책이 사실상 무력하다는 뜻
	- 그래서 두 가지가 따라온다 — 소유자에게도 정책을 적용하려면 `ALTER TABLE ... FORCE ROW LEVEL SECURITY`, 그리고 **앱은 소유자가 아닌 전용 롤로 접속**시킬 것
- 크로스 테넌트 조회는 **명시적으로 다른 경로**를 통해서만 (예: 본사 관리자 전용 서비스)

## 3. 함정 — 사용자를 테넌트에 종속시키면 생기는 문제

여기가 이번에 실제로 부딪힌 부분이다.

ASP.NET Identity 스키마를 그대로 가져오면서 `UserName` 을 이렇게 만드는 방식이 있다.

```
UserName           = {Email}.{TenantId}      예) admin@aiet.co.kr.root
NormalizedUserName = 위를 대문자로            예) ADMIN@AIET.CO.KR.ROOT   (unique index)
NormalizedEmail    = Email을 대문자로         예) ADMIN@AIET.CO.KR        (일반 index)
```

`UserName` 에 테넌트를 박아 unique를 걸면 **같은 이메일이 여러 테넌트에 각각 존재할 수 있다.** 이게 목적이다 — 김수진이 A매장 직원이면서 B매장 직원일 수 있으니까.

### 그런데 모든 사용자가 그래도 되는 건 아니다

플랫폼에 **두 종류의 사용자**가 있으면 이 구조가 깨진다.

| 사용자 유형 | 성격 | 예시 |
| ----------- | ----------- | ----------- |
| **테넌트 소속 사용자** | 특정 고객사에 고용됨. 테넌트 종속이 맞음 | 매장 직원, 점장, 수의사 |
| **플랫폼 전역 사용자** | 여러 테넌트를 넘나드는 최종 소비자 | 보호자(반려동물 주인) |

보호자는
- 매장 A와 매장 B를 **동시에** 이용할 수 있고 (연동은 매장별 초대코드)
- 동물병원 C에서도 **같은 반려동물 프로필**을 참조해야 하고
- 매장을 안 쓰다가 나중에 연동될 수도 있다

`{Email}.{TenantId}` 구조면 매장 2곳을 쓸 때 **계정이 2개로 쪼개진다.** 그러면
- 반려동물 프로필이 중복 생성됨
- 건강 이력이 매장별로 단절됨 → "데이터를 하나의 프로필로 통합"이라는 핵심 가치가 그대로 무너짐
- 로그인할 때 "어느 매장 계정으로 들어오셨나요"를 물어야 함 (최악의 UX)

### 해결

```
IdentityUser              ← 전역 유일. Email 하나 = 계정 하나
   │
   ├─ TenantMembership    ← N:M. 어느 테넌트에 어떤 역할로 속하는가
   │     UserId, TenantId, Role, JoinedOn
   │
   └─ Pet                 ← 보호자 소유. 테넌트 종속 아님
         │
         └─ PetTenantLink ← N:M. 이 반려동물이 어느 매장/병원에 등록됐는가
               PetId, TenantId, LinkedOn, Status
```

핵심은 **사용자·반려동물은 전역 엔티티**로 두고, **테넌트와의 관계를 별도 연결 테이블로 빼는 것.** 그러면
- 같은 계정으로 여러 매장을 볼 수 있음
- 매장 전환이 로그인이 아니라 **컨텍스트 전환**이 됨
- 매장을 끊어도 계정과 반려동물 데이터는 남음

### 교훈

> **"이 엔티티가 테넌트 안에 사는가, 테넌트를 넘나드는가"** 를 설계 초기에 엔티티별로 정해야 한다.

나중에 고치려면 unique index 재설계 + 데이터 병합 + 로그인 흐름 변경이 한꺼번에 온다. 계정 병합은 사용자에게 보이는 마이그레이션이라 특히 비싸다.

## 4. 프론트엔드에도 테넌트 개념이 필요하다

서버가 테넌트 구조면 클라이언트에도 "현재 테넌트" 컨텍스트가 있어야 한다. **이걸 URL 경로에 넣는 걸 권장.** ([[상태 관리]] · [[쿼리스트링(Query String)]])

```
/stores/$storeId/monitoring
/stores/$storeId/alerts
```

- 매장 전환이 URL로 표현됨 → 링크 공유·북마크·새로고침이 자연스럽게 동작
- 나중에 본사 통합관제처럼 **여러 테넌트를 가로지르는 화면**을 추가할 때 구조가 그대로 산다
- 전역 상태에만 두면 "어느 매장을 보고 있었는지"가 새로고침에 날아간다 — [[싱글 페이지 애플리케이션(SPA)]]에서 흔한 함정

## 5. 정리

- 격리 전략 3가지 — **DB 분리 / 스키마 분리 / 공유 테이블 + TenantId**. 대부분의 B2B SaaS는 세 번째
- 공유 테이블은 **TenantId 누락이 유일하지만 치명적인 위험.** 인덱스 선두 컬럼 + 리포지토리 계층 강제로 구조적으로 막을 것
- **모든 사용자가 테넌트에 종속되는 건 아니다.** 소비자(최종 사용자)는 보통 전역 엔티티여야 한다
- 엔티티마다 "테넌트 안인가 밖인가"를 **초기에** 결정할 것. 나중에 바꾸면 계정 병합까지 따라온다
- 프론트에서는 테넌트를 **URL 경로**에 두는 게 유리

인증 설계는 [[세션 vs JWT vs OAuth]], 스키마 구현은 [[TypeORM 엔티티 설계]]에 정리했다.
