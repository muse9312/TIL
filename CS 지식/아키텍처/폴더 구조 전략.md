# 폴더 구조 전략
----

**무엇을 기준으로 파일을 묶을 것인가**의 문제. 크게 **기술별(type-based)** · **기능별(feature-based)** · **아키텍처 강제형(FSD 등)** 세 갈래다.

폴더 구조는 취향 문제로 보이지만 실제로는 **의존 관계를 눈에 보이게 만드는 장치**다. 폴더가 곧 경계고, 경계가 없으면 [[응집도와 결합도]]를 관리할 수단이 없다.

## 1. 기술별 분류 — 파일의 "종류"로 묶기

```
src/
├── components/    Button, AlertTable, PetCard, StoreSelector, ...
├── hooks/         useAlerts, usePets, useDebounce, ...
├── api/           alerts.ts, pets.ts, stores.ts
├── types/
├── utils/
└── pages/
```

React 튜토리얼과 프레임워크 기본 템플릿이 거의 다 이 형태다. 그래서 **모든 프로젝트의 출발점**이 된다.

### 장점
* 진입장벽이 0. 설명이 필요 없다
* 파일이 적을 때는 진짜로 편하다 — 훅을 찾으려면 `hooks/`를 열면 된다
* 새 파일을 어디 둘지 고민이 없다

### 왜 커지면 무너지는가

문제는 폴더가 지저분해지는 게 아니다. **하나의 변경이 항상 여러 폴더로 흩어진다**는 게 문제다.

알람 기능 하나를 고치려면
```
components/AlertTable.tsx
components/AlertBadge.tsx
hooks/useAlerts.ts
api/alerts.ts
types/alert.ts
utils/formatAlertLevel.ts
```
여섯 폴더를 오간다. 기능은 하나인데 코드가 여섯 군데에 있다. **같이 바뀌는 것이 같이 있지 않다** — 응집도가 낮은 상태의 정의 그대로다.

여기서 세 가지가 연쇄로 따라온다.

* **삭제가 불가능해진다.** 기능을 접을 때 `components/`에서 지운 컴포넌트가 참조하던 훅이 다른 데서도 쓰이는지 알 수 없다. 그래서 아무도 안 지우고, 죽은 코드가 계속 쌓인다
* **경계가 없어서 아무나 아무거나 부른다.** `components/AlertTable`이 `hooks/usePets`를 import해도 막을 근거가 없다. 시간이 지나면 의존 그래프가 스파게티가 되고 순환 참조가 생긴다 → [[단방향 의존성]]
* **`components/`가 50개를 넘으면 검색으로만 산다.** 폴더가 정보를 주지 않는다

> 무너지는 정확한 지점은 파일 수가 아니라, **"이 파일이 저 파일을 알아도 되는가"를 처음 고민하게 되는 순간**이다.

## 2. 기능별 분류 — 도메인으로 묶기

```
src/
├── features/
│   ├── alerts/
│   │   ├── AlertTable.tsx
│   │   ├── useAlerts.ts
│   │   └── api.ts
│   └── pets/
└── shared/
```

하나의 기능에 필요한 모든 종류의 파일을 한 폴더에 넣는다. **폴더 안쪽은 여전히 기술별**이지만, 바깥 축이 도메인으로 바뀌었다.

### 장점
* **변경이 한 폴더 안에서 끝난다.** 기능 단위로 코드를 읽을 수 있다
* **삭제가 폴더 삭제**가 된다
* 팀을 나눠 일할 때 충돌이 준다

### 단점 · 남는 문제
* **`shared`가 쓰레기통이 된다.** 두 기능이 같이 쓰는 걸 넣다 보면 잡동사니 폴더가 되고, 결국 1번의 `utils/` 문제가 그대로 재현된다
* **기능끼리 서로 부르는 걸 아무도 안 막는다.** `features/alerts`가 `features/pets`를 import하면? 대개 그냥 한다. 이게 반복되면 폴더는 나뉘었는데 의존은 얽힌 상태가 된다
* **"기능"의 크기 기준이 없다.** 알람이 기능인가, 알람 확인 처리가 기능인가. 사람마다 다르게 자른다
* 규칙이 **문서로만 존재**해서 검사할 방법이 없다

## 3. 아키텍처 강제형 — FSD

2번의 남는 문제 세 개(공유 폴더, 기능 간 참조, 크기 기준)를 **규칙으로 못 박은 것**이 [[Feature-Sliced Design(FSD)]]다.

* 공유 폴더 → `shared`·`entities`로 **층위를 나눠** 무엇을 어디 내릴지 기준을 준다
* 기능 간 참조 → **같은 층 슬라이스끼리 import 금지**
* 크기 기준 → 레이어 정의로 대략의 눈금을 준다

대신 규칙이 늘어난 만큼 **배워야 할 게 늘고, 강제 도구 없이는 지켜지지 않는다.**

## 4. 셋 비교

| | 기술별 | 기능별 | FSD |
| ----------- | ----------- | ----------- | ----------- |
| 묶는 기준 | 파일의 종류 | 도메인 | 도메인 + 층위 |
| 변경 범위 | 여러 폴더로 흩어짐 | 한 폴더 | 한 슬라이스 |
| 기능 삭제 | 사실상 불가 | 폴더 삭제 | 폴더 삭제 |
| 의존 방향 | 규칙 없음 | 규칙 없음 | **아래로만, 강제됨** |
| 공유 코드 | `utils/` 쓰레기통 | `shared/` 쓰레기통 | `shared`/`entities` 층위 |
| 자동 검사 | 불가 | 불가 | **가능** (린터) |
| 학습 비용 | 없음 | 낮음 | 높음 |
| 보일러플레이트 | 없음 | 적음 | 많음 |

## 5. 판단 기준

| 상황 | 권장 |
| ----------- | ----------- |
| 화면 5개 미만, 혼자, 수명 짧음 | **기술별.** 다른 걸 쓰는 게 낭비다 |
| 화면 10~30개, 도메인이 뚜렷 | **기능별.** 대부분의 프로젝트가 여기 |
| 여러 명, 수년 유지, 도메인이 얽힘 | **FSD.** 규칙 강제의 값어치가 나온다 |
| 라이브러리 · 디자인 시스템 | 기술별에 가깝다. 도메인이 없으니 |

세 가지 질문으로 좁혀진다.

1. **한 기능을 고칠 때 몇 개 폴더를 여는가?** 셋 이상이면 기술별의 한계에 왔다
2. **기능 하나를 통째로 지울 수 있는가?** 못 지우면 경계가 없는 것
3. **"A가 B를 import해도 되나"를 고민한 적 있는가?** 있다면 규칙이 필요한 단계

### 마이그레이션은 한 방향이 싸다

`기술별 → 기능별 → FSD` 방향은 **파일을 모으는** 작업이라 상대적으로 싸다. 반대 방향(FSD를 풀어 기술별로)은 거의 일어나지 않는다.

다만 **아무 때나 싸지는 않다.** 비용은 파일 수가 아니라 **업무 로직의 양과 얽힘 정도**에 비례한다. 껍데기만 있을 때는 경로 치환이고, 로직이 쌓인 뒤에는 도메인 재설계가 된다. 그래서 구조 결정은 **가장 이른 시점에 하는 게 가장 싸다** — 정작 그때는 필요성이 안 느껴진다는 게 이 문제의 본질적인 어려움이다.

> 절충안: **아직 모르겠으면 기능별로 시작하되 `shared`를 규율 있게 관리하라.** 여기서 FSD로 가는 길은 남아 있고, 기술별로 시작하면 그 길이 훨씬 비싸진다.

## 정리

* 폴더 구조는 취향이 아니라 **의존 경계를 가시화하는 장치**다
* **기술별**은 시작이 쉽지만 **하나의 변경이 여러 폴더로 흩어진다.** 삭제 불가·경계 없음이 따라온다
* **기능별**이 그걸 해결하지만 **공유 폴더 쓰레기통 · 기능 간 참조 · 크기 기준**이 남는다
* **[[Feature-Sliced Design(FSD)]]** 는 그 셋을 규칙으로 못 박은 것. 대가는 학습 비용과 보일러플레이트
* 판단 질문 — 한 기능에 몇 폴더를 여는가 / 통째로 지울 수 있는가 / import 가능 여부를 고민한 적 있는가
* 전환은 **모으는 방향이 싸고, 이를수록 싸다**
