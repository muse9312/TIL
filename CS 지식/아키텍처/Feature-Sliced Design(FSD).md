# Feature-Sliced Design(FSD)
----

프론트엔드 프로젝트를 **레이어 → 슬라이스 → 세그먼트** 3층으로 자르고, **의존 방향을 위에서 아래로만** 강제하는 아키텍처 방법론.

핵심 주장은 하나다. **폴더 구조를 규약이 아니라 검사 가능한 규칙으로 만든다.** [[폴더 구조 전략]]의 여러 갈래 중, 규칙을 린터로 강제할 수 있을 만큼 구체적으로 못 박은 쪽이 FSD다.

> 기준: **스펙 v2.1**. v2에서 `processes` 레이어가 폐기됐다.

## 1. 3층 구조

```
src/
├── app/                  ← 레이어 (슬라이스 없음)
│   ├── providers/
│   └── styles/
├── pages/
│   └── alerts/           ← 슬라이스 (업무 도메인 단위)
│       ├── ui/           ← 세그먼트
│       ├── api/
│       └── model/
├── widgets/
├── features/
├── entities/
└── shared/               ← 레이어 (슬라이스 없음)
    ├── ui/
    ├── api/
    └── lib/
```

### ① 레이어 — 책임의 층위

| 레이어 | 책임 | 예 |
| ----------- | ----------- | ----------- |
| `app` | 앱 전체 설정 — 프로바이더, 전역 스타일, 라우터 초기화 | `QueryClientProvider`, 테마 |
| ~~`processes`~~ | **v2에서 폐기됨.** 여러 페이지에 걸친 흐름 | (사용하지 말 것) |
| `pages` | 라우트 하나에 대응하는 완결된 화면 | 알람 목록 화면, 재원 현황 화면 |
| `widgets` | 여러 기능을 합친 **자립형 UI 블록** | 사이드바, 실시간 알람 패널 |
| `features` | 사용자가 하는 **행위**, 업무 가치가 있는 동작 | 알람 확인 처리, 구역 필터 |
| `entities` | 업무 **명사** — 도메인 객체와 그 표현 | 반려동물, 매장, 알람 이벤트 |
| `shared` | 업무 지식이 없는 재사용 코드 | 버튼, `fetch` 래퍼, 날짜 유틸 |

규칙 세 가지가 따라붙는다.

* **모든 레이어는 선택적이다.** 필수 레이어는 없다. `widgets` 없이 `pages`에서 바로 `entities`를 써도 스펙 위반이 아니다
* `app` 과 `shared` 는 **슬라이스가 없다.** 세그먼트로 바로 나뉜다. 업무 도메인이 없는 층이라 자를 축이 없기 때문
* 나머지 네 레이어(`pages`·`widgets`·`features`·`entities`)는 **슬라이스 먼저, 그 안에 세그먼트**

### ② 슬라이스 — 업무 도메인

`entities/pet`, `features/acknowledge-alert` 처럼 **무엇에 관한 코드인가**로 자른다. 슬라이스 이름은 기술 용어가 아니라 업무 용어여야 한다. 이 축이 [[응집도와 결합도]]에서 말하는 "같이 바뀌는 것을 같이 둔다"에 해당한다.

### ③ 세그먼트 — 기술적 성격

| 세그먼트 | 담는 것 |
| ----------- | ----------- |
| `ui` | 컴포넌트, 스타일 |
| `api` | 백엔드 통신, 요청 |
| `model` | 스키마, 스토어, 업무 로직 |
| `lib` | **그 슬라이스 안에서만** 쓰는 유틸 |
| `config` | 설정, 기능 플래그 |

세그먼트는 기술별 분류다. 즉 FSD는 **바깥은 도메인으로, 안쪽은 기술로** 자른다. 프로젝트 최상위를 `components/`·`hooks/`로 나누는 방식이 무너지는 이유는 이 순서를 뒤집었기 때문이다 → [[폴더 구조 전략]]

## 2. import 규칙 — 이게 전부다

> 한 레이어의 모듈은 자기보다 **엄격히 아래** 레이어만 알고 import할 수 있다.
> **같은 레이어의 슬라이스끼리는 서로 import하지 못한다.**

```
app  →  pages  →  widgets  →  features  →  entities  →  shared
                  (아래로만. 옆으로도 안 됨)
```

```ts
// ✅ features → entities
import { PetCard } from '@/entities/pet';

// ❌ entities → features  (위로 올라감)
// ❌ features/alert-filter → features/acknowledge-alert  (같은 층 옆으로)
```

두 번째 규칙이 더 아프고, 더 중요하다. 같은 층 슬라이스끼리 막으면 **순환 참조가 구조적으로 불가능**해진다. 왜 그게 목표인지는 [[단방향 의존성]]에 정리했다.

### 옆으로 못 갈 때 뭘 하는가

두 슬라이스가 서로를 필요로 한다면 **공통분모를 아래 레이어로 내린다.** 이게 유일한 정답이고, 대부분의 FSD 리팩터링은 이 작업이다.

실제로 자주 걸리는 예가 **스키마 상호 참조**다.

```ts
// entities/detection-event/model/schema.ts
export const detectionEventSchema = z.object({ ... });

// entities/alert/model/schema.ts
import { detectionEventSchema } from '@/entities/detection-event';  // ❌ 같은 층
export const alertSchema = detectionEventSchema.extend({ level: ... });
```

zod 스키마는 서로 `extend`·`pick`으로 엮이기 쉬운데, 이게 그대로 같은 층 import 금지에 걸린다. 해법은 **공통 원시 타입을 `shared/api/schema`로 내리는 것**이다.

```
shared/api/schema.ts        ← eventBaseSchema, levelEnum, timestampSchema
        ↑              ↑
entities/detection-event   entities/alert     (각자 shared에서 가져와 확장)
```

내려보내고 나면 두 엔티티가 서로를 모른다. 이 작업 자체가 "무엇이 진짜 공통인가"를 강제로 정의하게 만든다는 게 FSD의 실질적 이득이다.

### 예외 — `@x` 표기
엔티티끼리의 참조가 정말 불가피할 때만 쓰는 **크로스 임포트 공개 API**가 스펙에 있다. `entities/alert/@x/detection-event.ts` 처럼 "이 슬라이스에만 열어주는 문"을 만든다. **탈출구지 기본값이 아니다.** 남발하면 규칙이 있으나 마나가 된다.

## 3. 가장 많이 틀리는 경계 — features vs widgets vs entities

FSD 도입 실패의 대부분이 여기서 난다. 레이어를 **나중에 추가하는 건 쉽지만, 잘못 자른 슬라이스를 되돌리는 건 어렵다.** 파일 이동이 아니라 import 그래프 전체가 따라 움직이기 때문이다.

판별 질문은 세 개다.

| 질문 | 그렇다면 |
| ----------- | ----------- |
| 이게 **명사**인가, 그 자체로 존재하는가? | `entities` |
| 사용자가 이걸 **한다**고 말할 수 있나? (동사) | `features` |
| 여러 기능을 **조립한 덩어리**이고, 어느 페이지에 붙여도 혼자 동작하나? | `widgets` |

### "실시간 알람 피드"는 어디에 두는가

실제로 팀 의견이 갈리는 케이스다. 답이 하나가 아니라서 갈린다.

| 해석 | 배치 | 근거 |
| ----------- | ----------- | ----------- |
| 알람이라는 **데이터를 보여주는 것** | `entities/alert/ui` | 표현일 뿐 행위가 없다 |
| 필터·확인처리 등 **조작이 붙은 기능** | `features/alert-feed` | 사용자가 하는 일이 있다 |
| 헤더·사이드바처럼 **어디에나 붙는 블록** | `widgets/alert-feed` | 여러 페이지에서 재사용 |
| 알람 화면에서만 쓰는 조각 | `pages/alerts/ui` | 재사용 계획이 없다 |

실무 기준은 **"지금 재사용되는가"** 다. 한 페이지에서만 쓰이면 그 페이지 슬라이스 안에 두고, 두 번째 사용처가 생길 때 위로 끌어올린다. 미래를 예측해서 미리 `widgets`에 두면 대개 틀린다.

> 판단이 갈릴 때는 **일단 더 위쪽(pages)에 두는 게 안전하다.** 위에서 아래로 내리는 건 쉽고, 아래에 잘못 둔 걸 위로 올리는 건 그 슬라이스를 참조하던 모든 코드가 깨진다.

## 4. 강제하지 않으면 무너진다

FSD는 **규칙을 지켰을 때만 이득이 나오는** 구조다. 규칙 하나만 새도 나머지 규칙의 근거가 사라진다. 사람의 리뷰로는 못 막는다 — 몇 주면 무너진다는 게 이 방법론에 대한 가장 흔한 후기다.

도구 상황은 다음과 같다. (2026년 9월 기준 npm 레지스트리 확인)

| 도구 | 최신 | 최근 배포 | 상태 |
| ----------- | ----------- | ----------- | ----------- |
| `steiger` + `@feature-sliced/steiger-plugin` | 0.6.0 / 0.7.0 | 2026-07 | **공식 린터.** 유지보수 중이나 여전히 0.x 베타 — API가 바뀔 수 있다 |
| `@feature-sliced/eslint-config` | 0.1.1 | **2024-04** | 사실상 정체. `eslint-plugin-boundaries`·`import`를 조합한 **eslintrc 기반**이라 ESLint 9 flat config 프로젝트에는 그대로 못 붙는다 |
| `eslint-plugin-import-fsd` | 3.0.4 | 2026-06 | 비공식. ESLint 9 flat config 지원 |
| `eslint-plugin-fsd-lint` | 1.2.1 | 2026-04 | 비공식. ESLint 9+ flat config 지원 |

정리하면 **공식 ESLint 설정은 낡았고, 살아 있는 선택지는 `steiger`(별도 CLI) 또는 서드파티 ESLint 플러그인**이다. `steiger`는 ESLint와 별개 프로세스라 CI에 한 줄을 더 넣어야 하고, 에디터에서 실시간으로 빨간 줄이 안 뜬다. 반대로 ESLint 플러그인은 에디터에 바로 붙지만 공식이 아니라 스펙 변경을 따라온다는 보장이 없다.

> 도입한다면 **첫 커밋에 린터를 같이 넣어라.** 나중에 붙이면 이미 쌓인 위반을 전부 고쳐야 해서 대개 안 붙인다.

검사의 층을 하나 더 얹는 방법도 있다. 커밋 메시지의 scope 를 레이어 이름으로 고정하면(→ [[Conventional Commits]]) **레이어 위반이 커밋 로그에서도 드러난다.** `feat(shared)` 커밋이 `entities/` 를 건드렸다면 방향이 뒤집힌 것이다. 린터를 대신하지는 못하지만, 리뷰어가 diff 를 열기 전에 냄새를 맡게 해준다.

## 5. 장점과 단점

### 장점
* **파일 위치가 토론거리가 아니게 된다.** "이거 어디 둬요"에 답이 있다. 온보딩 비용이 크게 준다
* **삭제가 쉽다.** 기능을 접을 때 슬라이스 폴더 하나를 지우면 끝난다. 기술별 분류에서는 다섯 폴더를 뒤져야 한다
* **영향 범위가 예측된다.** 아래 레이어를 고치면 위가 영향받고, 그 반대는 절대 없다
* **순환 참조가 구조적으로 불가능**하다 → [[단방향 의존성]]
* 규칙이 기계적이라 **린터로 검사 가능**하다. 대부분의 폴더 규약과 다른 결정적 차이

### 단점 · 함정
* **초기 보일러플레이트가 많다.** 버튼 하나 추가하는 데 슬라이스·세그먼트·`index.ts`가 따라온다. 작은 앱에서는 순수 비용이다
* **경계 판단에 계속 에너지가 든다.** 3절의 features/widgets 논쟁이 기능마다 반복된다. 팀 합의가 없으면 사람마다 다르게 자른다
* **`index.ts` 배럴이 레이어·슬라이스마다 늘어난다.** 캡슐화 이득과 동시에 번들러·개발 서버 성능 함정을 데려온다 → [[공개 API와 배럴 파일]]
* **파일 기반 라우팅과 자리를 다툰다.** `pages` 레이어와 라우터의 `routes/`가 겹친다 → [[FSD와 파일 기반 라우팅의 충돌]]
* **UI 라이브러리 CLI의 생성 경로와 어긋난다.** shadcn/ui는 `components.json`의 alias를 따라 파일을 만드는데, 이걸 `shared/ui`로 안 바꾸면 컴포넌트가 **두 군데로 갈라진다.** 코드를 옮기는 것보다 도구 설정을 같이 옮기는 걸 잊는 쪽이 사고가 크다
* **공식 도구가 아직 0.x다.** 4절 참고
* **`processes` 레이어 자료가 아직 인터넷에 남아 있다.** 폐기된 레이어라 새로 쓰면 안 되는데 블로그 글은 그대로다

## 6. 언제 맞고, 언제 과한가

| | FSD가 맞다 | 과하다 |
| ----------- | ----------- | ----------- |
| 수명 | 수년간 유지·확장 | 데모, PoC, 사내 도구 |
| 인원 | 여럿이 같은 코드를 만짐 | 혼자 |
| 도메인 | 업무 개념이 많고 서로 얽힘 | 화면 몇 개, 로직 거의 없음 |
| 화면 수 | 수십 개 이상으로 갈 예정 | 열 개 미만에서 끝 |

FSD가 푸는 문제는 **"이 코드가 저 코드를 알아도 되는가"** 다. 이 질문이 생기지 않는 규모에서는 답만 있고 문제가 없다.

### 도입 시점이 규모보다 중요하다

역설이 하나 있다. **FSD의 이득은 코드가 커진 뒤에 나오는데, 도입 비용은 커질수록 비싸진다.** 그래서 "충분히 커지면 도입하자"는 대개 "영원히 안 한다"가 된다.

전환 비용은 파일 수가 아니라 **업무 로직의 양**에 비례한다. 화면 껍데기만 있을 때는 폴더를 옮기고 import 경로를 고치면 끝이지만, 로직이 쌓인 뒤에는 슬라이스 경계를 정하는 일 자체가 도메인 재설계가 된다.

### 펫바디 관제 대시보드에서의 검토 (미결)

B2B 관제 대시보드를 [[싱글 페이지 애플리케이션(SPA)]]로 만들고 있고, FSD 도입 여부는 **아직 결정하지 않았다.** 검토에서 나온 논점만 남겨둔다.

**도입 쪽 근거**
* 소스가 15개 파일, 업무 로직 0줄 — **구조 변경 비용이 가장 싼 시점**이다. 지금 안 하면 다음 기회는 훨씬 비싸다
* 도메인이 이미 뚜렷하다. 매장 · 반려동물 · 감지 이벤트 · 알람 — `entities` 후보가 손에 잡힌다
* 화면이 관제/알람/재원/추이/히트맵으로 이미 다섯 갈래고, 여기서 더 늘어난다
* [[멀티테넌시 데이터 모델]] 때문에 "매장 컨텍스트"가 모든 화면을 관통한다. 컨텍스트가 어느 층에 사는지 정해두면 나중에 본사 통합관제 화면을 붙일 때 유리하다

**보류 쪽 근거**
* 아직 아무것도 안 만들어봐서 **`features` 경계를 판단할 근거가 없다.** 3절의 "실시간 알람 피드" 문제가 바로 첫 화면에서 터진다
* [[TanStack Router]] 파일 기반 라우팅과 `pages` 레이어가 겹친다. 어댑터를 두든 virtual routes를 쓰든 추가 비용이 생긴다 → [[FSD와 파일 기반 라우팅의 충돌]]
* shadcn/ui alias를 `shared/ui`로 옮겨야 하고, 안 옮기면 생성 위치가 갈린다
* 공식 린터가 0.x, 공식 ESLint 설정은 flat config를 못 따라왔다

**중간 선택지**도 있다. 모든 레이어가 선택적이라는 스펙을 이용해 **`shared` / `entities` / `pages` 세 층만 먼저 세우고**, `features`·`widgets`는 실제로 필요해질 때 끼워 넣는 방식이다. 위로 레이어를 추가하는 건 값이 싸고, 잘못 자른 슬라이스를 푸는 건 비싸다는 비대칭을 그대로 이용한 절충이다.

## 정리

* **레이어(층위) → 슬라이스(도메인) → 세그먼트(기술)** 3층. 바깥은 도메인으로, 안쪽은 기술로 자른다
* 규칙은 둘. **엄격히 아래로만 import**, **같은 층 슬라이스끼리 금지**. 두 번째가 순환 참조를 구조적으로 없앤다
* `app`·`shared`는 슬라이스가 없고, **모든 레이어는 선택적**이다. `processes`는 폐기됐다
* 같은 층에서 막히면 **공통분모를 아래로 내려라.** zod 스키마 상호 참조가 대표 사례
* **린터로 강제하지 않으면 몇 주 만에 무너진다.** 공식 `steiger`는 0.x, 공식 ESLint 설정은 flat config 미지원 — 첫 커밋에 같이 넣을 것
* 가장 많이 틀리는 곳은 **features/widgets 경계.** 애매하면 위쪽에 두고, 두 번째 사용처가 생길 때 내려라
* 도입 판단은 규모보다 **시점.** 이득은 커진 뒤에 나오고 비용은 커질수록 비싸다
