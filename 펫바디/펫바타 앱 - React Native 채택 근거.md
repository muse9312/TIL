# 펫바타 앱 - React Native 채택 근거
----

> 2026-10-12 결정. 상사에게 설명할 논리까지 포함한 **의사결정 기록**.

펫바타(B2C 보호자 앱, 피그마 PETVATAR '고객 앱' — 보호자 모드 + 매장 관리자 모드)는 **[[React Native]]([[Expo]] SDK 57)로 전부 구현**하고, 약관·공지·AI 교과서처럼 **읽기 전용 화면만 부분 [[웹뷰]]** 로 띄운다.
이전 데모 `piew-dev`(Expo + RN 0.86 + expo-router + NativeWind, iOS/Android [[홈 화면 위젯]]·[[Live Activity]] 검증)의 위젯 코드를 재사용한다.

> Expo SDK 57 = React Native 0.86 · React 19.2 (2026-06-30 릴리스, 2026-10-12 확인) — [Expo changelog](https://expo.dev/changelog/sdk-57)

## 1. 검토한 안

| 안 | 요약 | 결과 |
| ----------- | ----------- | ----------- |
| ① PWA | 웹을 홈 화면에 설치 | 탈락 |
| ② Capacitor | 웹을 네이티브 셸에 감싸기 | 탈락 |
| ③ 전체 웹뷰 + Expo 셸 | 화면은 전부 웹, 위젯·Live Activity만 RN | 탈락 (상사가 물을 수 있는 안, Q2) |
| ④ **RN 전체 + 읽기 전용 화면만 웹뷰** | 화면 성격에 따라 나눔 | **채택** |

### ① PWA
* 스토어 배포 불가 (Android TWA 제외)
* 홈 화면 위젯 불가
* iOS [[푸시 알림]]은 **홈 화면에 설치해야** 권한 요청 가능
	* iOS 16.4부터 지원, 설치된 웹앱에서 사용자 동작에 응답할 때만 요청 가능 (2026-10-12 확인) — [WebKit 블로그](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

### ② Capacitor
* 장점: 웹 스택(petbody-client)을 그대로 재사용
* 단점: 위젯·Live Activity를 Swift/Kotlin으로 **새로 작성**해야 함. piew-dev의 RN 자산을 못 씀

### ③ 전체 웹뷰 + Expo 셸
* 장점: 화면 개발을 웹 개발자가 그대로 맡을 수 있음. 모바일 웹과 화면 공유 가능
* 단점: 웹 프로젝트 + 네이티브 앱 + 둘을 잇는 [[네이티브 브리지]]까지 **세 덩어리**를 관리. 자세한 건 Q2

### ④ RN 전체 + 읽기 전용 화면만 웹뷰 (채택)
* 장점: 위젯·푸시·카메라와 화면이 **같은 앱**이라 연결 코드가 없음. JS 변경은 [[EAS Update]]로 심사 없이 배포
* 단점: 모바일 웹 버전이 필요해지면 그 화면은 따로 만들어야 함. 웹 개발자가 RN UI 부품을 새로 익혀야 함

## 2. 왜 위젯은 웹으로 못 만드나

[[홈 화면 위젯]]은 앱이 꺼져 있어도 **OS가 직접 그린다** (iOS WidgetKit/SwiftUI, Android AppWidget/RemoteViews). WebView도, JS 상시 실행도 불가능하다. [[Live Activity]]도 같다.
그래서 어떤 안을 고르든 위젯은 네이티브로 짜야 하고, 남는 질문은 "화면을 그 네이티브 앱과 어떻게 묶을까"뿐이다.

```
앱 (또는 푸시로 깨어난 백그라운드)
   │  쓰기
   ▼
공유 저장소 ── iOS: App Group / Android: SharedPreferences
   │  읽기
   ▼
위젯이 다시 그림
   │  탭
   ▼
딥링크로 앱의 해당 화면 이동
```

### 위젯 자체의 제약
* **iOS 하루 리로드 예산**이 있다 → 같은 내용을 반복 갱신하지 않도록 막아야 함 (공식 문서상 자주 보는 위젯 기준 보통 하루 40~70회, 2026-10-15 확인 → [[홈 화면 위젯]])
* GIF·영상 재생 불가 → 펫바타 애니메이션은 정지 이미지로 대체
* 백그라운드 갱신용 푸시(iOS silent push / Android FCM data message)는 **백엔드 작업이 필요**

## 3. Q1. "왜 전부 웹뷰로 안 하고 RN 중심으로 갔나?"

> **한 줄 답**: "펫바타의 차별점인 홈 위젯·Live Activity·푸시·카메라가 전부 네이티브 기능이라, 웹뷰로 가도 결국 네이티브 앱을 같이 만들어야 합니다. 그럼 앱이 두 개가 되는 셈이라 RN으로 통일하고, 읽기 전용 화면만 웹뷰로 붙였습니다."

1. **웹뷰로 해도 네이티브 개발은 안 없어진다**
	* 위젯·Live Activity·[[푸시 알림]]·[[소셜 로그인]](카카오·애플·구글)·QR/펫스캔 카메라·권한
	* 결국 웹 프로젝트 + 네이티브 앱 + 연결 코드 3개를 관리하게 됨
2. **웹뷰의 최대 장점인 빠른 배포를 RN도 가진다**
	* [[EAS Update]]([[OTA 업데이트]])로 JS 변경은 심사 없이 즉시 배포
	* 단 네이티브 코드·네이티브 의존성·권한·SDK 버전 변경은 새 빌드가 필요 (2026-10-12 확인) — [EAS Update 문서](https://docs.expo.dev/eas-update/introduction/)
3. **사용자 경험**
	* 피그마가 캐러셀·바텀시트·탭 전환·카메라·사진 업로드 위주
	* 저가형 안드로이드 웹뷰는 스크롤·제스처·키보드 품질이 떨어짐. 매일 여는 앱이라 리텐션 직결
	* 웹을 감싼 앱은 [[App Store 심사 가이드라인 4.2]](최소 기능) 반려 위험 — "repackaged website" 이상의 기능·UI를 요구 (2026-10-12 확인) — [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality)
4. **검증된 자산**
	* piew-dev에서 RN으로 위젯·Live Activity를 양 플랫폼 구현해 봄
	* 데이터 라이브러리([[TanStack Query]]·[[zustand]]·react-hook-form·zod)가 웹 관제(petbody-client)와 같아 학습 비용이 작음

웹뷰를 버린 게 아니라 **화면 성격에 따라 나눴다.** 약관·공지·AI 교과서처럼 자주 바뀌고 읽기만 하는 화면은 [[웹뷰]]가 유리하다 → 앱 업데이트 없이 내용을 고친다.

## 4. Q2. "위젯·Live Activity만 네이티브로 하고 화면은 전부 웹뷰로 해도 되잖아?"

먼저 **"가능하고, 검토도 했다"고 인정**한다. 안 ③이 그것이다.

> **한 줄 답**: "네이티브로 빠지는 게 위젯만이 아니라 로그인·푸시·카메라·권한까지라서, 화면만 웹으로 빼면 그 사이 연결 작업이 커집니다. 화면을 RN으로 짜는 비용은 웹과 거의 같아서, 연결 작업이 없는 쪽을 골랐습니다."

1. **'위젯만 네이티브'가 실제로는 넓다**
	* 푸시 수신·탭 시 화면 이동, 카카오톡 앱 로그인, 토큰 안전 보관, 카메라·사진·위치·권한, 안드로이드 뒤로가기, 외부 링크로 앱 열기([[딥링크]])
	* 전부 "웹 → 앱에 요청 → 처리 → 웹에 결과" 형태의 [[네이티브 브리지]] 코드가 됨
2. **위젯이 화면과 데이터를 주고받아야 한다**
	* 로그인 정보·반려동물 상태를 웹이 매번 앱으로 넘기고, 위젯 탭 시 다시 웹 화면으로 보내야 함
	* RN이면 같은 앱이라 그냥 공유
3. **화면을 웹으로 짜도 비용이 안 줄어든다**
	* 둘 다 React + TS, 라이브러리도 같음
	* 웹뷰 쪽에만 연결 코드 + 웹·앱 두 프로젝트의 별도 배포·버전 맞춤이 **추가**됨. 줄어드는 건 없고 연결 작업만 늘어남
4. **배포 속도 차이 없음**([[EAS Update]]), 체감 품질은 RN 우위

| 비교 | ③ 전체 웹뷰 + Expo 셸 | ④ RN 전체 + 부분 웹뷰 |
| ----------- | ----------- | ----------- |
| 관리할 프로젝트 | 웹 + 앱 + 브리지 | 앱 하나 (+ 읽기 전용 웹 페이지) |
| 위젯 ↔ 화면 데이터 | 브리지로 왕복 | 같은 앱에서 공유 |
| JS 변경 배포 | 즉시 (웹 배포) | 즉시 (EAS Update) |
| 제스처·키보드 품질 | 기기 웹뷰에 좌우 | 네이티브 |
| 4.2 반려 위험 | 있음 | 낮음 |
| 모바일 웹 동시 서비스 | 유리 | 화면 별도 개발 |

### 상사 안이 더 맞는 경우 (솔직하게)
* 모바일 웹 버전도 똑같이 서비스해야 할 때
* 앞으로 화면 개발을 웹 개발자만 맡을 때

> **마무리 멘트**: "모바일 웹이 필요해지면 그 화면만 웹으로 추가할 수 있게 API 규격과 디자인 토큰을 공유하도록 설계해 뒀습니다. 지금 기준으로는 앱 하나로 가는 게 비용이 가장 작습니다."

## 5. 예상 추가 질문

| 질문 | 답 |
| ----------- | ----------- |
| 웹 개발자가 RN 할 수 있나? | React·TS 기반이라 문법·라이브러리 대부분 동일, UI 부품만 다름. piew-dev에서 이미 해봄 |
| 나중에 모바일 웹이 필요하면? | [[OpenAPI]]로 생성한 API 타입·zod 스키마와 [[디자인 토큰]]을 웹과 공유하게 설계. 필요한 화면만 웹으로 |
| 웹뷰가 맞는 경우는? | RN 인력이 없거나, 같은 서비스를 웹으로도 내야 하거나, 화면 대부분이 읽기 위주일 때. 펫바타는 해당 없음 |

## 정리
* 위젯·Live Activity는 OS가 그리므로 **어떤 안이든 네이티브가 필요**하다 → 질문은 "화면을 그 앱과 어떻게 묶나"
* 화면까지 RN으로 하면 [[네이티브 브리지]]가 사라지고, 배포 속도는 [[EAS Update]]로 웹뷰와 같다
* 웹뷰는 읽기 전용·자주 바뀌는 화면에만. 전체를 웹뷰로 하는 [[하이브리드 앱]]은 모바일 웹을 같이 낼 때 다시 검토
* 웹 관제(petbody-client)와 API 타입·디자인 토큰을 공유해 퇴로를 열어 둔다
